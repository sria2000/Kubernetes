# Authentication, Authorization & RBAC in Kubernetes

## Authentication

Authentication is the process of verifying a user's identity before granting access to the Kubernetes cluster.

**Documentation**

https://kubernetes.io/docs/reference/access-authn-authz/authentication/

### Categories

- Normal Users (Humans)
- Service Accounts (Applications)

### Simple Analogy

```
Username + Password
```

### Important Points

- Kubernetes does **not** manage normal user accounts natively.
- Normal users cannot be created through Kubernetes API objects.
- Kubernetes supports several authentication mechanisms including:
  - X.509 Client Certificates
  - Static Token Authentication
  - Bootstrap Tokens
  - Service Account Tokens
  - OpenID Connect (OIDC)

### Static Token Authentication

The API Server can read bearer tokens from a file specified using:

```bash
--token-auth-file
```

Example token file:

```text
Password,sri,01,admins
```

### X.509 Client Certificates

A common production authentication mechanism where users authenticate using client certificates.

# Authorization

Authorization determines **what an authenticated user is allowed to do**.

Authentication happens first, followed by Authorization.

Documentation:

https://kubernetes.io/docs/reference/access-authn-authz/authorization/

## Authorization Modes

| Mode | Description |
|------|-------------|
| AlwaysAllow | Allows every request (Testing only) |
| AlwaysDeny | Denies every request (Testing only) |
| RBAC | Role Based Access Control (Recommended) |

---

# RBAC (Role Based Access Control)

Documentation:

https://kubernetes.io/docs/reference/access-authn-authz/rbac/

RBAC controls what authenticated users and applications are allowed to do.

## Components

### Role

Defines a set of permissions.

### Subjects

The identities to whom permissions are granted.

Subjects can be:

- Users
- Groups
- Service Accounts

### RoleBinding

Connects a Role to a Subject.

### Namespace Scope

- **Role** permissions apply only inside a namespace.
- **ClusterRole** permissions apply across the cluster.

# Generate a Service Account Token

Generate the default token:

```bash
kubectl create token test-sa
```

Generate a token valid for 10 hours:

```bash
kubectl create token test-sa --duration=10h
```

Generate a token valid for 100 hours:

```bash
kubectl create token test-sa --duration=100h
```

# RBAC Concepts

## API Groups

API Groups determine which Kubernetes API group the permission applies to.

List available API groups:

```bash
kubectl api-resources --api-group=""
```

```bash
kubectl api-resources --api-group="apps"
```

### Common API Groups

| API Group | Resources |
|-----------|-----------|
| "" | Pods, Services, ConfigMaps, Secrets |
| apps | Deployments, ReplicaSets, DaemonSets |
| batch | Jobs, CronJobs |
| networking.k8s.io | Ingress, NetworkPolicies |

---

## Resources

Resources belong to API Groups.

Examples

Core API Group:

- pods
- services
- configmaps

Apps API Group:

- deployments
- daemonsets
- replicasets

---

## Verbs

Verbs define the operations allowed on resources.

Common verbs:

| Verb | Description |
|------|-------------|
| get | Read a resource |
| list | List resources |
| create | Create resources |
| update | Update resources |
| delete | Delete resources |
| watch | Watch resource changes |

# Create a Role

Create a Role that can list Pods.

```bash
kubectl create role pod-reader \
    --verb=list \
    --resource=pods
```

View Roles

Describe the Role

# Test Before RoleBinding

Replace the URL below with your API Server URL.

Linux/macOS

```bash
curl -k \
-H "Authorization: Bearer $TOKEN" \
https://<API_SERVER>:6443/api/v1/namespaces/default/pods
```

Without the proper RoleBinding you should receive a **403 Forbidden** response.

---

# Create a RoleBinding

> **Recommended Method**

```bash
kubectl create rolebinding test-rolebinding \
    --role=pod-reader \
    --serviceaccount=default:test-sa
```

Describe it:

```bash
kubectl describe rolebinding test-rolebinding
```

Expected Subject:

```text
Kind              Name      Namespace
ServiceAccount    test-sa   default
```

> Although `--user=system:serviceaccount:default:test-sa` works in some cases, using `--serviceaccount=default:test-sa` is the recommended and clearer approach.

# ClusterRole

A ClusterRole grants permissions across the entire Kubernetes cluster.

Create a ClusterRole

```bash
kubectl create clusterrole pod-reader \
    --verb=get,list,watch \
    --resource=pods
```

Describe it

```bash
kubectl describe clusterrole pod-reader
```

---

# ClusterRoleBinding

Bind the ClusterRole to the Service Account.

```bash
kubectl create clusterrolebinding test-clusterrole \
    --clusterrole=pod-reader \
    --serviceaccount=default:test-sa
```

Describe it

```bash
kubectl describe clusterrolebinding test-clusterrole
```

---

# Verify Permissions

```bash
kubectl auth can-i list pods \
    --as=system:serviceaccount:default:test-sa
```

Expected Output

```text
yes
```

# Role vs ClusterRole

| Feature | Role | ClusterRole |
|----------|------|-------------|
| Scope | Namespace | Entire Cluster |
| Used With | RoleBinding | ClusterRoleBinding |
| Can Access Cluster Resources | No | Yes |
| Typical Use | Namespace-specific permissions | Cluster-wide permissions |
