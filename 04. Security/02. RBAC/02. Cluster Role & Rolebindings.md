# Kubernetes ClusterRole and ClusterRoleBinding Lab

## Overview

This lab demonstrates how to:

1. Create a Kubernetes user called `developer`
2. Create a client certificate for the user
3. Configure `kubectl` for the user
4. Create a `ClusterRole`
5. Create a `ClusterRoleBinding`
6. Give the developer read-only access to Nodes
7. Test the permissions
8. Understand the difference between `Role`, `RoleBinding`, `ClusterRole`, and `ClusterRoleBinding`
9. Troubleshoot `Forbidden` errors
10. Clean up the lab

The final setup will look like:

```text
                       Kubernetes Cluster
                              |
                 +------------+------------+
                 |                         |
                 v                         v
             Administrator              developer
                 |                         |
                 |                         |
        Creates RBAC objects       Receives permissions
                 |                         |
                 v                         v
           ClusterRoleBinding        ClusterRole
                 |                         |
                 +------------+------------+
                              |
                              v
                           Nodes
                       get/list/watch
```

---

# 1. ClusterRole vs Role

A `Role` is **namespace-scoped**.

A `ClusterRole` is **cluster-scoped**.

```text
Role
 |
 +-- Namespace
       |
       +-- Pods
       +-- Services
       +-- Deployments
```

Whereas:

```text
ClusterRole
 |
 +-- Cluster
      |
      +-- Nodes
      +-- PersistentVolumes
      +-- StorageClasses
      +-- Other cluster resources
```

---

# 2. RoleBinding vs ClusterRoleBinding

A `RoleBinding` grants permissions within a namespace.

```text
Role
 |
 v
RoleBinding
 |
 v
User
 |
 v
Namespace
```

A `ClusterRoleBinding` grants the ClusterRole's permissions at the cluster level.

```text
ClusterRole
 |
 v
ClusterRoleBinding
 |
 v
User
 |
 v
Cluster
```

---

# 3. Important Rule

Remember:

```text
Role + RoleBinding
        =
Namespace-level permissions
```

and:

```text
ClusterRole + ClusterRoleBinding
        =
Cluster-level permissions
```

# 6. Create the Developer Private Key

Run:

```bash
openssl genrsa -out developer.key 2048
```

Check:

```bash
ls -l developer.key
```

You should have:

```text
developer.key
```

Keep the private key secure.

---

# 7. Create a Certificate Signing Request

Run:

```bash
openssl req -new \
  -key developer.key \
  -out developer.csr \
  -subj "/CN=developer/O=developers"
```

The important value is:

```text
CN=developer
```

Kubernetes will authenticate the user as:

```text
developer
```

The organisation is:

```text
developers
```

---

# 8. Find the Kubernetes CA

If your cluster was created using `kubeadm`, the CA is normally located at:

```text
/etc/kubernetes/pki/ca.crt
/etc/kubernetes/pki/ca.key
```

Check:

```bash
ls -l /etc/kubernetes/pki/ca.*
```

You should see:

```text
ca.crt
ca.key
```

> **Important:** `ca.key` is highly sensitive. Do not share or expose it.

If you are using Kind, Minikube, EKS, AKS, GKE, or another Kubernetes distribution, the certificate process can be different.

---

# 9. Sign the Developer Certificate

For a kubeadm cluster:

```bash
openssl x509 -req \
  -in developer.csr \
  -CA /etc/kubernetes/pki/ca.crt \
  -CAkey /etc/kubernetes/pki/ca.key \
  -CAcreateserial \
  -out developer.crt \
  -days 365
```

You should now have:

```text
developer.key
developer.csr
developer.crt
```

The files mean:

| File            | Purpose                      |
| --------------- | ---------------------------- |
| `developer.key` | Developer's private key      |
| `developer.csr` | Certificate Signing Request  |
| `developer.crt` | Signed developer certificate |

# 12. Create the ClusterRole

Now we create the actual `ClusterRole`.

Create:

```text
developer-clusterrole.yaml
```

Contents:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: developer-clusterrole

rules:
- apiGroups: [""]
  resources:
  - nodes
  verbs:
  - get
  - list
  - watch
```

This ClusterRole gives:

```text
get nodes
list nodes
watch nodes
```

It does NOT give:

```text
create nodes
delete nodes
update nodes
```

# 15. Create the ClusterRoleBinding

The ClusterRole defines:

```text
WHAT can be done?
```

Now the `ClusterRoleBinding` defines:

```text
WHO gets those permissions?
```

Create:

```text
developer-clusterrolebinding.yaml
```

Contents:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: developer-clusterrolebinding

subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io

roleRef:
  kind: ClusterRole
  name: developer-clusterrole
  apiGroup: rbac.authorization.k8s.io
```

The important section is:

```yaml
subjects:
- kind: User
  name: developer
```

This means:

```text
Give permissions to developer
```

And:

```yaml
roleRef:
  kind: ClusterRole
  name: developer-clusterrole
```

means:

```text
Use developer-clusterrole
```

# 27. Important: `--as` Does Not Authenticate You

This command:

```bash
kubectl auth can-i get nodes --as=developer
```

does not actually log you in as `developer`.

It asks Kubernetes:

> Would the user `developer` be allowed to perform this action?

Actual authentication is performed using the certificate configured here:

```bash
kubectl config set-credentials developer \
  --client-certificate=developer.crt \
  --client-key=developer.key
```

# 28. Why You Got the Forbidden Error

If you switch to:

```bash
developer-context
```

and run:

```bash
kubectl apply -f developer-clusterrole.yaml
```

you may get:

```text
Error from server (Forbidden):

User "developer" cannot get resource "clusterroles"
in API group "rbac.authorization.k8s.io"
at the cluster scope
```

This is expected.

Why?

Because `developer` has not been given permission to manage ClusterRoles.

The administrator should create the ClusterRole and ClusterRoleBinding.

The developer receives the permissions.

The relationship is:

```text
ADMIN
  |
  +-- creates ClusterRole
  |
  +-- creates ClusterRoleBinding
  |
  v
DEVELOPER
  |
  +-- receives permissions
  |
  +-- can get/list/watch Nodes
  |
  +-- cannot modify RBAC
```

# 31. Role vs ClusterRole

| Feature                             | Role      | ClusterRole |
| ----------------------------------- | --------- | ----------- |
| Scope                               | Namespace | Cluster     |
| Can define Pod permissions          | Yes       | Yes         |
| Can define Node permissions         | No        | Yes         |
| Can define PV permissions           | No        | Yes         |
| Can define StorageClass permissions | No        | Yes         |
| Used with RoleBinding               | Yes       | Yes         |
| Used with ClusterRoleBinding        | No        | Yes         |

---

# 32. RoleBinding vs ClusterRoleBinding

| Feature                   | RoleBinding                                | ClusterRoleBinding       |
| ------------------------- | ------------------------------------------ | ------------------------ |
| Scope                     | Namespace                                  | Cluster                  |
| Can reference Role        | Yes                                        | No                       |
| Can reference ClusterRole | Yes                                        | Yes                      |
| Typical use               | Namespace access                           | Cluster-wide access      |
| Example                   | Developer can access Pods in `development` | Developer can view Nodes |

# 33. Important Kubernetes Concept

A `ClusterRole` does not necessarily mean that the permissions are automatically cluster-wide.

For example:

```text
ClusterRole
     |
     v
RoleBinding
     |
     v
Namespace
```

A `ClusterRole` can be referenced by a `RoleBinding`.

In that case, its permissions are limited to the namespace of the RoleBinding.

But:

```text
ClusterRole
     |
     v
ClusterRoleBinding
     |
     v
Cluster
```

makes the permissions cluster-wide.

Therefore:

```text
ClusterRole + RoleBinding
        =
ClusterRole permissions limited to namespace
```

while:

```text
ClusterRole + ClusterRoleBinding
        =
ClusterRole permissions across cluster
```

# 39. Interview Cheat Sheet

### What is a ClusterRole?

A `ClusterRole` defines permissions that can apply to cluster-scoped resources or can be used to define permissions across namespaces.

### What is a ClusterRoleBinding?

A `ClusterRoleBinding` grants a `ClusterRole` to a user, group, or ServiceAccount at the cluster level.

### Can a ClusterRole access Nodes?

Yes.

```yaml
resources:
- nodes
```

### Can a normal Role access Nodes?

No. Nodes are cluster-scoped.

### What is the difference between Role and ClusterRole?

```text
Role
    = Namespace-scoped permissions

ClusterRole
    = Cluster-level permissions
```

### What is the difference between RoleBinding and ClusterRoleBinding?

```text
RoleBinding
    = Grants permissions within a namespace

ClusterRoleBinding
    = Grants permissions across the cluster
```

### Can a ClusterRole be used with a RoleBinding?

Yes.

```text
ClusterRole + RoleBinding
    =
Permissions restricted to the RoleBinding's namespace
```

### Can a ClusterRole be used with a ClusterRoleBinding?

Yes.

```text
ClusterRole + ClusterRoleBinding
    =
Cluster-wide permissions
```
