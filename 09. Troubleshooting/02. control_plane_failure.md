# Control Plane Failure — Troubleshooting

## Overview

When the Kubernetes control plane is unhealthy, `kubectl` commands may hang, time out, or return stale/incorrect data. Troubleshooting starts at the API server and works outward to the individual control plane components (`etcd`, `kube-apiserver`, `kube-controller-manager`, `kube-scheduler`).

---

## 1. Verify Cluster Status

```bash
k get componentstatus
```

Shows the health of core control plane components (`scheduler`, `controller-manager`, `etcd`).

> **Note:** `componentstatus` (`cs`) is deprecated in newer Kubernetes versions (removed as of 1.31/1.32 depending on distro) since it only checks static, hardcoded endpoints and doesn't reflect true HA cluster health. For current clusters, prefer checking each component directly via its own health endpoint or `systemctl status`, and use `kubectl get --raw='/healthz'` or `/livez` / `/readyz` on the API server.

```bash
# Modern equivalent
kubectl get --raw='/healthz?verbose'
kubectl get --raw='/livez?verbose'
kubectl get --raw='/readyz?verbose'
```

---

## 2. Verify and Dump Cluster Info

```bash
k cluster-info
```

Displays the addresses of the master (API server) and core cluster services (e.g., CoreDNS).

```bash
k cluster-info dump
```

Dumps a detailed snapshot of cluster state for debugging — Pod specs, logs, and events across all namespaces. Useful for capturing a full picture before/after a failure, or for sharing with support.

```bash
# Dump to a file/directory for later analysis instead of flooding the terminal
k cluster-info dump --output-directory=/tmp/cluster-dump
```

## 3. Check Logs of Individual Control Plane Components

### If running as static Pods (kubeadm-based clusters)

```bash
k get pods -n kube-system
k logs -n kube-system kube-apiserver-<node-name>
k logs -n kube-system kube-scheduler-<node-name>
k logs -n kube-system kube-controller-manager-<node-name>
k logs -n kube-system etcd-<node-name>
```

### If running as systemd services (manual/from-scratch setup)

```bash
# Check service status
systemctl status kube-apiserver
systemctl status kube-controller-manager
systemctl status kube-scheduler
systemctl status etcd

# View logs
journalctl -u kube-apiserver -l
journalctl -u kube-controller-manager -l
journalctl -u kube-scheduler -l
journalctl -u etcd -l

# Follow logs live while reproducing the issue
journalctl -u kube-apiserver -f
```

> Note: `journalctl -l api-server` in the notes should be `journalctl -u kube-apiserver -l` — `-u` specifies the systemd unit name, and the unit is typically named `kube-apiserver.service`, not `api-server`.

## General Diagnostic Flow

1. **Start with `kubectl` responsiveness** — if `kubectl` commands hang entirely, the API server is likely down or unreachable; check `systemctl status kube-apiserver` / static pod status first.
2. **Check etcd health** — the API server depends on etcd; if etcd is down, the API server will also report unhealthy.
   ```bash
   ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
     --cacert=/etc/etcd/ca.crt --cert=/etc/etcd/etcd.crt --key=/etc/etcd/etcd.key \
     endpoint health
   ```
3. **Check certificates** — expired or misconfigured certs are a common root cause of control plane component failures (kubelet ↔ API server, API server ↔ etcd, etc.).
   ```bash
   openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -enddate
   ```
4. **Check disk pressure / resource exhaustion** on control plane nodes — etcd is especially sensitive to disk I/O latency.
   ```bash
   df -h
   free -h
   ```
5. **Check node status** for the control plane node itself.
   ```bash
   k get nodes
   k describe node <control-plane-node>
   ```

## Quick Reference

| Check | Command |
|---|---|
| Component health (legacy) | `k get componentstatus` |
| API server health endpoints | `k get --raw='/healthz?verbose'` |
| Cluster info | `k cluster-info` |
| Full debug dump | `k cluster-info dump` |
| Static pod logs | `k logs -n kube-system <pod-name>` |
| systemd service status | `systemctl status <component>` |
| systemd logs | `journalctl -u <component> -l` |
| etcd health | `etcdctl endpoint health` |
| Certificate expiry | `openssl x509 -in <cert> -noout -enddate` |
