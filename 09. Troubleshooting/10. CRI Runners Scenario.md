# CKA Prep — Pod Scheduling Troubleshooting Scenario (CI/Build Runner Cluster)

## Scenario

You administer a Kubernetes cluster that runs ephemeral CI/build-runner pods for several engineering teams. Developers report that their pipeline jobs are stuck `Pending` for 10+ minutes before eventually running — sometimes they time out and fail entirely. Grafana shows the cluster's overall CPU and memory usage sitting comfortably under 50%, so the on-call engineer's first instinct — "just add more nodes" — doesn't obviously fit the evidence. You need to prove, not guess, why runner pods aren't scheduling despite apparent headroom.

**Question:** Walk through how you'd debug this scheduling problem across the cluster and nodes. What node conditions and taints would you check, how would you confirm whether kubelet health or node status reporting is broken, and how would you prove whether the scheduler is working off stale or incorrect node capacity data rather than genuinely lacking room?

## Answer

Start with the Pending pod itself — `kubectl describe pod` on a stuck runner shows the scheduler's exact rejection reason in its events, which is worth more than any dashboard. For a CI cluster specifically, the two likeliest causes are (a) build-runner pods requesting far more CPU/memory than they use on average, so `Allocated resources` on each node is near 100% even though actual usage is low, or (b) a dedicated `ci-runners` node pool with taints that only some pipeline configs tolerate, silently excluding runners from otherwise-idle general-purpose nodes. Confirm kubelet/node reporting isn't the culprit by checking `LastHeartbeatTime` and the `NodeLease` renewal time — if those are current, the scheduler is working off live data, and the problem is genuinely requests-vs-allocatable or taints/affinity, not stale node status.

## Explanation

The general troubleshooting sequence (describe pod → node conditions/taints → allocatable vs requests → kubelet/lease staleness → scheduler logs) is the same as any scheduling investigation, but a CI/build cluster has a specific failure signature worth calling out explicitly:

- **"Free CPU/memory" in Grafana is usage, not what the scheduler sees.** The scheduler binds pods against *requested* resources on each node's `allocatable`, not live utilization. CI runners are a classic case where teams set generous CPU/memory requests "to be safe" for build jobs that spike briefly and idle the rest of the time — so a node can show 20% actual usage while being 95% *requested*, and the scheduler correctly refuses to place another pod there.
- **Dedicated runner node pools are a common taint trap.** If `ci-runners` nodes are tainted (e.g., `dedicated=ci:NoSchedule`) so other workloads can't land there, but a subset of pipeline YAML is missing the matching toleration (perhaps after a recent template change), those runner pods will sit `Pending` forever while the tainted nodes look completely idle in monitoring — because nothing is running there at all.

### Step-by-step

1. Grab a currently `Pending` runner pod and read its scheduler events directly: `kubectl -n ci describe pod <pod>`.
2. Check node readiness and schedulability: `kubectl get nodes -o wide`, watching for `NotReady` or `SchedulingDisabled`.
3. List taints across all nodes and compare against the failing pod's `tolerations` — this catches the "missing toleration after a template change" case.
4. Check node conditions (`MemoryPressure`, `DiskPressure`, `PIDPressure`) and their timestamps.
5. Check placement constraints in the pipeline's pod spec: `nodeSelector`/`nodeAffinity` pinning runners to a specific pool that's genuinely full.
6. Compare requests to allocatable: `kubectl describe node` → `Allocated resources`. This is where the "low usage, high requests" CI pattern shows up directly as a percentage.
7. Prove node reporting isn't stale: check `LastHeartbeatTime` on the `Ready` condition and the `NodeLease` renew time in `kube-node-lease`. If these are current, the scheduler's view of the node is accurate and the bottleneck is real (requests or taints), not a reporting bug.
8. If kubelet reporting *is* stale, check kubelet health directly (`systemctl status kubelet`, `journalctl -u kubelet`) on the affected node.
9. Confirm in scheduler logs that it's filtering nodes for the reason you've found (e.g., `Insufficient cpu`, taint mismatch) — this is the final proof, not an assumption.
10. Fix based on evidence: right-size runner resource requests (or add a `LimitRange`/`ResourceQuota` per team), add the missing toleration, or genuinely scale the `ci-runners` pool if requests are legitimately maxed out.

### Code implementation

```bash
# 1) What is the scheduler saying about this Pending runner pod?
kubectl -n ci describe pod build-runner-8f2k1

# 2) Are nodes Ready and schedulable?
kubectl get nodes -o wide

# 3) Taints across all nodes (a dedicated ci-runners pool is the usual suspect)
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .spec.taints[*]}{.key}={.value}:{.effect}{" "}{end}{"\n"}{end}'

# 4) Node Ready condition + heartbeat (stale = kubelet reporting problem)
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\tReady="}{range .status.conditions[?(@.type=="Ready")]}{.status}{"\tHB="}{.lastHeartbeatTime}{end}{"\n"}{end}'

# 5) Allocatable vs what's already Allocated (this is what proves the "low usage, high requests" theory)
for n in $(kubectl get nodes -l pool=ci-runners -o name | cut -d/ -f2); do
  echo "NODE: $n"
  kubectl describe node "$n" | awk '
    /^Allocated resources:/ {flag=1}
    flag{print}
    flag && /^Events:/ {exit}
  '
done

# 6) NodeLease — confirms kubelet heartbeats are current, independent of the Node object
kubectl get lease -n kube-node-lease <node-name> -o yaml

# 7) Does the runner pod's toleration match the ci-runners taint?
kubectl get pod build-runner-8f2k1 -n ci -o jsonpath='{.spec.tolerations}' | jq .

# 8) Scheduler logs — final proof of which filter rejected the node
kubectl -n kube-system get pods | grep scheduler
kubectl -n kube-system logs <kube-scheduler-pod> --tail=200 | grep -i build-runner-8f2k1
```

### Explanation of code

- `describe pod` on the stuck runner is always the first move — its `FailedScheduling` event states the rejection reason verbatim (`Insufficient cpu`, `node(s) had untolerated taint {dedicated: ci}`, etc.), turning a guess into a fact.
- Filtering nodes with `-l pool=ci-runners` before checking `Allocated resources` targets the specific node pool the runners are meant to land on, rather than diluting the picture with general-purpose nodes that were never in scope.
- `Allocated resources` in `describe node` output is the number that actually explains "Grafana shows 50% usage but pods won't schedule" — it reports *requested*, not *used*, resources, which is exactly the mismatch a generous CI resource-request template creates.
- The `NodeLease` check is a second, independent signal from the `Ready` condition's heartbeat — both should agree; if the lease is current but `Ready` transitions are old, that's itself a symptom worth investigating (e.g., kubelet updating the lease but failing to PATCH node status).
- Extracting `.spec.tolerations` from the pod and comparing it to the node taint list directly answers the "did a recent pipeline template change drop a toleration" hypothesis without relying on visual inspection of YAML.
- Grepping scheduler logs for the specific pod name at the end confirms the scheduler actually filtered on the condition you found — closing the loop from "node looks tainted/full" to "scheduler explicitly rejected this pod for that reason."
