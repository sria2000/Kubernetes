# Draining Worker Nodes

## Overview

Worker nodes sometimes need to be taken offline for planned maintenance — reboots for OS patching, hardware replacement, or any change requiring the node to go down, whether for a quick reboot or a longer maintenance window.

Kubernetes provides a safe way to do this without disrupting workloads: **drain** the node before taking it down.

---

## Check Node Status

```bash
k get nodes -o wide
```

Example nodes:
```
node01
node02
```

Suppose `node02` needs to go down for maintenance.

---

## Step 1: Drain the Node

```bash
kubectl drain node02
```

This will:
- **Gracefully terminate** all Pods currently running on the node
- **Cordon** the node so no new Pods are scheduled onto it

### Verify

```bash
k get nodes
```

`node02` will show status:
```
Ready,SchedulingDisabled
```

Any new Pods will now be scheduled onto the remaining available node (`node01`).

---

## Handling DaemonSets and Local Data

By default, `drain` will refuse to proceed if there are Pods managed by a DaemonSet or Pods using local (emptyDir) storage, since evicting them isn't necessarily safe or reversible. To force through these cases:

```bash
k drain node02 --ignore-daemonsets --delete-local-data
```

- `--ignore-daemonsets` — skips DaemonSet-managed Pods (they're expected to run on every node and will be recreated automatically when the node returns)
- `--delete-local-data` — allows eviction of Pods using local/ephemeral storage, accepting that data will be lost

> **Note:** `--delete-local-data` is deprecated in newer `kubectl` versions in favor of `--delete-emptydir-data` — same behavior, updated flag name.

Once run, `kubectl drain` begins **evicting** the Pods from the node (respecting PodDisruptionBudgets where defined).

---

## Step 2: Perform Maintenance

With the node drained and cordoned, it's now safe to:
- Reboot the node for patching
- Replace or service hardware
- Perform any other maintenance requiring the node offline

---

## Step 3: Bring the Node Back

After maintenance is complete:

```bash
k uncordon node02
```

This marks the node as schedulable again — `node02` returns to `Ready` status and can receive new Pods.

---

## Quick Reference

| Command | Purpose |
|---|---|
| `k get nodes -o wide` | Check current node status |
| `kubectl drain <node>` | Cordon node + gracefully evict all Pods |
| `k drain <node> --ignore-daemonsets --delete-emptydir-data` | Force drain through DaemonSet Pods and local-storage Pods |
| `k cordon <node>` | Mark node unschedulable **without** evicting existing Pods |
| `k uncordon <node>` | Mark node schedulable again after maintenance |

## Drain vs Cordon

- **`cordon`** only prevents *new* Pods from being scheduled — existing Pods keep running untouched.
- **`drain`** cordons the node **and** evicts existing Pods gracefully, respecting `terminationGracePeriodSeconds` and any `PodDisruptionBudget` set on the workloads.

This distinction is a common interview point: cordon is non-disruptive prep work, drain is the disruptive maintenance step.
