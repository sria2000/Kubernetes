# Exercise: Persistent Volume and Deployment Recovery

## Pre-Requisite

```bash

```

## Requirement

1. A deployment named `mariadb` in the `mariadb` namespace was deleted by mistake by an intern. The deployment used a PV named `mariadb-retained-pv`, which still exists (its `Retain` reclaim policy preserved it).
2. Task: recreate the deployment with a **new PVC** that binds to the existing PV `mariadb-retained-pv`.
3. Success criteria: the MariaDB pod is `Running`, and `/var/lib/mysql/initial.txt` exists inside the pod (proving the original data on the retained volume survived).

A `mariadb-deployment.yaml` file is provided by the setup script and can be used to recreate the deployment.

## Step 3 — Remove the Stale Claim Reference from the PV

```bash
k get pv
```
```
NAME                  CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM             STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
mariadb-retained-pv   250Mi      RWO            Retain           Released   mariadb/mariadb   local-path     <unset>                          3m42s
```

The PV is still claimed (in spirit) by the deleted `mariadb/mariadb` PVC, so its stale `claimRef` needs to be cleared:

```bash
k edit pv mariadb-retained-pv
```

Remove this block:

```yaml
claimRef:
  apiVersion: v1
  kind: PersistentVolumeClaim
  name: mariadb
  namespace: mariadb
  resourceVersion: "2485466"
  uid: 251c8a23-a843-42ff-a536-4a0fa0e9851e
```

Confirm it's now `Available`:

```bash
k get pv
```

mariadb-retained-pv   250Mi      RWO            Retain           Available           local-path     <unset>                          5m22s

### Building the PVC — What Needs to Match

Starting from the example PVC on the Kubernetes docs page, adjust:

| Field | Value | Why |
|---|---|---|
| `metadata.name` | `mariadb` | Must match `claimName: mariadb` referenced in the deployment |
| `metadata.namespace` | `mariadb` | PV's stale claimRef and deployment both use this namespace |
| `accessModes` | `ReadWriteOnce` | Must match PV's `RWO` |
| `resources.requests.storage` | `250Mi` | Must be ≤ the PV's actual capacity (`250Mi`) |
| `storageClassName` | `local-path` | Must match the PV's storage class exactly |
| `volumeMode` | `Filesystem` | Must match the PV's volume mode |
| `volumeName` | `mariadb-retained-pv` | Explicitly targets this PV for static binding |

To confirm the correct field names/syntax:

```bash
k explain pvc.spec --recursive
```

### Final `pvc.yaml`

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mariadb
  namespace: mariadb
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Filesystem
  resources:
    requests:
      storage: 250Mi
  storageClassName: local-path
  volumeName: mariadb-retained-pv
```

> **Common mistake:** copying the storage class (`slow`) and size (`8Gi`) straight from the Kubernetes docs example without updating them. The `storageClassName` must match the PV's actual class (`local-path`), and the requested `storage` must be ≤ the PV's capacity (`250Mi`) — otherwise the PVC stays `Pending` and never binds.

Apply it:

```bash
k apply -f pvc.yaml
```
```
persistentvolumeclaim/mariadb created
```

## Key Takeaways

- A PV with `Reclaim Policy: Retain` survives PVC/deployment deletion, but its `claimRef` still points at the old (now-gone) PVC — status shows `Released`, not `Available`.
- To reuse a `Released` PV, clear its `claimRef` via `kubectl edit pv <name>` so it becomes `Available` again.
- A new PVC binding to a specific PV (static binding) must match the PV's `accessModes`, `storageClassName`, and `volumeMode`, and request storage ≤ the PV's capacity — plus set `volumeName` to target it explicitly.
- Data on the underlying storage is independent of the Kubernetes objects (PVC/Deployment) pointing at it — deleting and recreating those objects doesn't touch the actual files, as proven by `initial.txt` surviving.
