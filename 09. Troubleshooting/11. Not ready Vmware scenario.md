# CKA Prep — NotReady Node Troubleshooting Scenario (On-Prem VMware Cluster)

## Scenario

You administer a self-managed Kubernetes cluster running on VMware vSphere VMs, provisioned from a golden VM template and joined to the cluster via an Ansible playbook. After rolling a routine OS-patching upgrade through the node pool — new VMs cloned from an updated template, old ones drained and destroyed — half the newly joined nodes show `NotReady`, and pods scheduled onto them keep flapping between `Pending` and being evicted to other nodes. The VMware admins insist the VMs themselves are healthy: vCenter shows them powered on, pingable, with normal CPU/memory. Kubernetes disagrees.

**Question:** Walk through how you'd troubleshoot these NotReady nodes after a template-based upgrade. What kubelet signals would you check first, how would you confirm whether the container runtime is functioning inside these freshly cloned VMs, and how would you determine whether CNI initialization or certificate/bootstrap issues — both common fallout from cloning a VM template — are preventing the nodes from joining correctly?

## Answer

Start with `kubectl describe node` on an affected node to read its `Conditions` and recent `Events` — this immediately tells you whether it's a kubelet-can't-report-status problem, a runtime problem, or a `NetworkPluginNotReady` problem. Because these are VMs cloned from a template, the two prime suspects are: (1) the golden template baked in a kubelet bootstrap certificate or machine-ID that's now duplicated or stale across clones, causing the kubelet-to-API TLS handshake to fail silently, and (2) the Ansible join playbook running before the container runtime or CNI plugin files finished installing on the freshly booted clone, leaving `/etc/cni/net.d/` empty or `containerd` not fully started at join time. SSH into one affected node to confirm kubelet and containerd service status directly, since vCenter's "VM is healthy" view has no visibility into either.

## Explanation

The general NotReady flow (node Conditions/Events → CNI DaemonSet health → kubelet/runtime on the node → CNI config on disk → certs/CSRs) is unchanged, but VM-template cloning introduces two failure modes that a bare-metal or cloud-managed-node-pool upgrade wouldn't:

- **Cloned VMs can inherit identity, not just OS state.** If the golden template was ever booted and had `machine-id` (`/etc/machine-id`) or a kubelet client certificate generated before being converted back into a template, every clone shares that identity. The API server can then see multiple nodes claiming the same identity, or reject a stale/duplicate cert outright — a classic "looks fine in vCenter, fails silently in kubelet logs" scenario.
- **Ansible playbook timing matters more with cloned VMs than fresh installs.** A VM booted from a template can come up with services in a different readiness order than a freshly provisioned cloud instance — cloud-init/similar customization scripts (hostname, network, machine-id regeneration) may still be finishing when the join playbook's `kubeadm join` step fires. That produces exactly the "kubelet joined but CNI/runtime weren't ready yet" pattern.

### Step-by-step

1. Identify the pattern: `kubectl get nodes`, confirm which nodes are `NotReady` and that they correspond to the newly cloned VMs from this upgrade.
2. Read node Conditions and Events on an affected node — look specifically for `KubeletNotReady`, `NetworkPluginNotReady`, or certificate-related messages.
3. Check the CNI DaemonSet: is it scheduled and `Running` on the affected node, or stuck `Pending`/`CrashLoopBackOff` because the node itself isn't ready enough to host it yet?
4. SSH into the affected VM (via vCenter console if network is part of the problem) and check `kubelet` and `containerd` service status directly — don't trust vCenter's power/ping state as a proxy for either.
5. Check `/etc/machine-id` on two or more affected clones — if they're identical, the template was tainted before cloning and every VM needs a regenerated machine-id and a rejoin.
6. Check `/etc/cni/net.d/` and `/opt/cni/bin/` on the node — empty or missing means the Ansible playbook's CNI install step ran before the runtime/network stack was actually ready, or didn't run at all on this clone.
7. Check for duplicate or stuck CSRs: `kubectl get csr` — cloned nodes with baked-in stale kubelet certs sometimes show as approved-but-invalid, or generate a flood of pending CSRs as they keep retrying.
8. Fix the immediate incident: regenerate `machine-id`, clear stale kubelet certs, restart `containerd`/`kubelet` in the right order, and manually re-run the CNI install step if needed.
9. Fix the root cause: update the Ansible playbook to regenerate `machine-id` and clear any kubelet PKI state as an explicit early step post-clone, and add a readiness wait (containerd active, CNI binaries present) before the `kubeadm join` task runs.

### Code implementation

```bash
# 1) Identify affected nodes
kubectl get nodes -o wide
kubectl get nodes | grep NotReady

# 2) Node Conditions + Events — the first real diagnostic signal
NODE=<notready-node-name>
kubectl describe node "$NODE"

# 3) CNI DaemonSet status on the affected node
kubectl -n kube-system get pods -o wide | grep "$NODE"
kubectl -n kube-system logs <cni-pod-on-that-node> --tail=200

# --- On the affected VM itself (via SSH or vCenter console) ---

# 4) kubelet and containerd service state
sudo systemctl status kubelet --no-pager
sudo journalctl -u kubelet -n 200 --no-pager | grep -i -E 'certificate|NetworkPluginNotReady|failed'

sudo systemctl status containerd --no-pager
sudo crictl info

# 5) Machine identity check — the template-cloning smoking gun
cat /etc/machine-id
# Compare this value across two or more NotReady nodes; identical = tainted template

# 6) CNI install state on this clone
ls -l /etc/cni/net.d/
ls -l /opt/cni/bin/ | head

# 7) Fix: regenerate machine-id and clear stale kubelet PKI state, then rejoin
sudo systemctl stop kubelet
sudo rm -f /etc/machine-id /var/lib/dbus/machine-id
sudo systemd-machine-id-setup
sudo rm -rf /etc/kubernetes/pki/kubelet-client-*.pem /var/lib/kubelet/pki/*
sudo systemctl start containerd
sudo kubeadm join <control-plane-endpoint> --token <token> --discovery-token-ca-cert-hash <hash>

# --- Back on the control plane ---

# 8) Check for stuck/duplicate CSRs from repeated failed join attempts
kubectl get csr
kubectl describe csr <csr-name>
kubectl certificate approve <csr-name>

# 9) Confirm recovery
kubectl get nodes
kubectl get pods -A -o wide | grep "$NODE"
```

### Explanation of code

- `describe node` is still the starting point — `NetworkPluginNotReady` in the conditions points straight at CNI, while a node stuck without ever posting a `Ready`/`False` condition at all points at kubelet-to-API communication (often certs).
- Comparing `/etc/machine-id` across multiple affected nodes is the single most VM-template-specific check in this whole flow — a shared machine-id across clones is invisible to vCenter (each VM is a distinct object there) but can confuse both `kubelet`'s node identity and any DHCP/cloud-init logic that keys off it.
- Clearing `/var/lib/kubelet/pki/*` and the `kubelet-client-*.pem` certs before rejoining forces a fresh CSR, which resolves the case where the golden template baked in a certificate that every clone inherited — without this, `kubeadm join` can appear to succeed while the kubelet still fails its TLS bootstrap silently.
- Checking `/etc/cni/net.d/` and `/opt/cni/bin/` directly on the node (rather than trusting the CNI DaemonSet's `Running` status) matters because the DaemonSet pod can show `Running` while its per-node init container failed partway through writing config — the file check is ground truth.
- `kubectl get csr` after a fix attempt catches the case where several failed join attempts left multiple pending CSRs behind; approving the wrong one, or leaving duplicates, re-creates the same identity confusion you just fixed.
- The final recovery check greps pods scheduled to the node specifically, since a node flipping to `Ready` doesn't by itself confirm workloads have stopped flapping — that's the real signal the fix worked end-to-end.
