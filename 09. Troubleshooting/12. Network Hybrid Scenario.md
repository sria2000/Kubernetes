# CKA Prep — Cross-Node Networking Troubleshooting Scenario (Hybrid On-Prem/GCP Cluster)

## Scenario

You administer a single Kubernetes cluster that spans two locations: a set of on-prem nodes in the office data center and a set of GCE nodes in GCP, joined together over a site-to-site VPN tunnel so the cluster looks logically flat. The networking team reports that pods on the same node can talk to each other fine, and pods on two on-prem nodes can talk to each other fine — but pods on an on-prem node consistently fail to reach pods on a GCP node, and some Services intermittently fail depending on which node their backing pod landed on.

**Question:** Walk through how you'd troubleshoot this cross-node networking failure given the added wrinkle of a VPN-tunneled hybrid topology. How would you validate CNI health, test pod-to-pod routing across the on-prem/cloud boundary specifically, confirm whether kube-proxy's Service dataplane is affected, and determine whether the failure is isolated to the on-prem↔GCP path or is a broader cluster-wide problem?

## Answer

First prove the exact scope: same-node works, on-prem↔on-prem works, so the fault is specifically the on-prem↔GCP path — that already rules out a broadly broken CNI DaemonSet and points at the network segment between the two locations. Run a pod-to-pod test forcing one pod onto an on-prem node and one onto a GCP node (via `nodeSelector`, not just anti-affinity, so you control *which* boundary you're crossing) and test both direct pod-IP and Service ClusterIP reachability. Because the CNI overlay (VXLAN/GENEVE) has to encapsulate pod traffic and pass it through the VPN tunnel, the top suspect is an MTU mismatch — the tunnel's own encapsulation overhead reduces the effective MTU below what the CNI's overlay assumes, and larger packets get silently dropped rather than triggering an obvious error, which produces exactly this "small ping works, real traffic like HTTP intermittently fails" pattern.

## Explanation

The core methodology is identical to any cross-node CNI investigation, but a VPN-tunneled hybrid topology adds a layer most single-datacenter or single-cloud clusters never have to think about:

- **Double encapsulation eats into MTU twice.** The CNI already encapsulates pod traffic (VXLAN adds 50 bytes, GENEVE similar) to build its overlay. Push that through an IPsec or GCP Cloud VPN tunnel and you add another 50–100+ bytes of tunnel overhead on top. If the CNI's MTU setting was calculated only against the physical NIC's 1500-byte MTU and never adjusted for the tunnel, packets near that size get fragmented or dropped somewhere in the tunnel — small ICMP pings (well under the threshold) succeed while HTTP responses or larger payloads intermittently fail, which matches the "some Services intermittently fail" symptom exactly.
- **"Same node works, on-prem-to-on-prem works" is the whole diagnosis in miniature.** You don't need to re-validate the CNI DaemonSet's general health across the entire cluster — the passing on-prem↔on-prem test already proves the CNI agents and kube-proxy are functioning correctly on at least a subset of nodes. The investigation should be scoped immediately to the tunnel path rather than re-walked from scratch as if it were a generic cluster-wide CNI failure.
- **Firewall/security-group rules exist on both ends independently.** GCP firewall rules and any on-prem firewall/router ACLs both have to permit the CNI's specific encapsulation protocol and port (e.g., UDP 4789 for VXLAN) across the tunnel — a rule change on either side, not just the CNI config, can silently break this path while leaving everything else intact.

### Step-by-step

1. Confirm the scope precisely: same-node (works), on-prem↔on-prem (works), on-prem↔GCP (fails) — this is already most of the diagnosis.
2. Deploy test pods pinned explicitly to one on-prem node and one GCP node using `nodeSelector` (not just anti-affinity, since anti-affinity won't guarantee which specific boundary is crossed).
3. Test pod-IP-to-pod-IP with both small (`ping`) and larger payloads (`curl` a real response body, or `ping -s 1400`) — the size-dependent failure is the MTU tell.
4. Compare CNI overlay MTU settings on an on-prem node vs a GCP node: `ip link show <overlay-iface>` on both sides.
5. Check the VPN tunnel's own MTU/MSS clamping configuration on both the on-prem router/firewall and the GCP Cloud VPN gateway.
6. Check firewall rules on both ends for the CNI's specific encapsulation protocol/port between the on-prem and GCP CIDR ranges.
7. Validate the Service dataplane specifically for cross-boundary traffic: hit a ClusterIP whose only backing pod is on the "other side" from the client pod, and check kube-proxy rules/logs on both nodes.
8. Check `EndpointSlices` to rule out stale endpoints coincidentally correlating with the intermittent failures (rule this out so it doesn't get conflated with the MTU issue).
9. Fix: lower the CNI overlay MTU (or set MSS clamping on the tunnel) to account for the tunnel encapsulation overhead, correct any missing firewall rule, then re-run the same tests.

### Code implementation

```bash
# 1) Test namespace
kubectl create ns net-debug 2>/dev/null || true

# 2) Pin one pod to an on-prem node, one to a GCP node explicitly
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: server-onprem
  namespace: net-debug
  labels: { app: net-debug, role: server }
spec:
  nodeSelector:
    topology.kubernetes.io/region: onprem
  containers:
  - name: nginx
    image: nginx:1.25-alpine
    ports: [{ containerPort: 80 }]
---
apiVersion: v1
kind: Pod
metadata:
  name: client-gcp
  namespace: net-debug
  labels: { app: net-debug, role: client }
spec:
  nodeSelector:
    topology.kubernetes.io/region: europe-west2   # example GCP region label
  containers:
  - name: netshoot
    image: nicolaka/netshoot:latest
    command: ["sleep", "36000"]
EOF

kubectl -n net-debug expose pod server-onprem --name=server-svc --port=80 --target-port=80
kubectl -n net-debug wait --for=condition=Ready pod/server-onprem pod/client-gcp --timeout=180s
kubectl -n net-debug get pods -o wide   # confirm each landed on the intended side

SERVER_IP=$(kubectl -n net-debug get pod server-onprem -o jsonpath='{.status.podIP}')
SVC_IP=$(kubectl -n net-debug get svc server-svc -o jsonpath='{.spec.clusterIP}')

# 3) Size-dependent test — the MTU tell
kubectl -n net-debug exec client-gcp -- ping -c 3 "$SERVER_IP"                    # small, likely OK
kubectl -n net-debug exec client-gcp -- ping -c 3 -M do -s 1400 "$SERVER_IP"      # near-MTU, likely fails if MTU is the issue
kubectl -n net-debug exec client-gcp -- curl -sS --max-time 3 "http://$SERVER_IP" | head

# Service path across the boundary
kubectl -n net-debug exec client-gcp -- curl -sS --max-time 3 "http://$SVC_IP" | head
kubectl -n net-debug get endpoints server-svc -o wide

# 4) Compare overlay MTU on both sides
kubectl debug node/<onprem-node> -it --image=nicolaka/netshoot -- chroot /host ip link show
kubectl debug node/<gcp-node> -it --image=nicolaka/netshoot -- chroot /host ip link show
# Look at the CNI overlay interface (e.g., vxlan.calico, flannel.1, cilium_vxlan) MTU on each

# 5) CNI + kube-proxy presence across both node groups
kubectl -n kube-system get pods -o wide
kubectl -n kube-system get ds -o wide
kubectl -n kube-system logs -l k8s-app=kube-proxy --tail=50 2>/dev/null || true
```

### Explanation of code

- Using `nodeSelector` with region-style labels (rather than podAntiAffinity) is the key change from the generic version — anti-affinity only guarantees "different nodes," but this scenario needs pods pinned to specific *sides* of the tunnel to reliably reproduce the failure.
- The paired `ping` calls — one default-size, one `-M do -s 1400` (forcing don't-fragment at a size close to a typical overlay+tunnel MTU ceiling) — are what actually distinguishes an MTU problem from a routing or firewall problem: a routing/firewall block fails at any size, while an MTU problem passes small packets and fails or hangs on larger ones.
- Comparing `ip link show` overlay-interface MTU on an on-prem node against a GCP node directly exposes a mismatch if one side's CNI agent calculated MTU against a 1500-byte physical NIC while the other implicitly accounts for less headroom (or vice versa) — this is often the actual root cause, not a code bug but a config value that was never adjusted for the tunnel.
- Testing the Service ClusterIP from the GCP-side client to an on-prem-side pod specifically confirms whether kube-proxy's DNAT rules are correct on both nodes — if pod-IP-to-pod-IP works but the Service IP doesn't, that isolates the problem to the Service dataplane rather than the underlying tunnel/MTU path, which is an important branch to rule in or out separately.
- Checking `EndpointSlices` guards against a false lead: if the backing pod was recently rescheduled and the EndpointSlice is momentarily stale, that alone could look like an "intermittent Service failure" unrelated to the tunnel, and you don't want to chase an MTU fix for a problem that's actually just endpoint propagation lag.
