## 1. Priority Class

**References:**
- https://kubernetes.io/docs/reference/kubernetes-api/scheduling/priority-class-v1/
- https://kubernetes.io/docs/concepts/scheduling-eviction/pod-priority-preemption/

Higher-value `PriorityClass` = higher scheduling priority. When resources are scarce, the scheduler can **preempt** (evict) lower-priority pods to make room for higher-priority ones.

### Quick Creation via kubectl

```bash
kubectl create priorityclass high-priority --value=1000
kubectl create priorityclass low-priority --value=100
```

> Can be applied to a **new** pod at creation, or attached to an **existing** pod's spec via `priorityClassName` (note: this field is immutable once the pod is created — you'd need to recreate the pod to change it).

### YAML — Defining a PriorityClass

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
description: "This priority class should be used for XYZ service pods only."
```

### YAML — Assigning to a Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
  labels:
    env: test
spec:
  containers:
  - name: nginx
    image: nginx
    imagePullPolicy: IfNotPresent
  priorityClassName: high-priority
```

**CKA Tip:** Know that `value` can be any 32-bit integer ≤ 1 billion (values above 1 billion are reserved for system-critical pods), and that `globalDefault: true` makes a class apply to any pod without an explicit `priorityClassName`.

## 2. Horizontal Pod Autoscaler (HPA)

Automatically scales the number of pod replicas based on observed metrics (commonly CPU).

### Quick Creation via kubectl

```bash
kubectl autoscale deployment php-apache --cpu-percent=50 --min=1 --max=3
```

### Worked Example

```bash
k create deployment nginx-deploy --image=nginx
k autoscale deployment nginx-deploy --min=2 --max=10 --dry-run=client -o yaml
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-deploy
spec:
  maxReplicas: 10
  minReplicas: 2
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-deploy
status:
  currentMetrics: null
  desiredReplicas: 0
```

> **Important:** The HPA API version must be `autoscaling/v2` (not `v1`) for `behavior` fields like the stabilization window to work.

### Adding a Stabilization Window

Controls how quickly the HPA reacts to scale-down signals — prevents "flapping" by requiring the lower replica count to be sustained for a period before actually scaling down.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-deploy
spec:
  maxReplicas: 10
  minReplicas: 2
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-deploy
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
status:
  currentMetrics: null
  desiredReplicas: 0
```

**CKA Tip:** Default stabilization window for scale-down is 300s (5 min); scale-up has no default stabilization (reacts immediately) unless configured otherwise.

## 3. Helm

You should be comfortable with basic Helm commands.

| Helm Command | Description |
|---|---|
| `helm search <repo/hub> <keyword>` | Search for Helm charts across the Artifact Hub and any repositories you've added. |
| `helm repo add <name> <url>` | Adds a Helm chart repository (e.g. nginx). |
| `helm install <release> <chart>` | Installs a chart as a release into Kubernetes. |
| `helm uninstall <release>` | Uninstalls (deletes) a Helm release. |
| `helm list` | Lists all installed Helm releases. |
| `helm template <release> <chart>` | Renders Kubernetes manifests locally without installing — useful for previewing what a chart would create. |

## 4. Skipping CRDs (Helm)

Some charts (e.g. `argo-cd`) bundle CustomResourceDefinitions. You can skip installing them, or render templates without them, via:

- `--skip-crds` — skips CRDs during `helm install`/`upgrade`.
- `--set crds.install=false` — chart-specific value (only works if the chart supports this convention).

### Example

```bash
helm template my-argo-cd argo/argo-cd --set crds.install=false --version 7.8.23 > argo_no-cr.yaml
```

Verify no CRDs are present in the rendered output:

```bash
cat argo_no-cr.yaml | grep CustomResourceDefinition
```

**CKA Tip:** `--skip-crds` is a native Helm flag available on any chart; `--set crds.install=false` depends on the chart author having built that toggle in — check the chart's `values.yaml` first.

## 5. Ingress & TLS

- `Ingress` manages external HTTP/HTTPS access to services, with routing rules based on host/path.
- TLS termination is configured under `spec.tls`, referencing a `Secret` of type `kubernetes.io/tls` (created via `kubectl create secret tls <name> --cert=... --key=...`).
- TLS section requires: `hosts` (list of hostnames) and `secretName` (the TLS secret to use).

**CKA Tip:** Remember `type: tls` requires both `tls.crt` and `tls.key` keys in the Secret data.

---

## 6. Gateway API

- Newer, more expressive alternative/successor to Ingress for managing traffic routing.
- Also supports HTTPS termination — a Gateway resource specifies a `Secret` reference for TLS, similar in spirit to Ingress's `secretName`.
- Key resources: `GatewayClass`, `Gateway`, and route types (`HTTPRoute`, etc.).

**CKA Tip:** Understand this exists conceptually as Ingress's replacement direction — for the exam, Ingress is still the primary tested object, but be aware Gateway API questions can appear.

---

## 7. Ingress → Gateway API Migration

A conceptual migration path exists for moving Ingress resources to the newer Gateway API model (Gateway + HTTPRoute objects replacing Ingress + IngressClass). Know this exists as a topic even if hands-on practice wasn't done here.

## 8. Kubernetes Volumes

### Volume Types Covered
- **configMap** — mounts config data as files into a pod.
- **emptyDir** — ephemeral, tied to pod lifecycle; deleted when the pod is removed.
- **hostPath** — mounts a path from the node's filesystem directly into the pod.

### Ephemeral vs Persistent
- **Ephemeral volumes** (e.g. `emptyDir`) — exist only as long as the pod does.
- **Persistent Volumes (PV)** — outlive individual pods; backed by external or local storage, bound via a **PersistentVolumeClaim (PVC)**.

### Volumes vs VolumeMounts
- `volumes:` — defined at the **pod** spec level; declares what storage is available.
- `volumeMounts:` — defined at the **container** level; declares where in the container's filesystem that volume is mounted.

### Storage Classes & Dynamic Provisioning
- A `StorageClass` defines a provisioner (e.g. `rancher.io/local-path`) that dynamically creates PVs on-demand when a PVC requests one, rather than requiring a PV to be pre-created manually.

### Multiple PVs — Claim by Name
- When several PVs exist, a PVC can target a **specific** one using `spec.volumeName` — this is how you statically bind a PVC to a pre-existing PV rather than letting dynamic provisioning pick one.

### Immutable ConfigMap
- A ConfigMap can be marked `immutable: true` — prevents accidental updates, and improves performance since the kubelet no longer needs to watch it for changes. Once immutable, you must delete and recreate it (under a new name, if referenced by name) to make changes.

### Useful Command

```bash
k rollout restart deployment/nginx
```
Restarts all pods in a deployment (e.g. to pick up a ConfigMap/Secret change that isn't automatically detected).

### Services — Quick Recap
- **ClusterIP** — internal-only access within the cluster (default type).
- **NodePort** — exposes the service on a static port on every node's IP, accessible externally.

## 9. Requests & Limits

| Concept | Meaning |
|---|---|
| **Capacity** | Total CPU/memory available on the node. |
| **Allocatable** | Resources available for pods after subtracting what the system/node components reserve. |
| **Allocated** | How much of allocatable is currently claimed by pod requests/limits. |

**CKA Tip:** The scheduler only checks **requests** (not limits) against allocatable capacity when deciding if a pod fits on a node. Limits can exceed allocatable (overcommitment) since they only cap runtime usage, not scheduling eligibility.

## 10. Debugging Kubernetes Nodes with `crictl`

Useful when you need to inspect containers below the kubectl/pod abstraction — directly via the container runtime.

| Command | Description |
|---|---|
| `crictl pods` | List all pods. |
| `crictl ps -a` | List all containers. |
| `crictl logs <container-id>` | Get container logs. |
| `crictl exec -i -t <container-id> ls` | Execute a command in a running container. |

**CKA Tip:** `crictl` talks directly to the container runtime (via the CRI socket) — useful when the API server or kubelet itself is having issues and `kubectl` isn't a reliable diagnostic path.

## 11. Network Policies — CNI Plugins (Calico)

- `NetworkPolicy` resources require a CNI plugin that supports enforcement (e.g. **Calico**) — some CNIs (like flannel by default) don't enforce them at all.
- Install the **Tigera operator** to deploy Calico.
- When installing, make sure the pod CIDR used by Calico's custom resources matches the CIDR passed to `kubeadm init --pod-network-cidr=...` — a mismatch here is a common cause of networking breakage.

---

## 12. Container Runtime Interface (CRI)

- CRI is the API/plugin interface that lets the kubelet talk to different container runtimes (containerd, CRI-O, or Docker via the `cri-dockerd` shim).
- Since Docker doesn't natively implement CRI, `cri-dockerd` acts as a translation layer between the kubelet and the Docker Engine API.

## 13. sysctl Kernel Parameters — Permanent Modification

Runtime `sysctl` changes don't survive a reboot unless persisted to a config file.

```bash
cat <<EOF | sudo tee /etc/sysctl.d/99-kubernetes-cri.conf
net.bridge.bridge-nf-call-iptables  = 1
net.ipv4.ip_forward                 = 1
net.bridge.bridge-nf-call-ip6tables = 1
EOF
```

Apply and load:

```bash
sudo sysctl --system
```

**CKA Tip:** Files under `/etc/sysctl.d/*.conf` are loaded on boot and by `sysctl --system` — this is the correct way to make kernel parameter changes persistent, versus a one-off `sysctl -w` which resets on reboot.

## 14. Editing Resources (`edit` / `patch` / Immutable Fields)

| Approach | Use Case |
|---|---|
| `kubectl edit <resource> <name>` | Manual, interactive edit — opens in your default editor. |
| `kubectl patch <resource> <name> -p '<json>'` | Scripted/automated updates without opening an editor. |

### Working Around Immutable Fields

Some fields (e.g. certain Deployment selector fields, or a PVC's `volumeName`) can't be changed in place via `edit` or `patch`. The workaround pattern:

```bash
k get deployment test-deployment -o yaml > deployment.yaml
k delete deployment test-deployment
# modify deployment.yaml
k create -f deployment.yaml
```

Export → delete → edit YAML → recreate.

## 15. Multi-container Pods — Shared Volume Access

- Multiple containers within the **same pod** can share storage by mounting the same `volume` (e.g. an `emptyDir`) at different paths in each container.
- Common pattern: **sidecar container** — a secondary container that supports the main application container (e.g. shipping logs, syncing files, acting as a proxy) without being the primary workload itself.

## 16. JSONPath & `kubectl explain`

- **JSONPath** (`kubectl get ... -o jsonpath='...'`) — extracts specific fields from API output; supports `range`/`end` to iterate over lists.
- **`kubectl explain <resource>.<field> --recursive`** — the fastest way to look up the exact schema/field names for a resource when you don't remember the YAML syntax; invaluable for the exam since there's no autocomplete on remembered YAML structure.

---

## 17. Custom Resource Definitions (CRDs)

- A CRD extends the Kubernetes API with a new resource type (e.g. what tools like Calico or Argo CD install to define their own objects).
- Helm charts that bundle CRDs may need special handling (see Section 4 — skipping CRDs) since Helm's CRD lifecycle management is limited (CRDs installed by a chart aren't automatically removed on `helm uninstall`, for instance).

## Reference: Deployment & Service Commands

| Command | Description |
|---|---|
| `kubectl create deployment my-dep --image=nginx --replicas=3 --port=5701` | Create a deployment with 3 replicas, exposing container port 5701. |
| `kubectl create deployment my-dep --image=busybox --replicas=3 --port=80` | Create a deployment with 3 replicas, exposing container port 80. |
| `kubectl set image deployment/frontend www=image:v2` | Rolling update of the "www" container in the "frontend" deployment to a new image. |
| `kubectl rollout restart deployment/frontend` | Rolling restart of the "frontend" deployment. |
| `kubectl scale --replicas=3 deployment/foo` | Scale a deployment to 3 replicas. |
| `kubectl expose deployment hello-world --type=NodePort --name=example-service` | Create a NodePort service exposing a deployment. |
| `kubectl create service nodeport my-ns --tcp=5678:8080` | Create a NodePort service directly (without `expose`), mapping service port 5678 → container port 8080. |

> Note: watch for typos between exam prep notes and actual commands — e.g. `--port=5701` vs `--port=80` in different variants of the same example above; always check the actual `--port` value you intend to use rather than copying a description verbatim.

## Exam-Day Tips (General)

- Use `kubectl explain <resource> --recursive` liberally instead of trying to memorize every YAML field.
- For immutable-field edits, default to the **export → delete → edit → recreate** pattern rather than fighting `kubectl edit`.
- When something's broken, work top-down: `systemctl status` → `journalctl -u <component>` → static pod manifests in `/etc/kubernetes/manifests/` → cross-check ports/addresses between dependent components (e.g. kube-apiserver ↔ etcd) → `netstat -ntlp` to confirm what's actually listening.
- Remember HPA needs `autoscaling/v2` for `behavior` (stabilization windows) to work — `v1` silently won't support it.
- Set aside dedicated practice time for JSONPath and `kubectl explain` — they're disproportionately time-saving in a timed exam environment.
