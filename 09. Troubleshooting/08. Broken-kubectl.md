# Troubleshooting a Broken Kubernetes Cluster

A revision walkthrough of two real misconfiguration errors, how they were diagnosed, and how they were fixed.

## Important Cluster Troubleshooting Pointers (Reference Toolkit)

| Command | Description |
|---|---|
| `systemctl status <kubelet / kube-apiserver, etcd>` | Check the status of individual components of Kubernetes. |
| `journalctl -u kubelet, kube-apiserver, etcd` | Check logs to understand the issue |
| `/etc/kubernetes/manifests` | Path to static K8s component pods for kubeadm based environments. |
| `cd /var/log/containers` | Log directory for all important pods |

These four are the starting toolkit for almost any "cluster is misbehaving" situation: check component status, read the logs, inspect the static pod manifests (since control plane components in kubeadm clusters run as static pods), and check container logs.

## Issue 1 — kubectl Can't Reach the API Server (Wrong Port in kubeconfig)

### Symptom

```bash
k get pods
```

```
Unhandled error
dial tcp IP:5443: connect: Connection refused
```

`kubectl` is trying to connect to the API server on port **5443**, and being refused.

### Diagnosis

Check what port the API server is actually listening on, by looking at its static pod manifest:

```bash
cd /etc/kubernetes/manifests/
cat kube-apiserver.yaml
```

The manifest shows the API server is configured to listen on **6443** (the standard kube-apiserver port) — not 5443. So the client (kubectl) is pointed at the wrong port; the server itself is fine.

### Root Cause

The kubeconfig file (`~/.kube/config`) had an incorrect port (`5443`) in the cluster's `server:` URL, mismatched against the API server's actual listening port (`6443`).

### Fix

```bash
vi ~/.kube/config
```

Change the server URL's port from `5443` to `6443`.

```bash
k get pods
```

### Follow-up Checks Along the Way

Even after fixing the port, it's worth confirming the kubelet itself is healthy:

```bash
systemctl status kubelet
```

And checking container logs for anything else amiss:

```bash
cd /var/log/containers
grep kube-apiserver *
```

This second check is what surfaced **Issue 2** below.

## Issue 2 — API Server Can't Reach etcd (Port Mismatch Between Components)

### Symptom

While grepping the API server's logs (from the follow-up check above):

```bash
grep kube-apiserver *
```

Found repeated connection errors like:

```
dial tcp 127.0.0.1:2389: connect: connection refused
```

The API server is trying to reach etcd on **port 2389** and failing.

### Diagnosis

**Step 1 — Check what port the API server is *configured* to use for etcd:**

```bash
cat /etc/kubernetes/manifests/kube-apiserver.yaml
```

Confirms the `--etcd-servers` flag points at `2389`.

**Step 2 — Check what port is actually listening:**

```bash
netstat -ntlp
```

**Step 3 — Check what port etcd itself is actually configured/listening on:**

```bash
cat /etc/kubernetes/manifests/etcd.yaml
```

The etcd manifest shows its client port is the standard **2379**, not `2389` — confirming the mismatch.

### Root Cause

The kube-apiserver's static pod manifest had a typo in the `--etcd-servers` flag: `2389` instead of the correct etcd client port `2379`. The API server was pointed at a port etcd wasn't listening on.

### Fix

```bash
vi /etc/kubernetes/manifests/kube-apiserver.yaml
```

Change:
```
--etcd-servers=http://127.0.0.1:2389
```
to:
```
--etcd-servers=http://127.0.0.1:2379
```

Since this file lives in `/etc/kubernetes/manifests/`, the kubelet automatically detects the change and restarts the static kube-apiserver pod — no manual restart command needed.

```bash
k get pods
```

No errors — cluster is healthy again.

## Summary Table

| Issue | Symptom | Root Cause | Fix Location |
|---|---|---|---|
| 1 | `kubectl` connection refused on 5443 | kubeconfig pointed at wrong API server port | `~/.kube/config` |
| 2 | API server logs show connection refused on 2389 (to etcd) | `--etcd-servers` flag had wrong port | `/etc/kubernetes/manifests/kube-apiserver.yaml` |

## Key Revision Takeaways

1. **`Connection refused` on the client side (kubectl) is a *client config* problem** — check `~/.kube/config`'s server URL/port against what the API server is actually listening on (`/etc/kubernetes/manifests/kube-apiserver.yaml`).
2. **`Connection refused` inside a component's own logs (e.g. API server → etcd) is an *inter-component* problem** — one static pod's manifest is pointing at the wrong port/address for another component. Cross-check the two manifests against each other.
3. **Static pod manifests are the single source of truth** for control plane component config in kubeadm clusters — any mismatch between what one component expects and what another actually exposes shows up as a connection error in logs.
4. **Editing a file in `/etc/kubernetes/manifests/` auto-triggers a kubelet restart** of that static pod — no need to manually delete/recreate it.
5. **General debugging flow:** confirm symptom → check component status (`systemctl status`) → check logs (`journalctl` / `/var/log/containers`) → inspect the relevant manifest(s) → cross-verify actual listening ports (`netstat -ntlp`) → fix the mismatched config → re-verify.
