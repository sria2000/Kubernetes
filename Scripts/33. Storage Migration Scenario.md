# CKA Prep — Storage Migration Scenario (Elastic Stack / Monitoring Platform)

## Scenario

You're the Kubernetes administrator for an internal observability platform running Elasticsearch, Prometheus, and Grafana across dev, staging, and prod namespaces. The cluster was built two years ago before dynamic provisioning was standard practice, so every Elasticsearch data node and Prometheus instance is backed by a manually created PersistentVolume — inconsistent naming (`pv-es-01`, `es-data-vol2`, `prom-storage-a`), inconsistent capacity, and a mix of `Retain` and `Delete` reclaim policies nobody fully remembers the reasoning for. New PVCs regularly get stuck `Pending` because they can't find a matching static PV. Leadership wants to move to StorageClass-based dynamic provisioning without losing any indexed log/metric history during the switch.

**Question:** What migration plan would you implement to move Elasticsearch and Prometheus from static PVs to StorageClass-backed dynamic provisioning? How would you map each existing PV/PVC to a new dynamically provisioned claim, and what safeguards would you put in place — particularly around reclaim policy — to guarantee no data loss during cutover?

## Answer

Create CSI-backed StorageClasses per workload tier (fast SSD for Elasticsearch hot nodes, standard for Prometheus/Grafana), set a sane default, and require every new claim to go through `storageClassName` rather than a manually created PV. Before touching anything, patch every legacy PV's `reclaimPolicy` to `Retain` so an accidental PVC deletion can never destroy indexed data. For each StatefulSet (Elasticsearch data nodes, Prometheus), provision a new PVC on the new StorageClass, copy data across (snapshot/restore where the CSI driver supports it, otherwise a migrator pod with `rsync`), cut the workload over to the new claim, validate, and only decommission the old PV after sign-off.

## Explanation

The mechanics are the same as any legacy-to-dynamic migration, but two things make Elasticsearch/Prometheus specifically tricky:

- **Elasticsearch is a StatefulSet with per-pod PVCs.** Each data node (`es-data-0`, `es-data-1`, ...) has its own claim via `volumeClaimTemplates`, so the migration has to be done per-pod, not once for the whole app. Getting the ordinal-to-volume mapping wrong means a node comes up with the wrong shard data.
- **Both apps care about write consistency during copy.** Elasticsearch can tolerate a rolling migration (one data node at a time, letting shards rebalance), but Prometheus's TSDB is a single append-only stream per instance — copying it while Prometheus is actively scraping risks a corrupted or inconsistent block. The safest approach is a brief write-freeze (scale replicas to 0, or pause scraping) during the copy for Prometheus specifically.

### Step-by-step

1. Inventory every legacy PV/PVC: which workload owns it, capacity, `accessModes`, reclaim policy, and whether the workload (ES node vs Prometheus instance) can tolerate a short write pause.
2. Safeguard first: `kubectl patch pv <name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'` on every legacy PV, regardless of its current policy.
3. Create StorageClasses: `sc-es-fast` (SSD, for Elasticsearch hot-tier nodes) and `sc-standard` (for Prometheus/Grafana), both with `volumeBindingMode: WaitForFirstConsumer` to fix the topology-driven `Pending` issues.
4. For each Elasticsearch data node: create a new PVC on `sc-es-fast`, take the node out of the cluster (or let it drain), copy its data directory, bring it back pointing at the new claim, and let Elasticsearch's shard allocator confirm the node rejoins healthy before moving to the next node.
5. For Prometheus: scale to 0 (or pause the scrape target briefly), copy the TSDB directory to the new PVC, update the StatefulSet's claim reference, scale back up, and verify query continuity across the cutover point.
6. Validate: cluster health (`green`) for Elasticsearch, no gaps in Prometheus query results, correct disk metrics on the new volumes.
7. Decommission: delete old PVCs only after sign-off; leave the old (Retained) PVs alone until the underlying disks are explicitly cleaned up in a separate, deliberate step.
8. Codify the whole thing in Helm/GitOps so future clusters never create static PVs again.

### Code implementation

**Patch legacy PVs to `Retain` (safeguard against data loss)**
```bash
kubectl get pv

kubectl patch pv pv-es-01 -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
kubectl patch pv prom-storage-a -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
```

**StorageClasses per workload tier**
```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: sc-es-fast
provisioner: csi.example.com
parameters:
  type: ssd
reclaimPolicy: Retain
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: sc-standard
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: csi.example.com
parameters:
  type: standard
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
```

**New PVC for one Elasticsearch data node (repeat per ordinal)**
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: es-data-v2-0
  namespace: observability
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 200Gi
  storageClassName: sc-es-fast
```

**Migrator pod (mount old read-only, copy into new)**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: es-data-migrator-0
  namespace: observability
spec:
  restartPolicy: Never
  containers:
    - name: copy
      image: alpine:3.20
      command: ["/bin/sh", "-c"]
      args:
        - apk add --no-cache rsync && rsync -aHAX --numeric-ids /old/ /new/
      volumeMounts:
        - name: old
          mountPath: /old
          readOnly: true
        - name: new
          mountPath: /new
  volumes:
    - name: old
      persistentVolumeClaim:
        claimName: es-data-0
    - name: new
      persistentVolumeClaim:
        claimName: es-data-v2-0
```

**Cutover — update the StatefulSet's volumeClaimTemplate reference**
```yaml
# Elasticsearch StatefulSet spec (relevant excerpt)
volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: sc-es-fast
      resources:
        requests:
          storage: 200Gi
```

### Explanation of code

- `kubectl patch pv ... Retain` is the single most important safety step — it means even if the migration goes wrong and a PVC gets deleted, the underlying volume and its data are preserved for manual recovery.
- `sc-es-fast` uses `reclaimPolicy: Retain` even for the *new* dynamically provisioned volumes, because indexed log/metric data is exactly the kind of thing you don't want silently deleted when a PVC is removed — unlike ephemeral dev/staging storage, which can safely use `Delete`.
- `volumeBindingMode: WaitForFirstConsumer` on both classes fixes the root cause of most `Pending` PVCs in a multi-zone cluster: it delays provisioning until the pod is actually scheduled, so the volume lands in the same zone as the node.
- The migrator pod pattern (mount old read-only + new read-write, `rsync -aHAX`) preserves permissions, ACLs, and extended attributes — important for Elasticsearch's on-disk Lucene segment files, which are sensitive to metadata mismatches.
- For Prometheus specifically, the same migrator pattern applies, but it should only run while the StatefulSet is scaled to 0 — Prometheus's WAL isn't safe to copy while a live process is writing to it, unlike Elasticsearch which can tolerate one node cycling out of a healthy cluster.
- Repeating steps 4–5 per StatefulSet ordinal (`es-data-0`, `es-data-1`, ...) is what makes this different from a single-PVC app migration — each pod's claim has to be migrated and validated independently before moving to the next, so a bad copy on one node doesn't take down cluster quorum.
