# Kubernetes StorageClass & VolumeSnapshotClass Design

## Scenario

You are the Kubernetes administrator for a **healthcare SaaS platform** running in a managed **GKE cluster** with three environments:

* `dev`
* `staging`
* `prod`

The platform:

* Stores patient records in a **PostgreSQL StatefulSet**
* Processes lab-report uploads through a **batch pipeline**
* Requires production data to be recoverable through **snapshots**
* Requires production data to be retained even if a **PVC is accidentally deleted**
* Allows development and staging environments to be torn down freely

The application team wants to deploy everything through **Helm** and:

* Request the appropriate storage tier
* Dynamically provision persistent storage
* Take on-demand snapshots
* Avoid directly creating or modifying `StorageClass` or `VolumeSnapshotClass`

The reason is that both `StorageClass` and `VolumeSnapshotClass` are **cluster-scoped resources** and are restricted to Kubernetes administrators.

---

# 1. Recommended Architecture

The recommended design is:

```text
                    Kubernetes Administrator
                             |
             +---------------+---------------+
             |                               |
      StorageClasses                 VolumeSnapshotClasses
       Cluster-scoped                    Cluster-scoped
             |                               |
     +-------+-------+                 +-----+------+
     |       |       |                 |            |
 Standard   DB-SSD  Prod-Critical     Standard    Prod
     |       |       |                 |            |
     +-------+-------+                 +------------+
             |
       Developers reference
       classes by name
             |
     +-------+------------------+
     |                          |
    PVC                  VolumeSnapshot
 Namespace-scoped          Namespace-scoped
     |                          |
     v                          v
 Persistent Disk             GCP Snapshot
```

The important design principle is:

> **Administrators create and control the cluster-scoped classes; developers consume them through namespace-scoped PVC and VolumeSnapshot objects.**

This provides **self-service without granting cluster-admin access**.

---

# 2. Storage Tier Design

Storage should be based on **workload requirements**, rather than simply creating a class for every environment.

Recommended classes:

| StorageClass       | Disk Type     | Workload                        | Reclaim Policy |
| ------------------ | ------------- | ------------------------------- | -------------- |
| `sc-standard`      | `pd-balanced` | General workloads / lab uploads | `Delete`       |
| `sc-db-ssd`        | `pd-ssd`      | PostgreSQL dev/staging          | `Delete`       |
| `sc-prod-critical` | `pd-ssd`      | PostgreSQL production           | `Retain`       |

### Why not create:

```text
sc-dev
sc-staging
sc-prod
```

The environment itself is not the storage characteristic.

Instead, separate the concerns:

```text
Environment
    +
Workload
    +
Performance
    +
Compliance
```

For example:

```text
dev PostgreSQL       -> sc-db-ssd
staging PostgreSQL   -> sc-db-ssd
prod PostgreSQL      -> sc-prod-critical
lab upload pipeline  -> sc-standard
```

This makes the storage architecture easier to maintain and prevents unnecessary duplication.

---

# 3. GKE CSI Provisioner

For GKE Persistent Disk storage, use the GCE Persistent Disk CSI driver:

```yaml
provisioner: pd.csi.storage.gke.io
```

The CSI driver dynamically provisions Persistent Disks when a PVC requests one of the approved StorageClasses.

---

# 4. Standard StorageClass

This class is intended for general-purpose workloads such as the lab-report processing pipeline.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: sc-standard
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: pd.csi.storage.gke.io

parameters:
  type: pd-balanced

allowVolumeExpansion: true

reclaimPolicy: Delete

volumeBindingMode: WaitForFirstConsumer
```

### Important settings

#### `type: pd-balanced`

Provides a good balance between:

* Performance
* Cost
* General-purpose workloads

Suitable for:

```text
Lab-report uploads
Batch processing
Application data
General persistent workloads
```

#### `reclaimPolicy: Delete`

If the PVC is deleted:

```text
PVC deleted
   |
   v
PV deleted
   |
   v
GCP Persistent Disk deleted
```

This is appropriate for disposable environments and non-critical data.

---

# 5. PostgreSQL SSD StorageClass

PostgreSQL has different performance requirements from a batch upload pipeline.

Database workloads typically benefit from lower latency and higher I/O performance.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: sc-db-ssd

provisioner: pd.csi.storage.gke.io

parameters:
  type: pd-ssd

allowVolumeExpansion: true

reclaimPolicy: Delete

volumeBindingMode: WaitForFirstConsumer
```

This can be used for:

```text
PostgreSQL dev
PostgreSQL staging
Non-critical databases
```

---

# 6. Production Critical StorageClass

Production PostgreSQL contains patient records and therefore requires additional protection.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: sc-prod-critical

provisioner: pd.csi.storage.gke.io

parameters:
  type: pd-ssd

allowVolumeExpansion: true

reclaimPolicy: Retain

volumeBindingMode: WaitForFirstConsumer
```

The key difference is:

```yaml
reclaimPolicy: Retain
```

---

# 7. Why `Retain` Is Important

Consider this scenario:

```bash
kubectl delete pvc data-patient-db-0 -n prod
```

With:

```yaml
reclaimPolicy: Delete
```

the underlying Persistent Disk may also be deleted.

That could result in:

```text
PVC deleted
     |
     v
PV deleted
     |
     v
Persistent Disk deleted
     |
     v
Potential data loss
```

With:

```yaml
reclaimPolicy: Retain
```

the underlying volume is retained.

Conceptually:

```text
PVC deleted
     |
     v
PV released
     |
     v
Persistent Disk remains
     |
     v
Administrator can recover / investigate
```

This provides an additional safety mechanism for production patient data.

---

# 8. Why `WaitForFirstConsumer`?

All StorageClasses should use:

```yaml
volumeBindingMode: WaitForFirstConsumer
```

Instead of immediately provisioning a disk, Kubernetes waits until the consuming Pod is scheduled.

This allows Kubernetes to consider:

* Node location
* Zone
* Topology
* Pod scheduling requirements

before provisioning the Persistent Disk.

This is particularly important for zonal storage.

Example:

```text
Pod
 |
 | scheduling decision
 v
Node in Zone A
 |
 v
Persistent Disk provisioned in Zone A
```

Rather than:

```text
PVC created
 |
 v
Disk immediately provisioned
 |
 v
Wrong zone
 |
 v
Pod scheduling problem
```

---

# 9. Production VolumeSnapshotClass

The `VolumeSnapshotClass` controls how snapshots are created by the CSI driver.

It is **cluster-scoped** and therefore should be created by the Kubernetes administrator.

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass

metadata:
  name: vsc-prod-critical

driver: pd.csi.storage.gke.io

deletionPolicy: Retain
```

The important setting is:

```yaml
deletionPolicy: Retain
```

This means deleting the Kubernetes `VolumeSnapshot` object does not automatically delete the underlying snapshot.

---

# 10. StorageClass vs VolumeSnapshotClass

These two resources solve different problems.

| Resource            | Purpose                                        | Scope     |
| ------------------- | ---------------------------------------------- | --------- |
| StorageClass        | Defines how storage is dynamically provisioned | Cluster   |
| PVC                 | Requests persistent storage                    | Namespace |
| VolumeSnapshotClass | Defines how snapshots are created              | Cluster   |
| VolumeSnapshot      | Requests a snapshot                            | Namespace |

The relationship is:

```text
StorageClass
     |
     v
PVC
     |
     v
Persistent Volume
     |
     v
Persistent Disk
```

And:

```text
VolumeSnapshotClass
     |
     v
VolumeSnapshot
     |
     v
PVC
     |
     v
Cloud Snapshot
```

# 11. PostgreSQL StatefulSet

The PostgreSQL StatefulSet can reference the approved StorageClass.

```yaml
apiVersion: apps/v1
kind: StatefulSet

metadata:
  name: patient-db
  namespace: prod

spec:
  serviceName: patient-db
  replicas: 1

  volumeClaimTemplates:
    - metadata:
        name: data

      spec:
        accessModes:
          - ReadWriteOnce

        storageClassName: sc-prod-critical

        resources:
          requests:
            storage: 100Gi
```

When the StatefulSet creates its PVC, Kubernetes generates a name such as:

```text
data-patient-db-0
```

The flow becomes:

```text
StatefulSet
     |
     v
PVC: data-patient-db-0
     |
     | storageClassName:
     | sc-prod-critical
     v
StorageClass
     |
     v
GCE PD CSI Driver
     |
     v
100Gi pd-ssd
```

---

# 12. Developer-Created VolumeSnapshot

Developers do **not** need to create a `VolumeSnapshotClass`.

They only create a namespaced `VolumeSnapshot` that references the approved class.

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot

metadata:
  name: patient-db-snapshot-2026-08-08
  namespace: prod

spec:
  volumeSnapshotClassName: vsc-prod-critical

  source:
    persistentVolumeClaimName: data-patient-db-0
```

The developer therefore interacts only with:

```text
Namespace
   |
   +-- PVC
   |
   +-- VolumeSnapshot
   |
   +-- Pods
   |
   +-- StatefulSets
```

They do **not** need access to:

```text
StorageClass
VolumeSnapshotClass
```

---

# 13. Helm Integration

The application team can expose the approved storage configuration through Helm values.

Example:

```yaml
persistence:
  enabled: true
  size: 100Gi
  storageClassName: sc-prod-critical

snapshots:
  enabled: true
  volumeSnapshotClassName: vsc-prod-critical
```

The Helm chart can then generate the appropriate PVC and VolumeSnapshot resources.

For example:

```yaml
storageClassName: {{ .Values.persistence.storageClassName }}
```

and:

```yaml
volumeSnapshotClassName: {{ .Values.snapshots.volumeSnapshotClassName }}
```

The developers only select from **approved class names**.

---

# 14. Environment-Specific Helm Values

A clean approach is to keep the Helm chart generic and use different values files.

### Dev

```yaml
persistence:
  enabled: true
  size: 20Gi
  storageClassName: sc-db-ssd

snapshots:
  enabled: false
```

### Staging

```yaml
persistence:
  enabled: true
  size: 50Gi
  storageClassName: sc-db-ssd

snapshots:
  enabled: true
  volumeSnapshotClassName: vsc-prod-critical
```

### Production

```yaml
persistence:
  enabled: true
  size: 100Gi
  storageClassName: sc-prod-critical

snapshots:
  enabled: true
  volumeSnapshotClassName: vsc-prod-critical
```

This allows the same Helm chart to be deployed into all environments while the storage policy changes through values.

# 15. Developer Self-Service Model

The complete model is:

```text
                 CLUSTER ADMIN
                      |
       +--------------+--------------+
       |                             |
       v                             v
StorageClass                  VolumeSnapshotClass
       |                             |
       |                             |
       +--------------+--------------+
                      |
                      v
                 DEVELOPERS
                      |
          +-----------+-----------+
          |                       |
          v                       v
         PVC               VolumeSnapshot
          |                       |
          v                       v
   Persistent Disk             Snapshot
```

The administrator controls:

* Storage tiers
* Disk types
* Reclaim policies
* Snapshot deletion policies
* CSI driver
* Cluster-wide storage policy

Developers control:

* PVC creation
* Storage size
* Approved StorageClass selection
* VolumeSnapshot creation
* Helm deployment

# 16. RBAC Consideration

The developers do **not** need permission to create:

```text
StorageClass
VolumeSnapshotClass
```

Those remain administrator-controlled.

They only need appropriate namespace permissions such as:

```text
create
get
list
delete
```

for resources such as:

```text
persistentvolumeclaims
volumesnapshots
statefulsets
pods
```

Therefore, the security boundary remains intact.

---

# 17. Why This Design Works

The key Kubernetes concept is **indirection**.

Developers don't need to create infrastructure definitions themselves.

They simply say:

```yaml
storageClassName: sc-prod-critical
```

Kubernetes then uses the administrator-defined StorageClass.

Similarly:

```yaml
volumeSnapshotClassName: vsc-prod-critical
```

causes the CSI snapshot controller to use the administrator-defined snapshot policy.

Therefore:

```text
Admin defines policy
        |
        v
Developer references policy
        |
        v
Kubernetes provisions infrastructure
```

This is the foundation of Kubernetes self-service.

---

# 18. Important Compliance Distinction

There are two different retention controls.

### StorageClass

```yaml
reclaimPolicy: Retain
```

Protects the underlying **Persistent Disk** when the PVC is deleted.

### VolumeSnapshotClass

```yaml
deletionPolicy: Retain
```

Protects the underlying **snapshot** when the VolumeSnapshot object is deleted.

Therefore:

```text
                Production PVC
                     |
                     v
              Persistent Disk
                     |
          +----------+----------+
          |                     |
       Retain                 Snapshot
          |                     |
          |                     v
          |              VolumeSnapshot
          |                     |
          |                  Retain
          |                     |
          +---------------------+
```

Both controls are useful for production compliance.

# 19. Recommended Final Design

| Requirement                    | Design                       |
| ------------------------------ | ---------------------------- |
| General storage                | `sc-standard`                |
| PostgreSQL performance         | `sc-db-ssd`                  |
| Production patient data        | `sc-prod-critical`           |
| General disk                   | `pd-balanced`                |
| PostgreSQL disk                | `pd-ssd`                     |
| Production PVC protection      | `reclaimPolicy: Retain`      |
| Dev/staging cleanup            | `reclaimPolicy: Delete`      |
| Topology-aware provisioning    | `WaitForFirstConsumer`       |
| PVC expansion                  | `allowVolumeExpansion: true` |
| Production snapshots           | `vsc-prod-critical`          |
| Snapshot protection            | `deletionPolicy: Retain`     |
| Deployment mechanism           | Helm                         |
| Developer access               | Namespace-scoped resources   |
| StorageClass management        | Kubernetes administrators    |
| VolumeSnapshotClass management | Kubernetes administrators    |

# 20. Interview Answer

If asked this scenario in an interview, a concise answer would be:

> I would create cluster-admin-managed StorageClasses based on workload and compliance requirements rather than creating one class per environment. For example, I would use `pd-balanced` for general workloads, `pd-ssd` for PostgreSQL, and a dedicated production-critical class using `pd-ssd` with `reclaimPolicy: Retain` so that the underlying disk survives PVC deletion.
>
> I would use `WaitForFirstConsumer` for topology-aware provisioning and enable volume expansion. For snapshots, I would create an administrator-controlled `VolumeSnapshotClass` using the GKE PD CSI driver with `deletionPolicy: Retain`.
>
> Developers would never need permission to create or modify either cluster-scoped class. Instead, their Helm charts would reference approved StorageClasses through `storageClassName` and create namespace-scoped PVCs. For snapshots, they would create a namespace-scoped `VolumeSnapshot` referencing the approved `VolumeSnapshotClass` by name and the source PVC.
>
> This gives us self-service dynamic provisioning while keeping cluster-wide storage and compliance policies under administrator control. Production gets `Retain` for both persistent storage and snapshots, while dev and staging can use `Delete` and be torn down safely.

```text
StorageClass
    ↓
Dynamic provisioning

PVC
    ↓
Storage request

PersistentVolume
    ↓
Actual Kubernetes storage

VolumeSnapshotClass
    ↓
Snapshot policy

VolumeSnapshot
    ↓
Snapshot request

reclaimPolicy: Retain
    ↓
Protect underlying volume

deletionPolicy: Retain
    ↓
Protect underlying snapshot

WaitForFirstConsumer
    ↓
Topology-aware provisioning

Helm
    ↓
Self-service application deployment
```

> **Core principle:** Cluster-scoped storage policies are administrator-owned, while namespace-scoped PVCs and VolumeSnapshots provide the developer self-service interface.
