# Kubernetes Sidecar Container Example (Log Collection with Fluentd)

## Objective

Learn how a **Sidecar Container** works by:

- Running an application container
- Generating log files
- Sharing logs using a shared volume
- Collecting logs using a Fluentd sidecar
- Verifying both containers share the same storage

---

# What is a Sidecar Container?

A **Sidecar Container** is a helper container that runs alongside the main application container inside the same Pod.

Both containers:

- Run together
- Share the same network
- Share the same storage (Volumes)
- Have separate processes

The sidecar adds additional functionality without modifying the application.

Typical use cases include:

- Log collection
- Monitoring
- Proxy
- Configuration reload
- Security

---

# Architecture

```
                Kubernetes Pod
+------------------------------------------------+

        Main Container (BusyBox)
                │
                │ Writes Logs
                ▼

        /var/log/1.log
        /var/log/2.log

                ▲
                │
        Shared Volume (emptyDir)
                │
                ▼

        Sidecar Container (Fluentd)
                │
                │ Reads Logs
                ▼

      Processes Log Files

+------------------------------------------------+
```

# YAML Manifest

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: fluentd-config
data:
  fluentd.conf: |
    <source>
      type tail
      format none
      path /var/log/1.log
      pos_file /var/log/1.log.pos
      tag PHP
    </source>
    <source>
      type tail
      format none
      path /var/log/2.log
      pos_file /var/log/2.log.pos
      tag JAVA
    </source>
    <match **>
       @type file
       path /var/log/fluent/access
    </match>

---
apiVersion: v1
kind: Pod
metadata:
  name: counter
spec:
  containers:
  - name: count
    image: busybox
    args:
    - /bin/sh
    - -c
    - >
      i=0;
      while true;
      do
        echo "$i: $(date)" >> /var/log/1.log;
        echo "$(date) INFO $i" >> /var/log/2.log;
        i=$((i+1));
        sleep 1;
      done
    volumeMounts:
    - name: varlog
      mountPath: /var/log

  - name: count-agent
    image: k8s.gcr.io/fluentd-gcp:1.30
    env:
    - name: FLUENTD_ARGS
      value: -c /etc/fluentd-config/fluentd.conf
    volumeMounts:
    - name: varlog
      mountPath: /var/log
    - name: config-volume
      mountPath: /etc/fluentd-config

  volumes:
  - name: varlog
    emptyDir: {}

  - name: config-volume
    configMap:
      name: fluentd-config
```

```bash
kubectl apply -f sidecar.yaml
```

# Test 1 - Verify the Application Generates Logs

Open a shell inside the **count** container.

```bash
kubectl exec -it counter -c count -- sh
```

List the log files.

```bash
ls -l /var/log
```

Output

```text
1.log
2.log
```

View the first log file.

```bash
tail -5 /var/log/1.log
```

Example

```text
15: Tue Jul 28 10:21:01 UTC
16: Tue Jul 28 10:21:02 UTC
17: Tue Jul 28 10:21:03 UTC
```

View the second log.

```bash
tail -5 /var/log/2.log
```

Example

```text
Tue Jul 28 INFO 15
Tue Jul 28 INFO 16
Tue Jul 28 INFO 17
```

Exit the container.

```bash
exit
```

This confirms that the application is continuously generating logs.

---

# Test 2 - Verify the Sidecar Can Read the Same Files

Open a shell inside the Fluentd sidecar.

```bash
kubectl exec -it counter -c count-agent -- sh
```

List the log directory.

```bash
ls -l /var/log
```

Example

```text
1.log
2.log
1.log.pos
2.log.pos
fluent
```

Notice the `.pos` files.

These files are created by Fluentd to remember the last position read in each log file.

View the application log.

```bash
tail -5 /var/log/1.log
```

You will see exactly the same data generated by the **count** container.

This proves both containers are sharing the same volume.

# Test 3 - Verify the ConfigMap

Display the Fluentd configuration.

```bash
cat /etc/fluentd-config/fluentd.conf
```

You should see the same configuration defined in the ConfigMap.

# Test 4 - View the Fluentd Output Directory

List the Fluentd output directory.

```bash
ls -R /var/log/fluent
```

Find the generated output files.

```bash
find /var/log/fluent -type f
```

Depending on the Fluentd version, files similar to the following are created.

```text
access.log
access.xxxxxxxxx.log
```

Display the output.

```bash
cat /var/log/fluent/access*
```

# Test 5 - Watch the Logs Grow

Open another terminal and enter the application container.

```bash
kubectl exec -it counter -c count -- sh
```

Watch the log file.

```bash
tail -f /var/log/1.log
```

Every second a new line appears.

Example

```text
25: Tue Jul 28 10:25:01 UTC
26: Tue Jul 28 10:25:02 UTC
27: Tue Jul 28 10:25:03 UTC
```

Press **Ctrl+C** to stop.

# Test 6 - View the Sidecar Logs

Exit the container and run

```bash
kubectl logs counter -c count-agent
```

This displays the Fluentd container logs.

# How It Works

```
                ConfigMap
           fluentd.conf
                 │
                 ▼

         Fluentd Sidecar
                 ▲
                 │
         Reads Log Files
                 │
                 ▼

        Shared Volume
          /var/log

        ▲          ▲
        │          │

     1.log      2.log

        ▲
        │

 BusyBox Application

Writes logs every second
```

---

# Key Points

- A Sidecar Container runs alongside the main application.
- Both containers share the same Pod, network, and volumes.
- The BusyBox container continuously writes log files.
- The Fluentd sidecar reads those log files from the shared `emptyDir` volume.
- The Fluentd configuration is provided through a ConfigMap.
- The application is not aware of Fluentd; it simply writes logs, while the sidecar handles log collection independently.
