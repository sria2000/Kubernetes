# Kubernetes ClusterIP Service

## What is a ClusterIP Service?

A **ClusterIP** Service is the default Service type in Kubernetes.

It provides a **stable internal IP address** that allows Pods within the Kubernetes cluster to communicate with an application.

> A ClusterIP Service is accessible **only from inside the Kubernetes cluster**.

---

# Key Features

- Provides a **stable virtual IP address**.
- Used for **internal communication** between applications.
- Accessible **only within the Kubernetes cluster**.
- Load balances traffic across multiple backend Pods.
- Default Service type in Kubernetes.
- Does **not** expose applications to the Internet.

---

# Why Do We Need a ClusterIP?

Pods are **ephemeral**.

Whenever a Pod is recreated:

- It receives a new IP address.
- Applications using the old Pod IP will fail.

Instead of connecting directly to Pods, applications communicate with the Service.

```
Frontend Pod
      |
      |
ClusterIP Service
      |
---------------------
|         |         |
Pod A    Pod B    Pod C
```

The Service provides one stable IP while Kubernetes automatically forwards requests to healthy Pods.

---

# Default Service Type

If no Service type is specified, Kubernetes automatically creates a **ClusterIP** Service.

For example:

```yaml
spec:
  ports:
    - port: 80
      targetPort: 80
```

is equivalent to:

```yaml
spec:
  type: ClusterIP

  ports:
    - port: 80
      targetPort: 80
```

---

# Service Manifest

**service.yaml**

```yaml
apiVersion: v1
kind: Service

metadata:
  name: simple-service

spec:
  ports:
    - port: 80
      targetPort: 80
```

Create the Service.

```bash
kubectl create -f service.yaml
```

Verify.

```bash
kubectl get service
```

Example:

```
NAME             TYPE        CLUSTER-IP

simple-service   ClusterIP   10.108.62.155
```

Notice that Kubernetes automatically assigned the Service type as **ClusterIP**.

---

# Creating a ClusterIP Service Using CLI

Display the available options.

```bash
kubectl create service --help
```

View ClusterIP-specific help.

```bash
kubectl create service clusterip --help
```

Create a ClusterIP Service.

```bash
kubectl create service clusterip test-service --tcp=80:80
```

Verify.

```bash
kubectl get service
```

Example:

```
NAME             TYPE        CLUSTER-IP

simple-service   ClusterIP   10.108.62.155

test-service     ClusterIP   10.107.199.113
```

---

# Generate YAML Using Dry Run

Instead of creating the Service immediately, generate the YAML.

```bash
kubectl create service clusterip test-service \
    --tcp=80:80 \
    --dry-run=client \
    -o yaml
```

Output:

```yaml
apiVersion: v1
kind: Service

metadata:
  labels:
    app: test-service
  name: test-service

spec:
  selector:
    app: test-service

  ports:
    - name: 80-80
      port: 80
      protocol: TCP
      targetPort: 80

  type: ClusterIP

status:
  loadBalancer: {}
```

This is a useful way to generate YAML manifests without manually writing them.

---

# ClusterIP is a Virtual IP

The ClusterIP assigned to a Service is **not the IP address of a Pod**.

Instead, it is a **virtual IP (VIP)** managed by Kubernetes.

Example:

```
Service IP

10.107.199.113
```

Backend Pods:

```
192.168.1.170

192.168.1.253
```

Applications communicate with the Service IP.

Kubernetes forwards the request to one of the backend Pods.

```
Frontend Pod
      |
10.107.199.113
      |
ClusterIP Service
      |
---------------------
|                   |
Pod 1            Pod 2
```

---

# Stable IP Address

A Pod IP changes whenever the Pod is recreated.

Example:

```
Old Pod

192.168.1.170
```

After recreation:

```
New Pod

192.168.1.200
```

However, the Service IP remains unchanged.

```
ClusterIP

10.107.199.113
```

This stable IP allows applications to communicate reliably even when Pods are replaced.

---

# Service Discovery

Every ClusterIP Service also receives a DNS name.

Instead of using the IP address:

```bash
curl 10.107.199.113
```

Applications can use:

```bash
curl test-service
```

Kubernetes DNS resolves the Service name to its ClusterIP automatically.

---

# ClusterIP vs Pod IP

| Pod IP | ClusterIP |
|---------|-----------|
| Assigned to a Pod | Assigned to a Service |
| Changes when the Pod is recreated | Remains stable while the Service exists |
| Represents a single Pod | Represents one or more Pods |
| Not recommended for application communication | Recommended for application communication |

---

# Traffic Flow

```
Frontend Pod
      |
      |
ClusterIP
10.107.199.113
      |
      |
Service
      |
--------------------
|                  |
Backend Pod 1   Backend Pod 2
```

Kubernetes automatically load balances requests across all healthy Pods.

# Interview Questions

### What is a ClusterIP Service?

A ClusterIP Service exposes an application using a stable internal IP address that is accessible only within the Kubernetes cluster.

---

### Is ClusterIP the default Service type?

Yes.

If no Service type is specified, Kubernetes creates a ClusterIP Service by default.

---

### Can ClusterIP be accessed from the Internet?

No.

ClusterIP is available only inside the Kubernetes cluster.

---

### Why is ClusterIP needed?

Because Pod IP addresses change whenever Pods are recreated. A ClusterIP provides a stable endpoint that applications can always use.

---

### Does ClusterIP perform load balancing?

Yes.

It distributes incoming traffic across all matching backend Pods.

---

# Key Takeaways

- ClusterIP is the **default Service type**.
- It provides a **stable internal virtual IP**.
- It is accessible **only within the Kubernetes cluster**.
- The ClusterIP remains unchanged as long as the Service exists.
- Kubernetes automatically load balances traffic across backend Pods.
- Applications should communicate with the **Service** instead of directly using Pod IP addresses.
- Every ClusterIP Service also receives a DNS name for easy service discovery.
