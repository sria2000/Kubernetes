# Kubernetes LoadBalancer Service

Documentation Referenced:

https://kubernetes.io/docs/concepts/services-networking/

---

# What is a LoadBalancer Service?

A **LoadBalancer** Service exposes an application to external users through an **external load balancer**.

Instead of users connecting directly to a **worker node** and its **NodePort**, they connect to the external load balancer.

The load balancer then forwards traffic to one of the Kubernetes worker nodes using the automatically created NodePort service, and Kubernetes routes the request to the appropriate Pod.

```
External User
      │
      ▼
External Load Balancer
      │
      ▼
NodePort Service (Created Automatically)
      │
      ▼
Worker Node
      │
      ▼
Pod
```

---

# Why do we need a LoadBalancer?

## Problem with NodePort

With a **NodePort** service, users must know:

- The IP address of one of the worker nodes
- The NodePort number

For example:

```
http://192.168.1.101:32542
```

This has several drawbacks:

- Users need to know the worker node IP.
- If the worker node changes, clients must update the IP.
- It is not user friendly.
- Traffic is not managed by an external load balancer.

---

# How LoadBalancer solves this

A **LoadBalancer** Service automatically creates a **NodePort** service behind the scenes.

The external load balancer then forwards traffic to these NodePorts.

```
Internet Users
        │
        ▼
External Load Balancer
        │
        ▼
Worker Node : NodePort
        │
        ▼
Pods
```

Users only access the external load balancer.

They no longer need to know:

- Worker node IP
- NodePort number

---

# Important Note

A Kubernetes **LoadBalancer** Service works only on supported cloud providers such as:

- AWS
- Azure
- Google Cloud
- Oracle Cloud
- DigitalOcean

These cloud providers automatically provision an external load balancer.

For **on-premises clusters** (or custom Kubernetes installations), additional software is required, such as:

- MetalLB
- F5 BIG-IP
- HAProxy
- NGINX Load Balancer

Without one of these solutions, the **EXTERNAL-IP** usually remains **Pending**.

# LoadBalancer Service YAML

```yaml
apiVersion: v1
kind: Service

metadata:
  name: simple-service

spec:
  selector:
    app: backend

  type: LoadBalancer

  ports:
  - port: 80
    targetPort: 80
```

---

# Explanation

| Field | Description |
|--------|-------------|
| type: LoadBalancer | Creates an external load balancer |
| selector | Finds matching Pods |
| port | Port exposed externally |
| targetPort | Container port receiving traffic |

---

# Create the Service

```bash
kubectl create -f lb-service.yaml
```

---

# Verify the Service

```bash
kubectl get service
```

Example:

```text
NAME             TYPE           CLUSTER-IP      EXTERNAL-IP   PORT(S)
kubernetes       ClusterIP      10.96.0.1       <none>        443/TCP
simple-service   LoadBalancer   10.111.186.17   <pending>     80:32542/TCP
```

Notice:

- Service Type = LoadBalancer
- Kubernetes automatically created a **NodePort (32542)**.
- The External IP is **Pending** because Killercoda is not running on a cloud provider.

---

# View Service Details

```bash
kubectl describe service simple-service
```

Example:

```text
Name:                     simple-service
Namespace:                default
Selector:                 app=backend
Type:                     LoadBalancer
IP:                       10.111.186.17
Port:                     80/TCP
TargetPort:               80/TCP
NodePort:                 32542/TCP
External Traffic Policy:  Cluster
```

Notice that Kubernetes automatically assigned a **NodePort**.

This proves that a **LoadBalancer Service internally creates a NodePort Service**.

# Create a Backend Pod

```bash
kubectl run backend-pod --image=nginx
```

Add the label expected by the Service.

```bash
kubectl label pod backend-pod app=backend
```

Verify:

```bash
kubectl get pods --show-labels
```

Example:

```text
NAME          READY   STATUS    LABELS
backend-pod   1/1     Running   app=backend
```

# Test the Service

Normally, on a cloud platform, you would access:

```
http://<External-IP>
```

Since Killercoda does not provide an external load balancer, use the ClusterIP for testing.


Example output:


This confirms that the Service successfully forwarded traffic to the backend Pod.

```
   │
   ▼
Kube Proxy
   │
   ▼

```

# Difference Between NodePort and LoadBalancer

| Feature | NodePort | LoadBalancer |
|----------|----------|--------------|
| Accessible from outside cluster | Yes | Yes |
| Requires Worker Node IP | Yes | No |
| Requires NodePort | Yes | No (handled automatically) |
| Creates NodePort | N/A | Yes |
| External Load Balancer | No | Yes |
| Best for | Labs, Testing | Production |

# Key Points to Remember

- A **LoadBalancer Service** exposes applications externally.
- Kubernetes automatically creates a **NodePort** for every LoadBalancer Service.
- Users connect to the external load balancer instead of worker nodes.
- The load balancer forwards traffic to the NodePort.
- Kubernetes then routes traffic to the correct Pod.
- On cloud platforms, an external IP is automatically assigned.
- On on-premises Kubernetes clusters, additional software such as **MetalLB** is required to provide external load balancing.
