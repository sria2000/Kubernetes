# Kubernetes Vertical Pod Autoscaler (VPA)

## Overview

Applications do not always consume the same amount of CPU and Memory.

- If **CPU/Memory requests are too low**, the application may become slow, get throttled, or even crash due to Out of Memory (OOM).
- If **CPU/Memory requests are too high**, cluster resources are wasted because Kubernetes reserves those resources even when the application is idle.

> Even if your application is idle and using very little CPU or memory, the requested resources are reserved and cannot be used by other Pods.

The **Vertical Pod Autoscaler (VPA)** automatically adjusts the **CPU and Memory requests** for containers running in your Pods based on their actual resource usage.

Unlike the **Horizontal Pod Autoscaler (HPA)**, which changes the **number of Pods**, the **VPA changes the CPU and Memory allocated to existing Pods**.

# VPA Architecture

```
                 Resource Usage
                       │
                       ▼
            +----------------------+
            |      Metrics Server  |
            +----------+-----------+
                       │
                       ▼
            +----------------------+
            |     VPA Recommender  |
            +----------+-----------+
                       │
        Calculates CPU & Memory Requests
                       │
                       ▼
            +----------------------+
            |      VPA Updater     |
            +----------+-----------+
                       │
          Evicts Pods (Auto Mode)
                       │
                       ▼
            +----------------------+
            |      Deployment      |
            +----------+-----------+
                       │
            New Pods start with
          updated CPU/Memory requests
```

---

# VPA Components

| Component | Purpose |
|-----------|---------|
| Recommender | Monitors resource usage and calculates recommended CPU & Memory requests |
| Updater | Evicts Pods when recommendations should be applied |
| Admission Controller | Applies recommended CPU and Memory values when new Pods are created |

---

# VPA Update Modes

| Update Mode | Description |
|-------------|-------------|
| **Off** | VPA only provides recommendations. No changes are made. |
| **Initial** | Recommendations are applied only when Pods are created. Existing Pods are never modified. |
| **Auto** | VPA automatically evicts Pods and recreates them with the recommended resources. |

# Install Vertical Pod Autoscaler

Clone the Kubernetes Autoscaler repository:

```bash
git clone https://github.com/kubernetes/autoscaler.git
```

Change to the VPA directory:

```bash
cd autoscaler/vertical-pod-autoscaler/
```

Install VPA:

```bash
./hack/vpa-up.sh
```

Verify installation:

```bash
kubectl get vpa
```

Example:

```text
No resources found in default namespace.
```

This simply means VPA is installed but no VerticalPodAutoscaler resources have been created yet.

---

# Step 1 - Create an Nginx Deployment

Create `nginx-deployment.yaml`

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: nginx-deployment

spec:
  replicas: 2

  selector:
    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx

    spec:
      containers:
      - name: nginx
        image: nginx:latest

        resources:
          requests:
            cpu: "50m"
            memory: "50Mi"
```

Create the Deployment:

```bash
kubectl create -f nginx-deployment.yaml
```

Verify:

```bash
kubectl get deployment

kubectl get pods
```

---

# Step 2 - Create a VPA

Create `vpa.yaml`

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler

metadata:
  name: nginx-vpa

spec:

  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-deployment

  updatePolicy:
    updateMode: Off
```

Apply:

```bash
kubectl apply -f vpa.yaml
```

Verify:

```bash
kubectl get vpa
```

Example:

```text
NAME        MODE   CPU   MEM   PROVIDED

nginx-vpa   Off
```

Initially no recommendations are available because VPA needs time to collect usage statistics.

---

# Step 3 - View Recommendations

Wait a few minutes.

Describe the VPA:

```bash
kubectl describe vpa nginx-vpa
```

After collecting metrics:

```bash
kubectl get vpa
```

Example:

```text
NAME        MODE   CPU   MEM     PROVIDED

nginx-vpa   Off    25m   250Mi   True
```

Recommended resources:

- CPU : **25m**
- Memory : **250Mi**

Since **updateMode=Off**, the recommendations are **not applied automatically**.

---

# Step 4 - Enable Automatic Updates

Terminal 1

Watch Pods:

```bash
kubectl get pods -w
```

Terminal 2

Edit the VPA:

```bash
kubectl edit vpa nginx-vpa
```

Change:

```yaml
updateMode: Off
```

to

```yaml
updateMode: Auto
```

Save the file.

Verify:

```bash
kubectl get vpa
```

Example:

```text
NAME        MODE   CPU   MEM     PROVIDED

nginx-vpa   Auto   25m   250Mi   True
```

# Observe Automatic Pod Recreation

Because VPA must modify CPU and Memory requests, it **cannot update a running Pod**.

Instead, it:

1. Evicts the existing Pod.
2. Creates a replacement Pod.
3. Applies the recommended CPU and Memory requests.

Example:

```text
nginx-deployment-67cf79f979-5hsjj   Terminating

nginx-deployment-67cf79f979-slktm   Pending

nginx-deployment-67cf79f979-slktm   ContainerCreating

nginx-deployment-67cf79f979-slktm   Running
```

---

# Verify VPA Eviction

Describe one of the recreated Pods:

```bash
kubectl describe pod <pod-name>
```

Events:

```text
Normal  EvictedByVPA

Pod was evicted by VPA Updater to apply resource recommendation.
```

This confirms that VPA updated the Pod with the recommended CPU and Memory values.

# HPA vs VPA

| Feature | HPA | VPA |
|---------|-----|-----|
| Scales | Number of Pods | CPU & Memory requests |
| Adds Pods | ✅ | ❌ |
| Removes Pods | ✅ | ❌ |
| Changes CPU Requests | ❌ | ✅ |
| Changes Memory Requests | ❌ | ✅ |
| Uses Metrics Server | ✅ | ✅ |
| Restarts Pods | No | Yes (Auto mode) |

# Advantages

- Optimizes CPU and Memory allocation.
- Prevents over-provisioning.
- Prevents under-provisioning.
- Improves cluster utilization.
- Reduces infrastructure costs.
- Automatically adapts to changing workloads.

---

# Limitations

- Updating resource requests requires Pod recreation.
- VPA may briefly interrupt workloads when Pods are evicted.
- Not recommended to run **HPA and VPA together** on the same CPU or Memory metrics because they may conflict.
- Best suited for applications with relatively stable traffic patterns.

---

# Interview Points

- VPA automatically adjusts **CPU and Memory requests** based on observed usage.
- VPA has three update modes: **Off**, **Initial**, and **Auto**.
- **Off** provides recommendations only.
- **Initial** applies recommendations only when Pods are first created.
- **Auto** evicts and recreates Pods using the recommended resources.
- VPA relies on the **Metrics Server** to collect resource usage.
- VPA changes resource requests, whereas HPA changes the number of Pod replicas.
- VPA cannot modify a running Pod; it must recreate the Pod to apply new resource requests.
- Production environments often use **HPA for stateless applications** and **VPA for stateful or long-running workloads**, depending on application characteristics.
