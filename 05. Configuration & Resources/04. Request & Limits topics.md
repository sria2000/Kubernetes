# Requests & Limits

Goal: create a pod that requests all the available CPU & memory resources on a specific worker node, to see how Kubernetes handles scheduling at (and past) capacity.

## Step 1: Describe Node to Check Capacity, Allocatable & Allocated

```bash
kubectl get nodes
k describe node node01
```

```
Allocatable:
  cpu:                1
  ephemeral-storage:  18698430040
  hugepages-2Mi:      0
  memory:             1846516Ki
  pods:               110
Allocated resources:
  (Total limits may be over 100 percent, i.e., overcommitted.)
  Resource           Requests    Limits
  --------           --------    ------
  cpu                100m (10%)  1 (100%)
  memory             10Mi (0%)   1Gi (56%)
  ephemeral-storage  0 (0%)      0 (0%)
  hugepages-2Mi      0 (0%)      0 (0%)
Events:              <none>
```

### Working Out the Remaining Capacity

**CPU:**
```
CPU = 1000m - 100m = 900m
```

**Memory:**
```
10 Mi = 10 × 1024 Ki
      = 10240 Ki

  1846516 Ki
-    10240 Ki
------------
  1836276 Ki

1836276 / 1024 = 1793.24 Mi
```

So the node has **900m CPU** and **~1793Mi memory** left to allocate.

## Step 2: Pod 1 — "Fit Pod" (exactly fills remaining capacity)

```bash
vi pod-1.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: fit-pod
spec:
  containers:
  - name: successful-container
    image: nginx
    resources:
      requests:
        memory: "1793Mi"
        cpu: "900m"
      limits:
        memory: "1793Mi"
        cpu: "900m"
```

```bash
kubectl create -f pod-1.yaml
```

Node status after scheduling:

```
Capacity:
  cpu:                1
  ephemeral-storage:  19221248Ki
  hugepages-2Mi:      0
  memory:             1948916Ki
  pods:               110
Allocatable:
  cpu:                1
  ephemeral-storage:  18698430040
  hugepages-2Mi:      0
  memory:             1846516Ki
  pods:               110

Allocated resources:
  (Total limits may be over 100 percent, i.e., overcommitted.)
  Resource           Requests      Limits
  --------           --------      ------
  cpu                1 (100%)      1900m (190%)
  memory             1803Mi (99%)  2817Mi (156%)
  ephemeral-storage  0 (0%)        0 (0%)
  hugepages-2Mi      0 (0%)        0 (0%)
Events:              <none>
```

Requests hit 100%, and limits show overcommitment (190% CPU, 156% memory) — expected, since limits are allowed to exceed allocatable.

```bash
kubectl delete -f pod-1.yaml
```

## Step 3: Pod 2 — "Unfit Pod" (exceeds remaining capacity)

```bash
nano pod-2.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: unfit-pod
spec:
  containers:
  - name: successful-container
    image: nginx
    resources:
      requests:
        memory: "500Mi"
        cpu: "200m"
      limits:
        memory: "854Mi"
        cpu: "200m"
```

```bash
kubectl create -f pod-2.yaml
```

Result — scheduling fails:

```
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  15s   default-scheduler  0/2 nodes are available: 1 Insufficient memory, 2 Insufficient cpu. no new claims to deallocate, preemption: 0/2 nodes are available: 2 No preemption victims found for incoming pod.
```

```bash
kubectl delete -f pod-2.yaml
```

### Important Pointer

**Question:** Can we launch a new pod after 100% of request (CPU and memory) is reached?

**Answer:** Yes. A pod without any resource requests is assumed to request 0 CPU and 0 memory. Although the pod gets scheduled, it can be evicted or throttled if the node becomes resource-starved — because it has no guaranteed resources.

## Step 4: Pod 3 — "Tmp Pod" (minimal footprint)

```bash
nano pod-3.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: tmp-pod
spec:
  containers:
  - name: successful-container
    image: nginx
    resources:
      requests:
        memory: "1Mi"
        cpu: "1m"
```

```bash
kubectl create -f pod-3.yaml
kubectl delete -f pod-3.yaml
```

```bash
kubectl run curl-pod --image=alpine/curl -- sleep 36000
```

## Summary

| Pod | Requests fit within remaining allocatable? | Outcome |
|---|---|---|
| `fit-pod` | Exactly matches remaining CPU/memory | Scheduled successfully |
| `unfit-pod` | Exceeds remaining CPU/memory | `FailedScheduling` — insufficient resources |
| `tmp-pod` | Minimal (1m CPU, 1Mi memory) | Scheduled easily |

**Key takeaway:** The scheduler only checks **requests** against allocatable capacity when deciding whether a pod fits. **Limits** can exceed allocatable (overcommitment) since they only cap usage at runtime, not at scheduling time.
