# Kubernetes Services & Networking

## Link -> https://kubernetes.io/docs/concepts/services-networking/service/

## What is a Service?

Pods in Kubernetes are **ephemeral**, meaning they can be created, destroyed, or replaced at any time.

When a Pod is recreated:
- It receives a **new IP address**.
- Applications should **never hard-code Pod IPs**.

A **Service** provides a **stable network endpoint** that always points to the correct Pods.

Think of a Service as a **gateway** or **load balancer** that distributes incoming traffic to healthy Pods.

---

# Why Do We Need Services?

Without a Service:

```
Frontend Pod
      |
      |  curl 10.244.0.5
      |
Backend Pod
```

If the Backend Pod is recreated:

```
Old IP : 10.244.0.5 ❌

New IP : 10.244.0.8
```

The Frontend application breaks because it still points to the old IP.

---

With a Service:

```
Frontend Pod
      |
      |
      v
 Backend Service
      |
  -------------------
  |        |        |
Pod A    Pod B    Pod C
```

The Frontend always communicates with the **Service**, and Kubernetes automatically forwards the request to one of the backend Pods.

---

# Kubernetes Networking Basics

Every Pod gets its own **private IP address**.

Example:

| Pod | Private IP |
|------|------------|
| frontend-pod | 10.244.0.3 |
| backend-pod-1 | 10.244.0.4 |
| backend-pod-2 | 10.244.0.5 |

Pods inside the same Kubernetes cluster can communicate directly using these private IPs.

To view Pod IPs:

```bash
kubectl get pods -o wide
```

Example:

```
NAME             IP
frontend-pod     10.244.0.3
backend-pod-1    10.244.0.4
backend-pod-2    10.244.0.5
```

---

# Communicating Using Pod IPs

Enter a Pod:

```bash
kubectl exec -it frontend-pod -- bash
```

Access another Pod directly:

```bash
curl 10.244.0.5
```

Although this works, **it is not recommended** because Pod IPs change whenever Pods are recreated.

**Never hard-code Pod IP addresses.**

---

# Service as a Stable Endpoint

Instead of talking directly to Pods:

```
Frontend Pod
       |
       |
       v
Backend Service
       |
       |
   Backend Pods
```

The Frontend communicates only with the Service.

Example:

```bash
kubectl exec -it frontend-pod -- bash

curl backend-service
```

or

```bash
curl <SERVICE-IP>
```

The Service automatically forwards the request to one of its backend Pods.

---

# Viewing Services

List all Services:

```bash
kubectl get service
```

Example:

```
NAME              TYPE        CLUSTER-IP
backend-service   ClusterIP   10.96.25.100
```

Use the Service IP:

```bash
curl 10.96.25.100
```

# Load Balancing

Suppose you have two backend Pods.

```
Backend Service
      |
  ------------
  |          |
Pod1       Pod2
```

Every request may be routed to a different Pod.

Example:

```
Request 1 -> Pod1

Request 2 -> Pod2

Request 3 -> Pod1
```

This distributes traffic evenly across replicas.

---

# Adding More Pods

Create another backend Pod.

```bash
kubectl run backend-pod-3 \
  --image=nginx \
  --labels=type=webserver
```

Now the Service automatically discovers it.

```
Backend Service
       |
-------------------------
|          |            |
Pod1      Pod2        Pod3
```

Testing:

```bash
kubectl exec -it frontend-pod -- bash

curl <SERVICE-IP>
```

Multiple requests may return responses from:

- backend-pod-1
- backend-pod-2
- backend-pod-3

No application changes are required.

# Service and Endpoints

A Service itself does **not** contain application data.

Instead, it maintains a list called **Endpoints**.

Endpoints are the IP addresses of all Pods matching the Service selector.

Example:

```
Service
   |
   +----> 10.244.0.4
   |
   +----> 10.244.0.5
   |
   +----> 10.244.0.8
```

When traffic reaches the Service, Kubernetes chooses one of these endpoints.

View Endpoints:

```bash
kubectl get endpoints
```

or

```bash
kubectl describe service backend-service
```

---

# Service Discovery Using DNS

Every Service automatically receives a DNS name.

Instead of using IPs:

```bash
curl backend-service
```

Kubernetes DNS resolves:

```
backend-service
      ↓
10.96.25.100
```

This is much easier than remembering IP addresses.

# Types of Kubernetes Services

| Service Type | Description | Typical Use Cases |
|--------------|-------------|-------------------|
| **ClusterIP** | Default Service type. Accessible only within the cluster. | Internal microservices communication |
| **NodePort** | Exposes the Service on a fixed port (30000–32767) on every Node. | Development, testing, demos |
| **LoadBalancer** | Creates an external cloud load balancer. | Production applications requiring Internet access |
| **ExternalName** | Maps the Service to an external DNS name. | Connecting to external services |

---

# ClusterIP

(Default)

```
Pod
  |
ClusterIP Service
  |
Pods
```

- Internal communication only
- Cannot be accessed from outside the cluster
- Most commonly used Service type

---

# NodePort

```
Internet
     |
NodeIP:30080
     |
NodePort Service
     |
Pods
```

- Opens the same port on every Kubernetes Node
- Useful for testing
- Accessible using:

```
<Node-IP>:NodePort
```

Example:

```
192.168.1.100:30080
```

---

# LoadBalancer

```
Internet
     |
Cloud Load Balancer
     |
Service
     |
Pods
```

Available on cloud providers such as:

- AWS
- Azure
- Google Cloud

The cloud provider automatically creates a public load balancer.

---

# ExternalName

Instead of forwarding traffic to Pods, the Service redirects DNS.

Example:

```
database.company.com
```

Your application simply connects to:

```
db-service
```

Kubernetes resolves it to:

```
database.company.com
```

# Interview Tips

**Why do we need a Service?**

Because Pod IP addresses change whenever Pods are recreated. A Service provides a stable endpoint that applications can always use.

---

**Does a Service have its own Pod?**

No.

A Service is a Kubernetes object that forwards traffic to Pods.

---

**Can multiple Pods belong to one Service?**

Yes.

A Service can load balance traffic across multiple Pods.

---

**How does a Service know which Pods to send traffic to?**

Using **Labels** and **Selectors**.

---

**Can Pods communicate without a Service?**

Yes.

Pods can communicate directly using Pod IPs, but this is **not recommended** because Pod IPs are temporary.

---

# Summary

- Every Pod gets a unique private IP.
- Pod IPs change when Pods are recreated.
- Never hard-code Pod IP addresses.
- A Service provides a stable IP and DNS name.
- Services distribute traffic across multiple Pods.
- Services use Endpoints to route traffic.
- ClusterIP is the default Service type.
- NodePort exposes applications through a Node port.
- LoadBalancer exposes applications externally using a cloud load balancer.
- ExternalName maps a Service to an external DNS name.
