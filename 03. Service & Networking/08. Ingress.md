# Kubernetes Ingress — Notes & Lab Walkthrough

## 1. Why Ingress?

If you have multiple services for different websites, using a separate `LoadBalancer` Service for each one gets expensive fast (each cloud LB = separate cost).

The ideal setup is a **single Load Balancer** in front of the cluster, with routing logic that decides which service each request should go to.

**Ingress** is the Kubernetes object that acts as this entry point — it routes external traffic to internal services based on rules you define (hostname, path, etc.), so you only need one LB.

```
Internet → LB → Ingress Controller → Ingress Resource (rules) → Service → Pod
```

## 2. Components of Ingress

| Component | Role |
|---|---|
| **Ingress Controller** | Sits between the LB and the Services. Implements/enforces the rules. Nothing happens without a controller running (e.g. nginx, AWS ALB, GCE, Traefik, HAProxy). Kubernetes ships the API object but **not** a default controller — you must install one. |
| **Ingress Resource** | The YAML object where you declare the routing rules (host, path, backend service). |

> 📌 **Tip:** A common first-timer mistake is creating an Ingress resource and expecting traffic to route — nothing works until an Ingress Controller is actually deployed and watching that IngressClass.

Reference: [K8s docs — Name-based virtual hosting](https://kubernetes.io/docs/concepts/services-networking/ingress/#name-based-virtual-hosting)
Reference: [K8s docs — Ingress Controllers](https://kubernetes.io/docs/concepts/services-networking/ingress-controllers/)
Reference: [ingress-nginx install docs](https://kubernetes.github.io/ingress-nginx/deploy/)

## 3. Path Types Supported

Every path in an Ingress rule must declare a `pathType`.

| Path Type | Description | Example Path | Matching Behaviour |
|---|---|---|---|
| **Exact** | Matches the URL path exactly, case-sensitive | `/foo/bar` | Only matches `/foo/bar` exactly |
| **Prefix** | Matches based on a `/`-separated URL path prefix, case-sensitive | `/foo` | Matches `/foo`, `/foo/` |
| **ImplementationSpecific** | Matching depends entirely on the IngressClass/controller — not portable across controllers | — | Controller-defined |

### Matching examples (official semantics)

| Kind | Path(s) | Request path(s) | Matches? |
|---|---|---|---|
| Prefix | `/` | (all paths) | Yes |
| Exact | `/foo` | `/foo` | Yes |
| Exact | `/foo` | `/bar` | No |
| Exact | `/foo` | `/foo/` | **No** |
| Exact | `/foo/` | `/foo` | **No** |
| Prefix | `/foo` | `/foo`, `/foo/` | Yes |
| Prefix | `/foo/` | `/foo`, `/foo/` | Yes |
| Prefix | `/aaa/bb` | `/aaa/bbb` | No |
| Prefix | `/aaa/bbb` | `/aaa/bbb` | Yes |
| Prefix | `/aaa/bbb/` | `/aaa/bbb` | Yes, ignores trailing slash |
| Prefix | `/aaa/bbb` | `/aaa/bbb/` | Yes, matches trailing slash |

> 📌 **Tip:** `Exact` is trailing-slash sensitive; `/foo` and `/foo/` are treated as **different** paths. `Prefix` normalizes on `/`-separated segments, so it's generally the safer default unless you specifically need strict exact matching.

> 📌 **Tip:** When multiple paths could match the same request, the Ingress controller picks the **longest matching path**. If paths are still equal, `Exact` wins over `Prefix`. Keep this in mind when you define overlapping rules like `/foo` and `/foo/bar`.

## 4. Building Ingress Resources with `kubectl create ingress`

### Rule 1 — single host, single backend
```bash
kubectl create ingress first-ingress --rule="example.internal/*=example-service:80"
```
```bash
kubectl describe ingress first-ingress
```
```
Rules:
  Host              Path  Backends
  ----              ----  --------
  example.internal
                    /   example-service:80 (<error: services "example-service" not found>)
```
> The backend shows an error here because the Service doesn't exist yet — the Ingress resource can be created independently of the Service/Pod existing.

### Rule 2 — two hosts, two backends
```bash
kubectl create ingress second-ingress \
  --rule="example.internal/*=example-service:80" \
  --rule="srilabs.internal/*=srilabs-service:80"
```

> 📌 **Tip:** `--rule` syntax is `host/path=service:port`. Use `*` as host to match any host (path-based-only routing). Multiple `--rule` flags = multiple host/path rules on the same Ingress object.

## 5. Path-Based Routing (no host)

### Generate the base manifest
```bash
kubectl create ingress path-based-ingress \
  --rule="*/=example-service:80" \
  --dry-run=client -o yaml
```

### Final manifest — `path-based-ingress.yaml`
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: path-based-ingress
spec:
  rules:
  - http:
      paths:
      - path: /app-1
        pathType: Exact
        backend:
          service:
            name: app-1-service
            port:
              number: 80
      - path: /app-2
        pathType: Exact
        backend:
          service:
            name: app-2-service
            port:
              number: 80
```
```bash
kubectl create -f path-based-ingress.yaml
kubectl describe ingress path-based-ingress
```
```
Rules:
  Host        Path  Backends
  ----        ----  --------
  *
              /app-1   app-1-service:80 (<error: services "app-1-service" not found>)
              /app-2   app-2-service:80 (<error: services "app-2-service" not found>)
```

## 6. Named Host + Path-Based Routing

### Generate the base manifest
```bash
kubectl create ingress named-path \
  --rule="example.internal/=app-1:80" \
  --dry-run=client -o yaml
```

### Final manifest — `named-path.yaml`
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: named-path
spec:
  rules:
  - host: example.internal
    http:
      paths:
      - path: /app-1
        pathType: Exact
        backend:
          service:
            name: app-1-service
            port:
              number: 80
      - path: /app-2
        pathType: Exact
        backend:
          service:
            name: app-2-service
            port:
              number: 80
```
```bash
kubectl create -f named-path.yaml
kubectl describe ingress named-path
```
```
Rules:
  Host              Path  Backends
  ----              ----  --------
  example.internal
                    /app-1   app-1-service:80 (<error: services "app-1-service" not found>)
                    /app-2   app-2-service:80 (<error: services "app-2-service" not found>)
```

## 7. Full End-to-End Lab: nginx Ingress Controller

### Step 1 — Create backend pods
```bash
kubectl run example-pod --image=nginx
kubectl run srilabs-pod --image=httpd
```

### Step 2 — Expose pods as Services
```bash
kubectl expose pod example-pod --name example-service --port=80 --target-port=80
kubectl expose pod srilabs-pod --name srilabs-service --port=80 --target-port=80
```
```bash
kubectl get service
```
```
NAME              TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
example-service   ClusterIP   10.98.103.81    <none>        80/TCP    7s
srilabs-service   ClusterIP   10.99.235.250   <none>        80/TCP    7s
```

> 📌 **Tip:** Confirm the Service is actually routing to the right pod by comparing `Endpoints` in `kubectl describe service <name>` against `kubectl get pods -o wide` (pod IP). If Endpoints is empty, your selector/labels don't match — this is the #1 cause of "Ingress works but backend 502s."

### Step 3 — Create Ingress with 2 host-based rules
```bash
kubectl create ingress main-ingress --class=nginx \
  --rule="example.internal/*=example-service:80" \
  --rule="srilabs.internal/*=srilabs-service:80"
```
```bash
kubectl describe ingress main-ingress
```
```
Rules:
  Host              Path  Backends
  ----              ----  --------
  example.internal
                    /   example-service:80 (192.168.1.141:80)
  srilabs.internal
                    /   srilabs-service:80 (192.168.1.78:80)
```

> 📌 **Tip:** `--class=nginx` sets `spec.ingressClassName`. If you skip this and have multiple controllers installed (e.g. nginx + AWS ALB), your Ingress may not be picked up by the controller you expect, or may be picked up by all of them.

### Step 4 — Install the nginx Ingress Controller
```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.12.0/deploy/static/provider/cloud/deploy.yaml
```
This creates: `ingress-nginx` namespace, ServiceAccounts, RBAC (Roles/ClusterRoles/Bindings), the controller Deployment, admission webhook Jobs, and the `nginx` IngressClass.

### Step 5 — Verify controller is up
```bash
kubectl get pods -n ingress-nginx
kubectl get service -n ingress-nginx
```
```
NAME                                 TYPE           CLUSTER-IP       EXTERNAL-IP   PORT(S)
ingress-nginx-controller             LoadBalancer   10.110.239.179   <pending>     80:31570/TCP,443:30105/TCP
```

> 📌 **Tip:** On a homelab/on-prem cluster with no cloud provider integration, `EXTERNAL-IP` will stay `<pending>` forever — there's no cloud controller to provision an LB. Options: use the `CLUSTER-IP` directly for testing (as below), use the `NodePort` (`31570` here), or install **MetalLB** to get real LoadBalancer IPs on bare metal.

### Step 6 — Verify routing with `curl` + `Host` header
```bash
curl -H "Host: example.internal" 10.110.239.179
curl -H "Host: srilabs.internal" 10.110.239.179
```
- `example.internal` → hits the nginx pod → "Welcome to nginx!"
- `srilabs.internal` → hits the httpd pod → "It works! Apache httpd"

> 📌 **Tip:** This is exactly how name-based virtual hosting works in production too — DNS points `example.internal` and `srilabs.internal` at the same LB IP, and the `Host` header (not the IP) is what the Ingress controller uses to pick the rule. Locally, you can fake this with an `/etc/hosts` entry pointing both names at the LB/Cluster IP instead of using `curl -H`.

### Step 7 — Cleanup
```bash
kubectl delete -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.12.0/deploy/static/provider/cloud/deploy.yaml

kubectl delete ingress main-ingress

kubectl delete service example-service srilabs-service
kubectl delete pod example-pod srilabs-pod
```

## 8. Additional Tips & Gotchas (beyond the lab)

- **IngressClass vs. annotation:** Older manifests use `kubernetes.io/ingress.class: nginx` as an annotation. Current best practice is `spec.ingressClassName: nginx` (what `--class` sets for you). Don't mix both on the same object.
- **Default backend:** You can set a `defaultBackend` on the Ingress spec to catch any request that doesn't match a rule, instead of getting a generic 404 from the controller.
- **TLS termination:** Ingress can terminate TLS via `spec.tls` referencing a `Secret` of type `kubernetes.io/tls`. The Ingress controller does the actual termination — the backend Service/Pod usually stays plain HTTP.
- **Rewrite/redirect annotations are controller-specific:** e.g. `nginx.ingress.kubernetes.io/rewrite-target` only works with ingress-nginx, not with AWS ALB or GCE ingress. Annotations are the main place where "portable" Ingress YAML breaks across controllers.
- **Multiple controllers in one cluster:** Perfectly valid — each Ingress picks its controller via `ingressClassName`. Useful for e.g. an internal-only nginx controller + external-facing ALB.
- **Debugging checklist when an Ingress "doesn't work":**
  1. Is an Ingress Controller actually running (`kubectl get pods -n <controller-namespace>`)?
  2. Does the Ingress have the right `ingressClassName`/annotation matching that controller?
  3. Does `kubectl describe ingress <name>` show real backend IPs, or still `<error: services ... not found>`?
  4. Does the Service have healthy `Endpoints` (`kubectl describe service <name>`)?
  5. Are you hitting it with the correct `Host` header / DNS name, not just the bare IP?
  6. Check controller logs: `kubectl logs -n ingress-nginx deploy/ingress-nginx-controller`.
- **Ingress vs. Gateway API:** Ingress is intentionally simple (host/path/backend). For more advanced traffic splitting, header-based routing, or multi-protocol support, the newer **Gateway API** is the direction Kubernetes networking is heading — worth knowing about even if Ingress still covers most day-to-day needs.
- **Homelab-specific note (bare metal / VMware VMs):** without a cloud LoadBalancer, pair the Ingress Controller with **MetalLB** in Layer2 mode to get a real routable `EXTERNAL-IP` on your local network, rather than relying on ClusterIP/NodePort workarounds for testing.
