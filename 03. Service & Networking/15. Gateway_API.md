# Kubernetes Gateway API

## Overview

**Ingress** is a Kubernetes API object used to manage external user access to Services running inside a Kubernetes cluster.

Although Ingress works well for many HTTP-based applications, it has several limitations for modern production environments.

To overcome these limitations, the **Gateway API** project was introduced.

Gateway API is the next generation of Kubernetes traffic management that provides a more flexible, extensible and role-oriented networking model.

---

# Why Gateway API?

### Limitations of Ingress

- Primarily designed for HTTP and HTTPS traffic.
- Limited support for advanced traffic management.
- No native support for TCP or UDP routing.
- Difficult to extend with new routing capabilities.
- Limited separation of responsibilities between cluster administrators and application teams.

---

# Advantages of Gateway API

- Supports both **Layer 4** and **Layer 7** protocols.
- Role-based networking model.
- Standard API across multiple Gateway implementations.
- Supports:
  - HTTP
  - HTTPS
  - TCP
  - UDP
  - gRPC
- Supports advanced traffic management.
- Supports HTTP traffic splitting and weighted routing.
- Easier migration from traditional Ingress.

# Gateway API Components

## 1. GatewayClass

A **GatewayClass** defines which Gateway Controller is responsible for implementing Gateway resources.

Different vendors can provide different Gateway Controllers.

Examples:

- NGINX Gateway
- Istio
- Kong
- Cilium
- Envoy Gateway

---

## 2. Gateway

A **Gateway** represents the traffic handling infrastructure.

It defines:

- Listener ports
- Protocols
- TLS configuration
- Entry point into the cluster

A Gateway may represent:

- Cloud Load Balancer
- Ingress Proxy
- Reverse Proxy
- Edge Gateway

---

## 3. HTTPRoute

HTTPRoute defines how HTTP requests should be routed from a Gateway to backend Services.

It contains:

- Path matching
- Host matching
- Header matching
- Backend Services
- Traffic splitting
- Weighted routing

---

## 4. Gateway Controller

A Gateway Controller watches Gateway API resources and configures the underlying networking infrastructure.

Examples:

- Creates Load Balancer
- Configures NGINX
- Programs Envoy
- Updates HAProxy

---


# Supported Route Types

| Route | OSI Layer | Routing Based On | TLS Support | Purpose |
|--------|-----------|------------------|-------------|---------|
| HTTPRoute | Layer 7 | HTTP Path, Headers, Hostname | Terminated | HTTP & HTTPS Routing |
| GRPCRoute | Layer 7 | gRPC Metadata | Terminated | gRPC Routing |
| TCPRoute | Layer 4 | Destination Port | Passthrough/Terminate | TCP Routing |
| UDPRoute | Layer 4 | Destination Port | None | UDP Routing |
| TLSRoute | Between L4-L7 | SNI | Passthrough/Terminate | TLS Routing |

---

# HTTP Traffic Splitting

Gateway API supports traffic splitting between multiple backend Services.

Example:

```
User Request

        │

        ▼

HTTPRoute

   ├── 80% → Version 1

   └── 20% → Version 2
```

This is commonly used for:

- Canary Deployments
- Blue/Green Deployments
- A/B Testing

Traffic weights are configured inside **backendRefs**.

# Create a Gateway

Create **gateway.yaml**

```yaml
apiVersion: gateway.networking.k8s.io/v1beta1
kind: Gateway

metadata:
  name: nginx-gateway
  namespace: default

spec:
  gatewayClassName: nginx

  listeners:

  - name: http
    protocol: HTTP
    port: 80
```

Apply

```bash
kubectl apply -f gateway.yaml
```

Verify

```bash
kubectl get gateway
```

# Create HTTPRoute

Create **httproute.yaml**

```yaml
apiVersion: gateway.networking.k8s.io/v1beta1
kind: HTTPRoute

metadata:
  name: apache-route

spec:

  parentRefs:

  - name: nginx-gateway

  rules:

  - matches:

    - path:
        type: PathPrefix
        value: /

    backendRefs:

    - name: apache-service
      port: 80
```

Apply

```bash
kubectl apply -f httproute.yaml
```

# TLS Modes

Gateway API supports two TLS modes.

---

## TLS Passthrough

The Gateway forwards encrypted traffic directly to backend Pods.

The backend Pod performs TLS decryption.

```
Client

   │ HTTPS

   ▼

Gateway

   │ Encrypted

   ▼

Backend Pod

Decrypts TLS
```

---

## TLS Termination

The Gateway decrypts HTTPS traffic before forwarding HTTP traffic to backend Services.

```
Client

   │ HTTPS

   ▼

Gateway

Decrypts TLS

   │ HTTP

   ▼

Backend Service
```

---

# TLS Passthrough vs TLS Termination

| Feature | TLS Passthrough | TLS Termination |
|---------|-----------------|----------------|
| TLS Decryption | Backend Pod | Gateway |
| Certificate Location | Backend | Gateway |
| HTTP Inspection | No | Yes |
| Header Manipulation | No | Yes |
| Routing | SNI | Full HTTP Routing |

---

# Supported TLS Routes

| Listener | TLS Mode | Route Type |
|----------|----------|------------|
| TLS | Passthrough | TLSRoute |
| TLS | Terminate | TCPRoute |
| HTTPS | Terminate | HTTPRoute |

# Create TLS Secret

Generate Certificate

```bash
openssl req -x509 -nodes -days 365 \
-newkey rsa:2048 \
-keyout tls.key \
-out tls.crt \
-subj "/CN=example.internal/O=example-org"
```

Create Secret

```bash
kubectl create secret tls example-tls \
--cert=tls.crt \
--key=tls.key
```

Verify

```bash
kubectl get secret
```

# Create TLS Gateway

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway

metadata:
  name: my-tls-gateway

spec:

  gatewayClassName: nginx

  listeners:

  - name: https
    protocol: HTTPS
    port: 443

    tls:
      mode: Terminate

      certificateRefs:

      - kind: Secret
        name: example-tls
```

Apply

```bash
kubectl apply -f my-tls-gateway.yaml
```

# Mapping Ingress API to Gateway API

## Entry Points

### Ingress

Every Ingress resource automatically provides:

- HTTP
- HTTPS

through the Ingress Controller.

### Gateway API

Gateway listeners explicitly define:

- Port
- Protocol
- TLS
- Certificates

---

## TLS

### Ingress

TLS is configured under the **tls** section.

Certificates are stored in Kubernetes Secrets.

### Gateway API

TLS is configured directly on the **Gateway Listener**.

Certificates are still stored as Kubernetes Secrets.

---

## Routing

### Ingress

Routing rules are embedded inside the Ingress resource.

### Gateway API

Routing rules are separated into dedicated Route resources such as:

- HTTPRoute
- TCPRoute
- UDPRoute
- TLSRoute
- GRPCRoute

This separation provides much greater flexibility and allows different teams to independently manage infrastructure and application routing.

---

# Ingress vs Gateway API

| Feature | Ingress | Gateway API |
|---------|----------|-------------|
| HTTP | Yes | Yes |
| HTTPS | Yes | Yes |
| TCP | Limited | Yes |
| UDP | Limited | Yes |
| gRPC | Limited | Yes |
| Traffic Splitting | Vendor-specific | Native |
| Canary Deployments | Limited | Native |
| Blue/Green Deployments | Limited | Native |
| Multiple Route Types | No | Yes |
| Extensible | Limited | Yes |
| Role Separation | Limited | Excellent |

---

# Advantages

- Modern replacement for Ingress.
- Supports Layer 4 and Layer 7 traffic.
- Vendor-neutral API.
- Supports advanced traffic management.
- Native traffic splitting and weighted routing.
- Better separation between infrastructure and application teams.
- Supports multiple Gateway implementations.
