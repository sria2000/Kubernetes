# Kubernetes Service Lab - Manual Endpoints

This hands-on lab demonstrates how a Kubernetes **Service** works by manually creating an **Endpoint**. It also explains the difference between **Port** and **TargetPort**.

---

# Lab Architecture

```
                 Frontend Pod
                       |
                       |
                 curl Service IP
                       |
                       v
                +----------------+
                | ClusterIP      |
                | simple-service |
                +----------------+
                       |
                  Endpoints
                       |
                       v
                  Backend Pod
                    (nginx)
```

Unlike a normal Service, this lab manually creates the **Endpoints** object instead of using selectors.

---

# Step 1: Create the Backend Pod

Create an NGINX backend Pod.

```bash
kubectl run backend-pod --image=nginx
```

Verify it is running.

```bash
kubectl get pods
```

---

# Step 2: Create the Frontend Pod

Create an Ubuntu Pod that stays running.

```bash
kubectl run frontend-pod \
  --image=ubuntu \
  --command -- sleep 36000
```

---

# Step 3: Test Communication Between Pods

View the Pod IP addresses.

```bash
kubectl get pods -o wide
```

Example:

```
NAME           READY   STATUS    IP
backend-pod    1/1     Running   192.168.1.207
frontend-pod   1/1     Running   192.168.1.252
```

Enter the Frontend Pod.

```bash
kubectl exec -it frontend-pod -- bash
```

Install curl.

```bash
apt-get update
apt-get install -y curl
```

Access the Backend Pod directly using its IP.

```bash
curl 192.168.1.207
```

Expected output:

```
Welcome to nginx!
```

At this point the Frontend Pod communicates directly with the Backend Pod.

> **Note**
>
> This is **not recommended** because Pod IPs change whenever Pods are recreated.

---

# Step 4: Create a ClusterIP Service

Create a Service named **simple-service**.

**service.yaml**

```yaml
apiVersion: v1
kind: Service

metadata:
  name: simple-service

spec:
  ports:
    - port: 80
      targetPort: 80
```

Create the Service.

```bash
kubectl create -f service.yaml
```

Verify.

```bash
kubectl get service
```

Example:

```
NAME             TYPE        CLUSTER-IP
simple-service   ClusterIP   10.98.151.120
```

---

# Step 5: Verify the Service

Describe the Service.

```bash
kubectl describe service simple-service
```

Notice:

```
Endpoints: <none>
```

Since there are **no endpoints**, the Service has nowhere to forward traffic.

Testing it will fail.

```bash
curl <SERVICE-IP>
```

---

# Step 6: Create a Manual Endpoint

Normally Kubernetes creates Endpoints automatically using selectors.

In this lab we create them manually.

Replace the IP below with the Backend Pod IP.

**endpoint.yaml**

```yaml
apiVersion: v1
kind: Endpoints

metadata:
  name: simple-service

subsets:
  - addresses:
      - ip: 192.168.1.207

    ports:
      - port: 80
```

Create the Endpoint.

```bash
kubectl create -f endpoint.yaml
```

Describe the Service again.

```bash
kubectl describe service simple-service
```

Now you should see:

```
Endpoints:
192.168.1.207:80
```

The Service now knows where to send traffic.

---

# Step 7: Test the Service

Enter the Frontend Pod.

```bash
kubectl exec -it frontend-pod -- bash
```

Access the Service.

```bash
curl <SERVICE-IP>
```

Example:

```bash
curl 10.98.151.120
```

Expected output:

```
Welcome to nginx!
```

Traffic Flow:

```
Frontend Pod
      |
      |
Service IP
      |
      |
Endpoint
      |
Backend Pod
```

The Frontend Pod no longer communicates directly with the Backend Pod.

---

# Step 8: Understanding Port vs TargetPort

Modify the Service.

**service.yaml**

```yaml
apiVersion: v1
kind: Service

metadata:
  name: simple-service

spec:
  ports:
    - port: 8080
      targetPort: 80
```

Delete and recreate the Service.

```bash
kubectl delete -f service.yaml

kubectl create -f service.yaml

kubectl create -f endpoint.yaml
```

Verify.

```bash
kubectl get service
```

Example:

```
NAME             TYPE        CLUSTER-IP      PORT(S)

simple-service   ClusterIP   10.103.93.24   8080/TCP
```

---

# Step 9: Test Port Mapping

Enter the Frontend Pod.

```bash
kubectl exec -it frontend-pod -- bash
```

Access the Service.

```bash
curl 10.103.93.24:8080
```

Expected output:

```
Welcome to nginx!
```

Although the request was sent to **8080**, Kubernetes forwarded it to **port 80** on the Backend Pod.

Traffic Flow:

```
Client
   |
8080
   |
Service
   |
TargetPort 80
   |
Backend Pod
```

---

# Port vs TargetPort

| Port | TargetPort |
|------|------------|
| Port exposed by the Service | Port on the Pod |
| Clients connect here | Application listens here |
| Can be any valid port | Must match the container application port |

Example:

```
Client
   |
8080
   |
Service
   |
80
   |
NGINX Pod
```

The client never knows the Pod is listening on port 80.

---

# Why Use Different Ports?

Suppose your application listens on port **80**, but you want clients to use **8080**.

```
Client
      |
      | 8080
      |
Service
      |
      | 80
      |
NGINX
```

This flexibility is one of the major benefits of Kubernetes Services.

---

# Key Takeaways

- Pods can communicate directly using Pod IPs.
- Pod IPs are temporary and should never be hard-coded.
- A Service provides a stable IP address.
- A Service without Endpoints cannot forward traffic.
- Endpoints tell a Service where to route requests.
- Clients connect to the Service **Port**.
- Kubernetes forwards traffic to the **TargetPort** on the Pod.
- Normally, Endpoints are created automatically using Labels and Selectors. In this lab, they were created manually to demonstrate how Services work internally.
