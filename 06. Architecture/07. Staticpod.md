# Scheduling Pods Without a Scheduler: Static Pods

## Background: How Scheduling Normally Works

- The **scheduler** is responsible for deciding which worker node a pod should run on.
- Once the scheduler decides the node, the **API server** communicates with the **kubelet** on that node, which in turn takes care of actually running the pod.

## What Are Static Pods?

You can bypass the scheduler entirely and tell the kubelet directly to run a specific pod. Pods created this way — without going through the scheduler — are called **static pods**.

There are multiple ways to tell a kubelet to run a pod directly. One common method: placing the pod's YAML manifest in a specific directory that the kubelet watches.

## How It Works

If you place a pod YAML file in the kubelet's manifest directory (typically `/etc/kubernetes/manifests`), the pod is created automatically — the kubelet notices the file and starts the pod without any scheduler involvement.

Similarly, if you remove the YAML file from that directory, the kubelet detects the deletion and terminates the pod.

## Example

```bash
root@controlplane:/etc/kubernetes/manifests$ vi sripod.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sripod
spec:
  containers:
  - name: sripod-container
    image: nginx
```

Once saved, the kubelet picks it up automatically:

```bash
root@controlplane:/etc/kubernetes/manifests$ k get pods
NAME                  READY   STATUS    RESTARTS   AGE
sripod-controlplane   0/1     Pending   0          3s
```

Note the pod name gets suffixed with the node name (`-controlplane`) — a telltale sign it's a static pod.

Deleting the manifest file removes the pod:

```bash
root@controlplane:/etc/kubernetes/manifests$ rm sripod.yaml
root@controlplane:/etc/kubernetes/manifests$ k get pods
No resources found in default namespace.
```

## Key Takeaways

- Static pods are managed directly by the **kubelet**, not the scheduler or the control plane's pod management.
- The kubelet watches a manifest directory (path configured via `--pod-manifest-path` or `staticPodPath` in the kubelet config) and creates/deletes pods based on files added/removed there.
- The API server still gets a **read-only mirror** of the static pod so you can see it with `kubectl get pods`, but you can't manage it (edit/delete) through the API — you have to modify the manifest file on the node itself.
- Static pod names are automatically suffixed with the node's hostname.
