# Kubernetes Readiness Probe

## Documentation Reference

https://kubernetes.io/docs/concepts/workloads/pods/probes/

---

# Kubernetes Container Probes

A **probe** is a health check performed by the **kubelet** on containers running inside a Pod.

Kubernetes provides three types of probes:

1. Startup Probe
2. Liveness Probe
3. Readiness Probe

---

# Readiness Probe

## Purpose

A **readiness probe determines whether a container is ready to accept traffic.**

A container may be:

- Running
- Started successfully

but still not be ready to handle user requests.

Examples:

- Application is loading configuration
- Database connection is not established
- Cache is still warming up
- Application startup tasks are still running

In such cases, Kubernetes keeps the container running but removes the Pod from Service traffic.

---

# Readiness Probe Behaviour

```
Pod starts
    |
    |
Container Running
    |
    |
Readiness Probe Check
    |
    |
    +----------------+
    |                |
 Success          Failure
    |                |
    |                |
READY 1/1        READY 0/1
    |                |
    |                |
Receive traffic   Removed from Service endpoints
```

---

# Types of Readiness Probes

Kubernetes supports:

1. HTTP Probe
2. TCP Probe
3. Exec Probe

---

# Exec Readiness Probe Example

## ready.yaml

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: readiness

spec:

  containers:

  - name: readiness
    image: ubuntu
    tty: true

    readinessProbe:

      exec:
        command:
        - cat
        - /tmp/healthy

      initialDelaySeconds: 5
      periodSeconds: 5
```

---

# Explanation

The readiness probe executes this command inside the container:

```bash
cat /tmp/healthy
```

Kubernetes checks the command exit status.

Rules:

```
Exit Code 0
     |
     |
Probe Successful
Pod receives traffic


Exit Code != 0
     |
     |
Probe Failed
Pod removed from Service traffic
```

---

# Deploy Pod

Create the Pod:

```bash
kubectl apply -f ready.yaml
```

Check status:

```bash
kubectl get pods
```

Output:

```
NAME        READY   STATUS
readiness   0/1     Running
```

---

# Why is READY 0/1?

The container is running:

```
STATUS: Running
```

but the readiness probe is failing.

The probe is checking:

```bash
cat /tmp/healthy
```

The file does not exist:

```
/tmp/healthy
```

Therefore:

```
cat /tmp/healthy
```

returns a non-zero exit code.

Kubernetes marks the Pod as:

```
Not Ready
```

---

# Create the Health File

Create the file inside the container:

```bash
kubectl exec -it readiness -- touch /tmp/healthy
```

Verify:

```bash
kubectl exec -it readiness -- ls /tmp
```

Output:

```
healthy
```

---

# Verify Pod Readiness

Check:

```bash
kubectl get pods
```

Output:

```
NAME        READY   STATUS    RESTARTS   AGE
readiness   1/1     Running   0          17m
```

Now:

```
READY 1/1
```

means:

- Container is running
- Readiness probe succeeded
- Pod can receive traffic

---

# Important Difference: Running vs Ready

A Pod can be:

```
STATUS = Running
READY  = 0/1
```

Meaning:

- Container is running
- Application is not ready
- Traffic should not be sent to this Pod

Example:

```
Pod
 |
 +-- Container Running
 |
 +-- Application Starting
 |
 +-- Readiness Failed

READY: 0/1
```

---

# Readiness Probe with Service

A Service sends traffic only to Ready Pods.

Example:

```
              Service
                 |
        +--------+--------+
        |                 |
      Pod-1             Pod-2
    READY 1/1         READY 0/1
        |                 |
   Receives traffic   No traffic
```

If Pod-2 becomes ready:

```
              Service
                 |
        +--------+--------+
        |                 |
      Pod-1             Pod-2
    READY 1/1         READY 1/1
        |                 |
   Receives traffic   Receives traffic
```

---

# Readiness Probe Parameters

## initialDelaySeconds

Time Kubernetes waits before starting the first readiness check.

Example:

```yaml
initialDelaySeconds: 5
```

Flow:

```
Container starts

     |
     |
Wait 5 seconds

     |
     |
Run readiness probe
```

---

## periodSeconds

How frequently Kubernetes performs the readiness check.

Example:

```yaml
periodSeconds: 5
```

Meaning:

```
Every 5 seconds
check container readiness
```

---

# Readiness vs Liveness vs Startup Probe

| Probe | Purpose | Failure Action |
|---|---|---|
| Startup Probe | Check if application has started | Wait until startup completes |
| Liveness Probe | Check if application is alive | Restart container |
| Readiness Probe | Check if application can receive traffic | Remove Pod from Service |

---

# Real World Example

Consider an application deployment:

```
             Load Balancer
                  |
               Service
                  |
        +---------+---------+
        |                   |
      Pod-1               Pod-2
```

During startup:

```
Pod-2
 |
 +-- Application starting
 |
 +-- Database connection pending
 |
 +-- Readiness probe failing
```

Kubernetes keeps Pod-2 running but removes it from traffic.

Once ready:

```
Pod-2
 |
 +-- Database connected
 |
 +-- Application ready
 |
 +-- Readiness probe successful
```

Kubernetes adds it back to the Service.

---

# Interview Summary

- Readiness probe checks if a container is ready to accept traffic.
- A failed readiness probe does **not restart the container**.
- Kubernetes removes the Pod from Service endpoints when readiness fails.
- Once readiness succeeds, Kubernetes adds the Pod back.
- Exec readiness probes execute commands inside the container.
- Exit code `0` means the probe succeeded.
- Non-zero exit code means the Pod is not ready.
- Use readiness probes to prevent sending traffic to unhealthy applications.
