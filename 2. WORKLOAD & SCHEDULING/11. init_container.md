# Kubernetes Init Containers

## Documentation

https://kubernetes.io/docs/concepts/workloads/pods/init-containers/

---

# What is an Init Container?

An **Init Container** is a special container that runs **before the main application container starts**.

Its purpose is to perform initialization or preparation tasks that must complete successfully before the application can run.

Think of it as a **preparation container**.

---

# Key Characteristics

Init containers are similar to regular containers, except:

- They **always run to completion**.
- Each init container must complete successfully before the next init container starts.
- The application container starts **only after all init containers have finished successfully**.
- If an init container fails, the **kubelet repeatedly restarts it until it succeeds** (using the Pod's restart policy).

---

# How Init Containers Work

```
Pod Starts
     │
     ▼
+----------------------+
| Init Container #1    |
+----------------------+
     │ Success
     ▼
+----------------------+
| Init Container #2    |
+----------------------+
     │ Success
     ▼
+----------------------+
| Main Application     |
| Container            |
+----------------------+
```

If any init container fails:

```
Pod Starts
     │
     ▼
+----------------------+
| Init Container       |
|       FAILS          |
+----------------------+
     │
     ▼
Kubelet Restarts
Init Container
     │
     ▼
Until Success
```

The application container **never starts** until all init containers complete successfully.

---

# Why Use Init Containers?

Typical initialization tasks include:

- Waiting for a database to become available
- Downloading configuration files
- Creating directories
- Setting file permissions
- Performing health checks
- Registering with external services
- Initializing shared data

# Example 1 - Deployment with Init Container

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  labels:
    app: myapp

spec:
  replicas: 1

  selector:
    matchLabels:
      app: myapp

  template:
    metadata:
      labels:
        app: myapp

    spec:

      containers:
      - name: myapp
        image: alpine:latest

        command:
        - sh
        - -c
        - while true; do echo "logging" >> /opt/logs.txt; sleep 1; done

        volumeMounts:
        - name: data
          mountPath: /opt

      initContainers:
      - name: logshipper
        image: alpine:latest

        command:
        - sh
        - -c
        - tail -F /opt/logs.txt

        volumeMounts:
        - name: data
          mountPath: /opt

      volumes:
      - name: data
        emptyDir: {}
```

Deploy

```bash
kubectl apply -f init.yaml
```

---

# Observe the Pod

```bash
kubectl get pods -w
```

Output

```text
NAME                     READY   STATUS      RESTARTS   AGE
myapp-66c5479b54-n4wfw   0/1     Init:0/1    0          16s
```

Notice the Pod status:

```
Init:0/1
```

This means:

- 0 out of 1 init containers have completed.
- The main application container has **not started yet**.

---

# Modify the Init Container

Suppose you change:

From

```yaml
command:
- sh
- -c
- tail -F /opt/logs.txt
```

To

```yaml
command:
- sh
- -c
- echo "Welcome"
```

The init container prints:

```
Welcome
```

Then exits successfully.

Only after that does the application container start.

# Example 2 - Multiple Init Containers

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod

spec:

  containers:
  - name: app-container
    image: nginx

  initContainers:

  - name: check-google
    image: alpine/curl
    command:
    - ping
    - -c
    - "10"
    - google.com

  - name: check-kubernetes
    image: alpine/curl
    command:
    - curl
    - kubernetes.io
```

Create the Pod

```bash
kubectl apply -f init.yaml
```

---

# Observe the Startup Process

```bash
kubectl get pods -w
```

Example

```text
NAME        READY   STATUS               AGE

myapp-pod   0/1     Init:0/2             8s
myapp-pod   0/1     Init:1/2            11s
myapp-pod   0/1     PodInitializing     12s
myapp-pod   1/1     Running             13s
```

Explanation

```
Init:0/2

First init container is running.
```

↓

```
Init:1/2

First init container completed.
Second init container is running.
```

↓

```
PodInitializing

All init containers completed.
Application container is starting.
```

↓

```
Running

Application container is running.
```

# What Happens if an Init Container Fails?

Suppose you accidentally change:

```yaml
image: alpine/curl
```

to

```yaml
image: alpine/curlxx
```

Deploy again.

```
kubectl get pods -w
```

Output

```text
NAME        READY   STATUS                   RESTARTS

myapp-pod   0/1     Init:0/2                 0
myapp-pod   0/1     Init:1/2                 0
myapp-pod   0/1     Init:RunContainerError   0
myapp-pod   0/1     Init:RunContainerError   1
```

The application container never starts because the init container cannot complete successfully.

The kubelet keeps retrying until the issue is fixed.

# Init Containers vs Regular Containers

| Feature | Init Container | Regular Container |
|----------|---------------|-------------------|
| Runs before application | ✅ | ❌ |
| Runs only once | ✅ | ❌ |
| Must complete successfully | ✅ | ❌ |
| Runs continuously | ❌ | ✅ |
| Executes sequentially | ✅ | ❌ |
| Can block application startup | ✅ | ❌ |

# Common Use Cases

- Wait for a database to become available
- Download application configuration
- Copy startup scripts
- Create required directories
- Set file permissions
- Verify network connectivity
- Perform dependency checks
- Populate shared volumes before the application starts

---

# Summary

- Init Containers run **before** application containers.
- They execute **one at a time** in sequence.
- Every init container must complete successfully before the next one starts.
- The main application starts only after all init containers finish.
- If an init container fails, the kubelet keeps retrying it until it succeeds.
- Init containers are ideal for initialization, setup, and dependency checks before the application starts.
