# Kubernetes LimitRange – Hands-On Lab

## Overview

A Kubernetes **LimitRange** is a policy used to constrain the resource allocations that can be specified for objects in a namespace.

It can control:

* Minimum CPU and memory
* Maximum CPU and memory
* Default CPU and memory limits
* Default CPU and memory requests

A `LimitRange` applies to individual containers or Pods in a namespace.

> **Important:** A `LimitRange` is namespace-scoped. A LimitRange created in one namespace does not affect Pods in another namespace.

---

# 1. Create a Namespace

Create a namespace called `dev`:

```bash
kubectl create namespace dev
```

Check the namespace:

```bash
kubectl get namespace
```

Or:

```bash
kubectl describe namespace dev
```

---

# 2. Create a LimitRange

Create a file called:

```text
lim.yaml
```

Add the following:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: dev-limits
  namespace: dev

spec:
  limits:
  - type: Container

    default:
      cpu: "500m"
      memory: "256Mi"

    defaultRequest:
      cpu: "200m"
      memory: "128Mi"

    max:
      cpu: "1"
      memory: "512Mi"

    min:
      cpu: "100m"
      memory: "64Mi"
```

Apply it:

```bash
kubectl apply -f lim.yaml
```

Expected:

```text
limitrange/dev-limits created
```

---

# 3. Check the LimitRange

List LimitRanges:

```bash
kubectl get limitrange -n dev
```

Expected:

```text
NAME         AGE
dev-limits   ...
```

Describe it:

```bash
kubectl describe limitrange dev-limits -n dev
```

You should see something similar to:

```text
Type        Resource  Min   Max    Default Request  Default Limit
Container   cpu       100m  1      200m             500m
Container   memory    64Mi  512Mi  128Mi            256Mi
```

---

# 4. Understand the Policy

Our LimitRange defines the following:

| Resource | Minimum | Maximum | Default Request | Default Limit |
| -------- | ------: | ------: | --------------: | ------------: |
| CPU      |    100m |   1 CPU |            200m |          500m |
| Memory   |    64Mi |   512Mi |           128Mi |         256Mi |

### CPU values

```text
100m = 0.1 CPU
200m = 0.2 CPU
500m = 0.5 CPU
1000m = 1 CPU
```

Therefore:

```text
Minimum CPU = 100m
Default Request = 200m
Default Limit = 500m
Maximum CPU = 1
```

# 5. Create a Pod Without Resources

This is one of the most useful tests.

Create:

```text
pod.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
  namespace: dev

spec:
  containers:
  - name: nginx
    image: nginx
```

Notice that there is **no**:

```yaml
resources:
```

section.

Apply it:

```bash
kubectl apply -f pod.yaml
```

Expected:

```text
pod/nginx created
```

Check the Pod:

```bash
kubectl get pod nginx -n dev
```

Now describe it:

```bash
kubectl describe pod nginx -n dev
```

Look under the container.

You should see:

```text
Limits:
  cpu:     500m
  memory:  256Mi

Requests:
  cpu:     200m
  memory:  128Mi
```

## Why?

The Pod did not specify any resources.

The `LimitRange` automatically supplied the defaults:

```text
default:
  cpu: 500m
  memory: 256Mi

defaultRequest:
  cpu: 200m
  memory: 128Mi
```

Therefore:

```text
Pod YAML
   |
   | No resources specified
   ↓
LimitRange
   |
   +---- Default Request
   |       CPU: 200m
   |       Memory: 128Mi
   |
   +---- Default Limit
           CPU: 500m
           Memory: 256Mi
```

# 6. Create a Pod Above the Maximum

Now we deliberately violate the LimitRange.

Create:

```text
bad-pod.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: bad-pod
  namespace: dev

spec:
  containers:
  - name: nginx
    image: nginx

    resources:
      requests:
        cpu: "200m"
        memory: "128Mi"

      limits:
        cpu: "2"
        memory: "1Gi"
```

The LimitRange allows:

```text
Maximum CPU    = 1
Maximum Memory = 512Mi
```

But our Pod requests:

```text
CPU    = 2
Memory = 1Gi
```

Both are above the maximum.

Try:

```bash
kubectl apply -f bad-pod.yaml
```

Expected result:

```text
Error from server (Forbidden)
```

You may see an error similar to:

```text
pods "bad-pod" is forbidden:
maximum cpu usage per Container is 1, but limit is 2
```

The exact error may vary depending on which violation Kubernetes reports first.

Check:

```bash
kubectl get pods -n dev
```

The Pod should not have been created.

# 7. Create a Pod Below the Minimum

Now test the opposite situation.

Create:

```text
too-small.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: too-small
  namespace: dev

spec:
  containers:
  - name: nginx
    image: nginx

    resources:
      requests:
        cpu: "50m"
        memory: "32Mi"

      limits:
        cpu: "100m"
        memory: "64Mi"
```

Our minimum values are:

```text
CPU    = 100m
Memory = 64Mi
```

But the requests are:

```text
CPU    = 50m
Memory = 32Mi
```

Therefore the requests are below the minimum.

Try:

```bash
kubectl apply -f too-small.yaml
```

The Pod should be rejected.

You should get an error similar to:

```text
Error from server (Forbidden)
```

# 8. Create a Valid Pod

Now create a Pod that satisfies the policy.

Create:

```text
good-pod.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: good-pod
  namespace: dev

spec:
  containers:
  - name: nginx
    image: nginx

    resources:
      requests:
        cpu: "300m"
        memory: "200Mi"

      limits:
        cpu: "500m"
        memory: "256Mi"
```

Apply:

```bash
kubectl apply -f good-pod.yaml
```

Expected:

```text
pod/good-pod created
```

Check:

```bash
kubectl get pods -n dev
```

You should see:

```text
NAME        READY   STATUS    RESTARTS   AGE
nginx       1/1     Running   0          ...
good-pod    1/1     Running   0          ...
```

---

# 9. Why Is `good-pod` Valid?

Our policy says:

```text
CPU:
Minimum = 100m
Maximum = 1

Memory:
Minimum = 64Mi
Maximum = 512Mi
```

The Pod specifies:

```text
CPU Request = 300m
CPU Limit   = 500m

Memory Request = 200Mi
Memory Limit   = 256Mi
```

Therefore:

```text
100m <= 300m <= 500m <= 1 CPU

64Mi <= 200Mi <= 256Mi <= 512Mi
```

Everything is within the allowed range.

# 12. LimitRange and Deployments

A LimitRange also affects Pods created by a Deployment.

For example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: dev

spec:
  replicas: 1

  selector:
    matchLabels:
      app: my-app

  template:
    metadata:
      labels:
        app: my-app

    spec:
      containers:
      - name: my-app
        image: nginx

        resources:
          requests:
            cpu: "200m"
            memory: "128Mi"

          limits:
            cpu: "500m"
            memory: "256Mi"
```

Apply:

```bash
kubectl apply -f my-app.yaml
```

The Deployment creates a ReplicaSet, which creates a Pod.

The LimitRange in `dev` applies to the resulting Pod.

Check:

```bash
kubectl get deployment -n dev
kubectl get replicaset -n dev
kubectl get pods -n dev
```

# 13. Important Distinction: LimitRange vs ResourceQuota

This is an important Kubernetes interview and certification topic.

## LimitRange

Controls resources for **individual containers/Pods**.

Example:

```text
One container cannot exceed:

CPU    = 1
Memory = 512Mi
```

Think:

```text
LimitRange
     |
     ↓
Individual Container
     |
     └── "How much can THIS container request/use?"
```

---

## ResourceQuota

Controls the **total amount of resources consumed by a namespace**.

For example:

```text
Namespace:
    Maximum CPU    = 10
    Maximum Memory = 20Gi
    Maximum Pods   = 20
```

Think:

```text
ResourceQuota
       |
       ↓
   Namespace
       |
       +---- Pod 1
       +---- Pod 2
       +---- Pod 3
       +---- Pod 4
       |
       └── Total resources cannot exceed quota
```

---

# 14. LimitRange vs ResourceQuota

| Feature                         | LimitRange                 | ResourceQuota             |
| ------------------------------- | -------------------------- | ------------------------- |
| Scope                           | Namespace                  | Namespace                 |
| Controls                        | Individual containers/Pods | Total namespace resources |
| Minimum resources               | Yes                        | No                        |
| Maximum resources per container | Yes                        | No                        |
| Default requests                | Yes                        | No                        |
| Default limits                  | Yes                        | No                        |
| Total CPU quota                 | No                         | Yes                       |
| Total memory quota              | No                         | Yes                       |
| Maximum number of Pods          | No                         | Yes                       |

# 17. Key Takeaways

### 1. LimitRange is namespace-scoped

```text
dev LimitRange
      ↓
Only affects objects in dev
```

It does not affect `test`.

---

### 2. LimitRange can provide defaults

If a container doesn't specify resources:

```yaml
resources:
```

the LimitRange can automatically provide:

```text
requests
limits
```

---

### 3. LimitRange can enforce minimums

A container cannot specify less than:

```text
CPU    = 100m
Memory = 64Mi
```

---

### 4. LimitRange can enforce maximums

A container cannot specify more than:

```text
CPU    = 1
Memory = 512Mi
```

---

### 5. LimitRange is not ResourceQuota

Remember:

```text
LimitRange
    =
Individual container/Pod limits and defaults


ResourceQuota
    =
Total namespace resource consumption
```

# 18. Quick Interview Question

**Q: What happens if I create a Pod without CPU and memory requests/limits in a namespace that has a LimitRange?**

**Answer:**

If the LimitRange defines `default` and `defaultRequest` values, Kubernetes automatically applies those values to the container.

For example:

```yaml
default:
  cpu: "500m"

defaultRequest:
  cpu: "200m"
```

A Pod with no resource configuration can therefore end up with:

```text
Request = 200m
Limit   = 500m
```

# 19. Quick Exam Reminder

Remember these four fields:

```yaml
spec:
  limits:
  - type: Container

    min:
      ...

    max:
      ...

    default:
      ...

    defaultRequest:
      ...
```

### `min`

Smallest allowed value.

### `max`

Largest allowed value.

### `default`

Default **limit**.

### `defaultRequest`

Default **request**.

The easiest way to remember:

```text
min             → minimum allowed
max             → maximum allowed
default         → default LIMIT
defaultRequest  → default REQUEST
```
