## Documentation

https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/

---

# What is the Sidecar Pattern?

The **Sidecar Pattern** is a **multi-container Pod pattern** where a secondary container runs alongside the main application container.

The sidecar container extends or enhances the functionality of the primary application **without modifying the application code**.

Both containers:

- Run inside the same Pod
- Share the same network namespace (same IP)
- Can communicate using `localhost`
- Can share storage using Volumes

---

# Real World Example

Imagine a bank application.

```
               Kubernetes Pod
+------------------------------------------------+
|                                                |
|   Main Application Container                   |
|   --------------------------                   |
|   Banking Application                          |
|                                                |
|   Writes logs to /opt/logs.txt                 |
|                                                |
|                │                               |
|                │ Shared Volume                 |
|                ▼                               |
|         emptyDir Volume                        |
|                ▲                               |
|                │                               |
|   Sidecar Container                            |
|   --------------------------                   |
|   Log Shipper                                  |
|   Reads logs                                   |
|   Sends logs to monitoring system              |
|                                                |
+------------------------------------------------+
```

The application only focuses on business logic.

The sidecar handles additional responsibilities like logging or monitoring.

# Why use a Sidecar?

Without a Sidecar:

```
Application
    │
    ├── Business Logic
    ├── Logging
    ├── Monitoring
    ├── Metrics
    └── Security
```

The application becomes large and difficult to maintain.

With a Sidecar:

```
Application
    │
    └── Business Logic

Sidecar
    ├── Logging
    ├── Monitoring
    ├── Metrics
    └── Security
```

The responsibilities are separated, making the application cleaner and easier to maintain.

# Types of Sidecar Patterns

## 1. Ambassador Pattern

A special type of Sidecar where the secondary container acts as a **proxy**.

It forwards requests between the application and external services.

Example:

```
Application
      │
      ▼
Ambassador Sidecar
      │
      ▼
Database / External Service
```

Typical use cases:

- Reverse proxy
- API Gateway
- Service Mesh
- TLS termination

---

## 2. Adapter Pattern

The Adapter sidecar transforms application output into a standard format.

Example:

```
Application Logs
        │
        ▼
Adapter Sidecar
        │
Transforms Logs
        │
        ▼
Monitoring Platform
```

Typical use cases:

- Log normalization
- Metrics conversion
- Format transformation
- Data aggregation

# Example Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  labels:
    app: myapp

spec:
  replicas: 1

  selector:
    matchLabels:
      app: myapp

  template:
    metadata:
      labels:
        app: myapp

    spec:

      containers:
      - name: myapp
        image: alpine:latest

        command:
        - sh
        - -c
        - while true; do echo "logging" >> /opt/logs.txt; sleep 1; done

        volumeMounts:
        - name: data
          mountPath: /opt

      initContainers:
      - name: logshipper
        image: alpine:latest

        # restartPolicy: Always makes this an Init Sidecar
        restartPolicy: Always

        command:
        - sh
        - -c
        - tail -F /opt/logs.txt

        volumeMounts:
        - name: data
          mountPath: /opt

      volumes:
      - name: data
        emptyDir: {}
```

# Describe the Pod

```bash
kubectl describe pod <pod-name>
```

Example

```bash
kubectl describe pod myapp-68bdc564bb-7drlr
```

You will notice two containers:

```
Init Containers

logshipper
```

and

```
Containers

myapp
```

The **logshipper** is defined as an init container with:

```yaml
restartPolicy: Always
```

This makes it behave as a **Sidecar Container**, so it continues running alongside the main application after initialization.

---

# Shared Volume

Both containers mount the same volume.

```
Volume

emptyDir
```

Mounted as

```
/opt
```

The application writes logs:

```
/opt/logs.txt
```

The sidecar continuously reads the same file.

---

# How it Works

```
Main Container

echo "logging" >> /opt/logs.txt
        │
        ▼
----------------------------
Shared emptyDir Volume
----------------------------
        ▲
        │
tail -F /opt/logs.txt
        │
        ▼
Sidecar Container
```

The main container keeps generating logs.

The sidecar continuously monitors the same file and can ship the logs to an external logging system.

# Useful Commands

Deploy

```bash
kubectl apply -f side.yaml
```

View Pods

```bash
kubectl get pods
```

Describe Pod

```bash
kubectl describe pod <pod-name>
```

View logs from the main container

```bash
kubectl logs <pod-name> -c myapp
```

View logs from the sidecar container

```bash
kubectl logs <pod-name> -c logshipper
```

Open a shell inside the main container

```bash
kubectl exec -it <pod-name> -c myapp -- sh
```

Open a shell inside the sidecar container

```bash
kubectl exec -it <pod-name> -c logshipper -- sh
```

Delete the deployment

```bash
kubectl delete -f side.yaml
```

# Advantages of Sidecar Pattern

| Advantage | Description |
|------------|-------------|
| Separation of concerns | Keeps business logic separate from logging, monitoring, and security. |
| Reusable | The same sidecar can be reused across multiple applications. |
| Shared resources | Containers share storage and networking inside the Pod. |
| Easy maintenance | Update the sidecar independently without changing application code. |
| Better observability | Simplifies logging, monitoring, and metrics collection. |

---

# Summary

- Sidecar is a **multi-container Pod pattern**.
- It runs alongside the main application container.
- Both containers share the same network and storage.
- Sidecars are commonly used for logging, monitoring, security, metrics, and service mesh.
- **Ambassador Pattern** acts as a proxy for external communication.
- **Adapter Pattern** transforms application output into a standard format.
- In Kubernetes, an init container with `restartPolicy: Always` behaves as a **Sidecar Container** and continues running with the main application.
