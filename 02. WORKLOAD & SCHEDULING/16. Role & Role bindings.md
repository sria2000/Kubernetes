# Kubernetes RBAC — User, Role and RoleBinding

## Overview

This guide demonstrates how to:

1. Create a Kubernetes test user called `developer`
2. Create a namespace
3. Create a `Role`
4. Create a `RoleBinding`
5. Configure `kubectl` for the user
6. Test the user's permissions
7. Verify what the user can and cannot do

The final RBAC structure will be:

```text
                    Kubernetes Cluster
                           |
                           |
                     User: developer
                           |
                           v
                    RoleBinding
                           |
                           v
                    Role: developer-role
                           |
              +------------+------------+
              |            |            |
              v            v            v
          get pods     list pods    delete pods
              |
              v
       development namespace
```

---

# 1. Kubernetes RBAC Concepts

RBAC stands for:

```text
Role-Based Access Control
```

The main objects are:

| Object               | Purpose                                        |
| -------------------- | ---------------------------------------------- |
| `Role`               | Defines permissions inside a namespace         |
| `RoleBinding`        | Assigns a Role to a user/group/service account |
| `ClusterRole`        | Defines cluster-level permissions              |
| `ClusterRoleBinding` | Assigns cluster-level permissions              |

A simple way to remember:

```text
Role
  = What can the user do?

RoleBinding
  = Who gets those permissions?
```

For example:

```text
Role
 |
 +-- get pods
 +-- list pods
 +-- create pods
 +-- delete pods
```

Then:

```text
RoleBinding
 |
 +-- developer
```

Therefore:

```text
developer
    |
    +--> developer-role
             |
             +--> get pods
             +--> list pods
             +--> create pods
             +--> delete pods
```

# 4. Create a Kubernetes User

## Important

Kubernetes does not normally have a command such as:

```bash
kubectl create user developer
```

Kubernetes users are authenticated using mechanisms such as:

* Client certificates
* OIDC
* External identity providers
* Cloud IAM integrations
* Other authentication mechanisms

For this lab, we will use a **client certificate**.

---

# 5. Create the User's Private Key

Create a private key for the user:

```bash
openssl genrsa -out developer.key 2048
```

Check:

```bash
ls -l developer.key
```

You should have:

```text
developer.key
```

Keep this file private.

---

# 6. Create a Certificate Signing Request

Create a CSR:

```bash
openssl req -new \
  -key developer.key \
  -out developer.csr \
  -subj "/CN=developer/O=developers"
```

The important part is:

```text
CN=developer
```

Kubernetes will identify the authenticated user as:

```text
developer
```

The organisation is:

```text
developers
```

So:

```text
CN = username
O  = group
```

---

# 7. Find the Kubernetes CA

If you are using a `kubeadm` cluster, the Kubernetes CA files are normally:

```text
/etc/kubernetes/pki/ca.crt
/etc/kubernetes/pki/ca.key
```

Check:

```bash
ls -l /etc/kubernetes/pki/ca.*
```

You should see:

```text
ca.crt
ca.key
```

> **Important:** The CA private key (`ca.key`) is extremely sensitive. Do not expose or distribute it.

If you are using another Kubernetes installation such as Kind, Minikube, EKS, AKS or GKE, the certificate process can be different.

---

# 8. Sign the Developer Certificate

For a kubeadm cluster:

```bash
openssl x509 -req \
  -in developer.csr \
  -CA /etc/kubernetes/pki/ca.crt \
  -CAkey /etc/kubernetes/pki/ca.key \
  -CAcreateserial \
  -out developer.crt \
  -days 365
```

You should now have:

```text
developer.key
developer.csr
developer.crt
```

The files are:

| File            | Purpose                     |
| --------------- | --------------------------- |
| `developer.key` | User's private key          |
| `developer.csr` | Certificate Signing Request |
| `developer.crt` | Signed user certificate     |

The CSR is no longer required after the certificate has been created.

# 9. Create the Role

Create a file:

```text
developer-role.yaml
```

Contents:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer-role
  namespace: development

rules:
- apiGroups: [""]
  resources:
  - pods
  verbs:
  - get
  - list
  - watch
  - create
  - delete
```

This Role gives the user permission to:

```text
get pods
list pods
watch pods
create pods
delete pods
```

Only in:

```text
development
```

namespace.

# 12. Create the RoleBinding

The Role defines permissions, but it does not give those permissions to anyone.

We need a `RoleBinding`.

Create:

```text
developer-rolebinding.yaml
```

Contents:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-rolebinding
  namespace: development

subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io

roleRef:
  kind: Role
  name: developer-role
  apiGroup: rbac.authorization.k8s.io
```

The important section is:

```yaml
subjects:
- kind: User
  name: developer
```

This says:

```text
Give permissions to user developer
```

The `roleRef` says:

```yaml
roleRef:
  kind: Role
  name: developer-role
```

which means:

```text
Use the developer-role permissions
```

# 24. Test Another Namespace

Our Role exists only in:

```text
development
```

Create another namespace:

```bash
kubectl create namespace testing
```

Now try:

```bash
kubectl auth can-i get pods -n testing
```

Expected:

```text
no
```

Why?

Because:

```text
developer-role
```

is defined in:

```text
development
```

not:

```text
testing
```

This demonstrates that a `Role` is **namespace-scoped**.

---

# 25. Important Difference: Role vs ClusterRole

A `Role` is namespace-scoped.

```text
Role
 |
 +--> development namespace
```

A `ClusterRole` is cluster-scoped.

```text
ClusterRole
 |
 +--> entire Kubernetes cluster
```

For example:

```text
Role
 └── Can access Pods in development

ClusterRole
 └── Can define permissions across the cluster
```

# 30. Important: `--as` vs Real Authentication

There is an important distinction.

This:

```bash
kubectl auth can-i get pods --as=developer
```

does **not** authenticate you as the developer.

It asks Kubernetes:

> "Would the user named `developer` be allowed to perform this action?"

The certificate configuration:

```bash
kubectl config set-credentials developer \
  --client-certificate=developer.crt \
  --client-key=developer.key
```

is what allows you to actually authenticate using the developer certificate.

```bash
kubectl config delete-context developer-context
```

```bash
kubectl config delete-user developer
```

```bash
rm -f developer.key

rm -f developer.crt
rm -f developer.csr
```

# 33. Interview Summary

### What is a Role?

A `Role` defines permissions within a namespace.

Example:

```yaml
kind: Role
metadata:
  namespace: development
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list"]
```

---

### What is a RoleBinding?

A `RoleBinding` assigns a Role to a user, group, or ServiceAccount.

```yaml
kind: RoleBinding
subjects:
- kind: User
  name: developer

roleRef:
  kind: Role
  name: developer-role
```

---

### What is the difference?

```text
Role
=
WHAT can be done?
```

```text
RoleBinding
=
WHO can do it?
```

---

### Role vs ClusterRole

```text
Role
    |
    +-- Namespace scoped

ClusterRole
    |
    +-- Cluster scoped
```

---

### RoleBinding vs ClusterRoleBinding

```text
RoleBinding
    |
    +-- Grants permissions within a namespace

ClusterRoleBinding
    |
    +-- Grants ClusterRole permissions across the cluster
```
