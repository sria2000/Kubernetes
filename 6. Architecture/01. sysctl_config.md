# sysctl — Managing Kernel Parameters in Linux

## 1. What is sysctl?

`sysctl` is the standard utility for interacting with kernel parameters exposed via `/proc/sys`.

It provides a more convenient interface than directly manipulating files under `/proc/sys` — same underlying mechanism, but with read/write/persist conveniences built in (naming convention, validation, bulk-load from config files).

> 📌 **Tip:** `/proc/sys` is a live view into the running kernel's tunables. Every file under it corresponds to a `sysctl` parameter — `sysctl` and direct file access are two doors into the exact same data, not two separate systems.

---

## 2. Understanding the Structure

`/proc/sys` is organized hierarchically by subsystem (`net`, `vm`, `kernel`, `fs`, etc.), and `sysctl` parameter names map directly onto that directory path using dots instead of slashes.

```bash
ls -l /proc/sys
ls -l /proc/sys/net
ls -l /proc/sys/net/ipv4
cat /proc/sys/net/ipv4/ip_forward
```

> 📌 **Tip:** The mapping is mechanical — `/proc/sys/net/ipv4/ip_forward` **is** `net.ipv4.ip_forward` as a sysctl name. Once you see the pattern, you can predict the file path for any sysctl parameter name and vice versa.

---

## 3. Modifying Parameters (Runtime — Non-Persistent)

### Read a value two ways
```bash
sysctl vm.swappiness
cat /proc/sys/vm/swappiness
```
Both return the same value — confirming they're the same underlying setting.

### Write a value two ways

**Direct file write:**
```bash
echo 70 > /proc/sys/vm/swappiness
sysctl vm.swappiness      # confirms it changed to 70
```

**Using sysctl directly:**
```bash
sysctl vm.swappiness=80
sysctl vm.swappiness      # confirms it changed to 80
```

> 📌 **Tip:** `sysctl -w vm.swappiness=80` and `sysctl vm.swappiness=80` are equivalent — the `-w` (write) flag is implied when you pass a `key=value` pair.

### These changes do NOT survive a reboot
```bash
reboot
sysctl vm.swappiness    # back to the original/default value
```

> 📌 **Tip:** This is the single most common mistake with `sysctl` — testing a tuning change live with `echo` or `sysctl key=value`, confirming it works, then forgetting it silently reverts on the next reboot or kernel restart. Always follow up a working runtime change with the permanent step below.

---

## 4. Making Changes Permanent

To ensure your kernel parameter changes survive a reboot, **you need to store them in configuration files** that the system reads during boot.

| Configuration Files | Description |
|---|---|
| `/etc/sysctl.conf` | The traditional main configuration file. You can add your parameter settings here. |
| `/etc/sysctl.d/*.conf` | The modern, preferred approach. You should place your custom settings in a file here, typically named something like `99-custom.conf` |

### Steps

```bash
cd /etc/sysctl.d
vi 99-custom.conf
```

Add the following line to the file:
```
vm.swappiness=70
```

Load the config without rebooting:
```bash
sysctl --system
```

Verify persistence:
```bash
reboot
sysctl vm.swappiness    # should now show 70 after reboot
```

> 📌 **Tip:** `sysctl --system` reads and applies **every** file under `/etc/sysctl.d/*.conf`, plus `/etc/sysctl.conf` and a few other legacy locations, in a defined precedence order — it's the same mechanism the system uses automatically at boot, so running it manually is a safe way to test your permanent config takes effect without actually rebooting.

---

## 5. Additional Tips & Gotchas

- **Naming convention:** using a numbered prefix like `99-custom.conf` in `/etc/sysctl.d/` isn't just cosmetic — files are applied in lexical order, and a later file's setting for the same key overrides an earlier one. `99-` is a common convention to ensure your custom overrides apply last, after any vendor/distro defaults.
- **Precedence order** (later wins) when `sysctl --system` runs: `/etc/sysctl.d/*.conf` → `/run/sysctl.d/*.conf` → `/usr/lib/sysctl.d/*.conf` → `/etc/sysctl.conf` (exact order can vary slightly by distro — check `man sysctl.d` on the specific system).
- **Don't hand-edit `/etc/sysctl.conf` on modern distros** if you can avoid it — mixing your custom settings into the same file as distro-managed defaults makes upgrades and audits harder. Dropping a single well-named file into `/etc/sysctl.d/` is cleaner and easier to track in config management (Ansible, Puppet, etc.) or version control.
- **Common parameters worth knowing for interviews/hardening work:**
  - `net.ipv4.ip_forward` — enables IP forwarding (routing); required on any node acting as a router, VPN gateway, or Kubernetes node using certain CNI setups.
  - `vm.swappiness` — how aggressively the kernel swaps; frequently tuned down (or to `0`/`1`) on Kubernetes nodes and databases to avoid unwanted swapping under memory pressure.
  - `kernel.panic` — seconds to wait before auto-rebooting after a kernel panic; commonly set on production servers to avoid a wedged node needing manual intervention.
  - `net.ipv4.tcp_syncookies` — SYN flood protection, frequently checked in security hardening audits (CIS/STIG benchmarks).
  - `fs.file-max` — system-wide max open file handles; a classic tuning knob for high-connection-count services.
- **CIS/STIG relevance:** hardening benchmarks (CIS Benchmarks, DISA STIGs) reference dozens of specific `sysctl` parameters by name — expect these to show up directly in RHEL hardening audits via tools like OpenSCAP, which check the live `/proc/sys` value against the benchmark's required value.
- **Namespaced parameters:** some `sysctl` parameters are per-network-namespace (most of `net.*`) rather than truly global — this matters in container/Kubernetes contexts, where a Pod's network namespace can have its own value for something like `net.ipv4.ip_forward` independent of the host, and certain sysctls can only be set at the Pod level if explicitly allowlisted by the container runtime/kubelet (`securityContext.sysctls`).

## Quick Reference — Commands Used

```bash
ls -l /proc/sys/<path>                    # explore parameter structure
cat /proc/sys/<path>/<parameter>          # read a value directly via file
sysctl <parameter>                        # read a value via sysctl
sysctl <parameter>=<value>                # set a value at runtime (non-persistent)
echo <value> > /proc/sys/<path>/<param>   # set a value directly via file (non-persistent)
vi /etc/sysctl.d/99-custom.conf           # create a permanent config file
sysctl --system                           # apply all sysctl.d/sysctl.conf files immediately
```
