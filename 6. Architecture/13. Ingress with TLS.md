# Ingress with TLS (HTTPS)

**Purpose:** Ensures secure communication between client and server. TLS is terminated at the Ingress controller — traffic is encrypted client → ingress, and the controller forwards plain HTTP internally to the service.

Tested end-to-end on a Killercoda Kubernetes playground.

## 1. Install NGINX Ingress Controller

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.2/deploy/static/provider/cloud/deploy.yaml
```

Check the pods:

```bash
kubectl get pods -n ingress-nginx
```

```
NAME                                        READY   STATUS      RESTARTS   AGE
ingress-nginx-admission-create-s9nrr        0/1     Completed   0          42s
ingress-nginx-admission-patch-gv5kk         0/1     Completed   1          42s
ingress-nginx-controller-6c74fdc586-g8zrq   1/1     Running     0          42s
```

> `admission-create` and `admission-patch` are one-shot **Jobs** that set up the admission webhook's TLS cert and are expected to show `Completed`, not `Running`. Only the `ingress-nginx-controller` pod needs to be `1/1 Running`.

Confirm the ingress class registered:

```bash
kubectl get ingressclass
```

You should see `nginx` listed.

## 2. Create a Self-Signed TLS Certificate

```bash
openssl req -x509 -nodes -days 365 \
  -newkey rsa:2048 \
  -keyout tls.key -out tls.crt \
  -subj "/CN=myapp.example.com/O=myapp"
```

## 3. Create a TLS Secret from the Cert

```bash
kubectl create secret tls myapp-tls --cert=tls.crt --key=tls.key
kubectl get secret myapp-tls
```

## 4. Deploy a Test App + Service

```yaml
# app.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: nginx
        image: nginx
---
apiVersion: v1
kind: Service
metadata:
  name: myapp-svc
spec:
  selector:
    app: myapp
  ports:
  - port: 80
    targetPort: 80
```

```bash
kubectl apply -f app.yaml
```

## 5. Create the Ingress with TLS

```yaml
# ingress-tls.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - myapp.example.com
    secretName: myapp-tls
  rules:
  - host: myapp.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: myapp-svc
            port:
              number: 80
```

```bash
kubectl apply -f ingress-tls.yaml
kubectl get ingress
```

## 6. Find the Node Port and Node IP

Check the ingress controller's service:

```bash
kubectl get svc -n ingress-nginx
```

```
NAME                                 TYPE           CLUSTER-IP       EXTERNAL-IP   PORT(S)                      AGE
ingress-nginx-controller             LoadBalancer   10.105.232.223   <pending>     80:32317/TCP,443:31189/TCP   4m12s
ingress-nginx-controller-admission   ClusterIP      10.107.145.252   <none>        443/TCP                      4m12s
```

> `EXTERNAL-IP` shows `<pending>` in Killercoda since there's no cloud load balancer provisioner — use a node's `INTERNAL-IP` + the NodePort instead (NodePort exposes the service on every node).

Grab just the HTTPS NodePort (the `443:XXXXX` mapping):

```bash
kubectl get svc -n ingress-nginx ingress-nginx-controller -o jsonpath='{.spec.ports[?(@.port==443)].nodePort}'
```

Get a node's internal IP:

```bash
kubectl get nodes -o wide
```

```
NAME           STATUS   ROLES           AGE   VERSION   INTERNAL-IP   EXTERNAL-IP   OS-IMAGE             KERNEL-VERSION      CONTAINER-RUNTIME
controlplane   Ready    control-plane   11d   v1.35.1   172.30.1.2    <none>        Ubuntu 24.04.4 LTS   6.8.0-136-generic   containerd://2.2.1
node01         Ready    <none>          11d   v1.35.1   172.30.2.2    <none>        Ubuntu 24.04.4 LTS   6.8.0-136-generic   containerd://2.2.1
```

## 7. Test It

```bash
curl -k --resolve myapp.example.com:31189:172.30.2.2 https://myapp.example.com:31189
```

- `-k` skips cert validation (expected — the cert is self-signed).
- `--resolve` fakes DNS so `myapp.example.com` maps to the cluster node, without editing `/etc/hosts`.
- A successful response returns the default nginx welcome page, served over HTTPS.

> Common mistake: forgetting the space between the port and `https://` in the command — e.g. `...31189https://...` gets parsed as one garbled argument and curl errors with `no URL specified`.

If it doesn't return the page, check the Ingress resource itself:

```bash
kubectl get ingress myapp-ingress -o wide
kubectl describe ingress myapp-ingress
```
