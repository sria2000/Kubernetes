# Kubernetes StorageClass

## Overview

A **StorageClass** defines **how Kubernetes dynamically provisions Persistent Volumes (PV)**.

Instead of an administrator manually creating Persistent Volumes, a StorageClass allows Kubernetes to automatically create storage whenever a PersistentVolumeClaim (PVC) is created.

The StorageClass specifies the storage provisioner (plugin or CSI driver), reclaim policy, volume binding mode, and other storage parameters.

Documentation:

https://kubernetes.io/docs/concepts/storage/storage-classes/

---

# Storage Flow

```
Application
     │
     ▼
PersistentVolumeClaim (PVC)
     │
     ▼
StorageClass
     │
     ▼
Provisioner / CSI Driver
     │
     ▼
Persistent Volume (PV)
     │
     ▼
Physical Storage
```

---

# Why Use StorageClasses?

Without a StorageClass:

- Administrator must manually create Persistent Volumes.
- Developers wait until matching PVs are available.
- Storage management becomes difficult.

With a StorageClass:

- PVs are created automatically.
- No manual intervention required.
- Storage is provisioned only when needed.

---

# Components of a StorageClass

A StorageClass typically defines:

- Provisioner (CSI Driver)
- Reclaim Policy
- Volume Binding Mode
- Allow Volume Expansion
- Storage Parameters

# Volume Binding Modes

## Immediate

The Persistent Volume is created immediately after the PVC is created.

```
PVC Created
      │
      ▼
PV Created Immediately
```

---

## WaitForFirstConsumer

The Persistent Volume is created only after a Pod using the PVC is scheduled.

```
PVC Created
      │
      ▼
Waiting...
      │
      ▼
Pod Scheduled
      │
      ▼
PV Created
```

This helps Kubernetes provision storage on the correct node or availability zone.

---

# Example PVC Using a StorageClass

```yaml
apiVersion: v1
kind: PersistentVolumeClaim

metadata:
  name: csi-pvc

spec:
  storageClassName: do-block-storage

  accessModes:
  - ReadWriteOnce

  resources:
    requests:
      storage: 1Gi
```

Create the PVC

```bash
kubectl apply -f pvc.yaml
```

Verify

```bash
kubectl get pvc

kubectl get pv
```

Notice that Kubernetes automatically creates and binds a Persistent Volume.

---

# Create a Pod Using the PVC

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: test-pod

spec:
  containers:
  - name: volume-test
    image: nginx

    volumeMounts:
    - name: local-path
      mountPath: /data

  volumes:
  - name: local-path
    persistentVolumeClaim:
      claimName: csi-pvc
```

Deploy

```bash
kubectl apply -f test-pod.yaml
```

Verify

```bash
kubectl get pods
```

# Reclaim Policy

The **Reclaim Policy** determines what happens to the Persistent Volume after its PVC is deleted.

There are two commonly used policies:

| Policy | Description |
|----------|-------------|
| Delete | Deletes both the Persistent Volume and the underlying storage. |
| Retain | Keeps the Persistent Volume and underlying storage after the PVC is deleted. Manual cleanup is required. |

# Persistent Volume Access Modes

Access Modes define **how a Persistent Volume can be mounted by Pods.**

| Access Mode | Abbreviation | Description |
|-------------|--------------|-------------|
| ReadWriteOnce | RWO | Read-write by Pods on a single node. |
| ReadOnlyMany | ROX | Read-only by multiple nodes. |
| ReadWriteMany | RWX | Read-write by multiple nodes. |
| ReadWriteOncePod | RWOP | Read-write by only one Pod. |

---

# StorageClass Summary

- A **StorageClass** defines how Kubernetes dynamically provisions Persistent Volumes.
- It eliminates the need for administrators to manually create Persistent Volumes.
- StorageClasses specify the provisioner, reclaim policy, and volume binding mode.
- The **Reclaim Policy** controls what happens to storage after a PVC is deleted.
- Access Modes determine how Persistent Volumes can be mounted by Pods and nodes.
- Dynamic provisioning using StorageClasses is the recommended approach for production Kubernetes environments.
