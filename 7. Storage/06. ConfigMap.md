# Kubernetes ConfigMaps

## Overview

Applications often need configuration information such as database hostnames, ports, application modes, feature flags, and API endpoints.

Hardcoding configuration values inside container images is not recommended because changing a configuration would require rebuilding and redeploying the application.

A **ConfigMap** is a Kubernetes object used to store **non-sensitive configuration data** as **key-value pairs**.

> **Note:** ConfigMaps should only be used for **non-sensitive data**. Sensitive information such as passwords, API keys, or certificates should be stored in **Secrets**.

Documentation:

- https://kubernetes.io/docs/concepts/configuration/configmap/

---

# Benefits of ConfigMaps

- Store application configuration separately from code
- Avoid rebuilding container images for configuration changes
- Reuse the same container image across multiple environments
- Share configuration across multiple Pods
- Mount configuration as files or environment variables

---

# Creating ConfigMaps

## Method 1 - Create from Literal Values

View available options

```bash
kubectl create configmap --help
```

Create a ConfigMap

```bash
kubectl create configmap first-configmap \
--from-literal=key1=value1 \
--from-literal=key2=value2
```

Verify

```bash
kubectl describe configmap first-configmap
```

Example Output

```text
Name: first-configmap

Data
====
key1:
----
value1

key2:
----
value2
```

List ConfigMaps

```bash
kubectl get configmap
```

Example Output

```text
NAME               DATA   AGE
first-configmap    2      30s
kube-root-ca.crt   1      11d
```

View YAML

```bash
kubectl get configmap first-configmap -o yaml
```

Example Output

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: first-configmap

data:
  key1: value1
  key2: value2
```

# Method 2 - Create from a File

Create a file

```text
large-file.txt

key1=value1
key2=value2
key3=value3
```

Create ConfigMap

```bash
kubectl create configmap second-configmap --from-file=large-file.txt
```

Verify

```bash
kubectl get configmap second-configmap -o yaml
```

Example Output

```yaml
apiVersion: v1
kind: ConfigMap

data:
  large-file.txt: |
    key1=value1
    key2=value2
    key3=value3
```

# Method 4 - Create Using a YAML Manifest

Create the manifest

```yaml
apiVersion: v1
kind: ConfigMap

metadata:
  name: manifest-configmap

data:
  key1: "value1"
  key2: "value2"

  big-data: |
    This is Line 1
    This is Line 2
    This is Line 3
```

Deploy

```bash
kubectl apply -f configmap.yaml
```

Verify

```bash
kubectl get configmap manifest-configmap -o yaml
```


# Using ConfigMaps in Pods

Create a ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap

metadata:
  name: demo-configmap

data:
  DB_HOST: "172.31.10.30:3306"
  DB_USER: "dbadmin"
  DB_PASS: "db!2312$#"
  APP_MODE: "production"
  APP_CAPACITY: "100%"

  large-data: |
    This is Line 1
    This is Line 2
    This is Line 3
```

Deploy

```bash
kubectl apply -f configmap.yaml
```

# Method 1 - Mount ConfigMap as Files

Documentation:

https://kubernetes.io/docs/tasks/configure-pod-container/configure-pod-configmap/#add-configmap-data-to-a-volume

Pod Manifest

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: configmap-volume-pod

spec:
  containers:
  - name: nginx-container
    image: nginx

    volumeMounts:
    - name: config-volume
      mountPath: /etc/config

  volumes:
  - name: config-volume
    configMap:
      name: demo-configmap
```

Deploy

```bash
kubectl apply -f pod.yaml
```

Verify

```bash
kubectl exec -it configmap-volume-pod -- sh
```

```bash
cd /etc/config

ls

cat APP_MODE

cat DB_HOST
```

Each ConfigMap key becomes a file inside `/etc/config`.

---

# Method 2 - Use ConfigMap as Environment Variables

Pod Manifest

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: configmap-env-pod

spec:
  containers:
  - name: nginx-container
    image: nginx

    env:
    - name: MODE_APP
      valueFrom:
        configMapKeyRef:
          name: demo-configmap
          key: APP_MODE
```

Deploy

```bash
kubectl apply -f pod-env.yaml
```

Verify

```bash
kubectl exec -it configmap-env-pod -- sh
```

```bash
echo $MODE_APP
```

Output

```text
production
```

# Immutable ConfigMaps

An **Immutable ConfigMap** cannot be modified after it is is created.

Benefits

- Prevents accidental updates
- Improves API server performance
- Suitable for stable production configurations

Documentation:

https://kubernetes.io/docs/concepts/configuration/configmap/#configmap-object

---

# Mutable ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap

metadata:
  name: mutable-configmap

data:
  config.properties: |
    APP_MODE=production
    LOG_LEVEL=info
```

---

# Immutable ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap

metadata:
  name: immutable-configmap

immutable: true

data:
  config.properties: |
    APP_MODE=production
    LOG_LEVEL=info
```

Create

```bash
kubectl apply -f mutable-cm.yaml

kubectl apply -f immutable-cm.yaml
```

---

# Edit ConfigMaps

Mutable ConfigMap

```bash
kubectl edit configmap mutable-configmap
```

Immutable ConfigMap

```bash
kubectl edit configmap immutable-configmap
```

The second command will fail because immutable ConfigMaps cannot be modified.

---

# Mount an Immutable ConfigMap

Deployment

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: my-app

spec:
  replicas: 2

  selector:
    matchLabels:
      app: my-app

  template:
    metadata:
      labels:
        app: my-app

    spec:
      containers:
      - name: my-app-container
        image: nginx

        ports:
        - containerPort: 80

        volumeMounts:
        - name: config-volume
          mountPath: /etc/myapp/config

      volumes:
      - name: config-volume
        configMap:
          name: immutable-configmap
```

Deploy

```bash
kubectl apply -f app-deployment.yaml
```

Verify

```bash
kubectl get pods
```

```bash
kubectl exec -it <pod-name> -- sh
```

```bash
cd /etc/myapp/config

ls

cat config.properties
```

# Updating an Immutable ConfigMap

Since immutable ConfigMaps cannot be modified, create a new ConfigMap.

```yaml
apiVersion: v1
kind: ConfigMap

metadata:
  name: immutable-configmap-v2

immutable: true

data:
  config.properties: |
    APP_MODE=production-V2
    LOG_LEVEL=debug
```

Deploy

```bash
kubectl apply -f immutable-v2.yaml
```

Edit the Deployment

```bash
kubectl edit deployment my-app
```

Change

```yaml
configMap:
  name: immutable-configmap
```

to

```yaml
configMap:
  name: immutable-configmap-v2
```

Verify

```bash
kubectl get pods
```

Check the updated configuration

```bash
kubectl exec -it <pod-name> -- sh
```

```bash
cat /etc/myapp/config/config.properties
```

Output

```text
APP_MODE=production-V2
LOG_LEVEL=debug
```

# Comparison of ConfigMap Creation Methods

| Method | Use Case | Advantage | Disadvantage |
|----------|----------|-----------|--------------|
| `--from-literal` | Small key-value pairs | Quick and simple | Not suitable for large configurations |
| `--from-file` | Individual configuration file | Easy to manage single files | One key per filename |
| `--from-file=<directory>` | Multiple configuration files | Creates multiple entries automatically | Keys are based on filenames |
| YAML Manifest | Production deployments | Version controlled, reusable, GitOps friendly | Requires creating a YAML file |

---

# Summary

- ConfigMaps store **non-sensitive configuration data**.
- Configuration is stored as key-value pairs.
- ConfigMaps separate configuration from application code.
- They can be created from literals, files, directories, or YAML manifests.
- Applications can consume ConfigMaps as mounted files or environment variables.
- Immutable ConfigMaps cannot be modified after creation and are recommended for stable production workloads.
- Use **Secrets** instead of ConfigMaps for passwords, API keys, certificates, or other sensitive data.
