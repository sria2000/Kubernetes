# Kubernetes Security Context

## Overview

A **Security Context** defines privilege and access control settings for a Pod or Container.

It allows you to control:
- The Linux user and group a container runs as.
- File ownership for mounted volumes.
- Privilege escalation and Linux capabilities.
- Access to the host filesystem and other security-related settings.

Without a Security Context, containers often run as the **root user (UID 0)**, which increases security risks.

Documentation Referenced:

https://kubernetes.io/docs/tasks/configure-pod-container/security-context/

---

# Why Use Security Context?

- Run containers as a non-root user.
- Reduce the impact of container compromise.
- Control ownership and permissions of mounted volumes.
- Improve overall Kubernetes security.

---

# Important Security Context Parameters

| Parameter | Description |
|-----------|-------------|
| runAsUser | User ID (UID) the container runs as. |
| runAsGroup | Primary Group ID (GID) for the container. |
| fsGroup | Group ownership applied to mounted volumes. |
| privileged | Runs container with full privileges. (Avoid if possible.) |
| allowPrivilegeEscalation | Allows/disallows privilege escalation. |
| readOnlyRootFilesystem | Makes root filesystem read-only. |

# Example 1 - Insecure Pod (Runs as Root)

## Pod Manifest

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: insecure-pod
spec:
  containers:
  - name: demo-container
    image: busybox:latest
    command: ["sleep","36000"]
    volumeMounts:
    - name: host-root
      mountPath: /host

  volumes:
  - name: host-root
    hostPath:
      path: /
```

Create the Pod

```bash
kubectl apply -f pod.yaml
```

Connect to the Pod

```bash
kubectl exec -it insecure-pod -- sh
```

Verify current user

```bash
id
```

Example Output

```text
uid=0(root) gid=0(root)
```

Browse the mounted host filesystem

```bash
cd /host

ls
```

The container is running as **root**, giving it elevated privileges.

# Example 2 - Run Container as Non-Root

## Pod Manifest

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: controlled-pod

spec:

  securityContext:
    runAsUser: 1000
    runAsGroup: 2000
    fsGroup: 3000

  containers:
  - name: demo-container
    image: busybox:latest
    command: ["sleep","36000"]

    volumeMounts:
    - name: host-root
      mountPath: /host

  volumes:
  - name: host-root
    hostPath:
      path: /
```

Create the Pod

```bash
kubectl apply -f pod-controlled.yaml
```

Connect to the Pod

```bash
kubectl exec -it controlled-pod -- sh
```

Verify User

```bash
id
```

Example Output

```text
uid=1000 gid=2000 groups=2000,3000
```

Navigate to mounted directory

```bash
cd /host/tmp

touch test.txt

ls -l
```

The container now runs as a **non-root user**, significantly improving security.

# Example 3 - fsGroup with EmptyDir Volume

When a Pod mounts an **emptyDir** volume, Kubernetes can automatically change the group ownership using **fsGroup**.

## Pod Manifest

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: fsgroup-pod

spec:

  securityContext:
    runAsUser: 1000
    runAsGroup: 2000
    fsGroup: 3000

  volumes:
  - name: host-root
    emptyDir: {}

  containers:
  - name: demo-container
    image: busybox:latest
    command: ["sleep","36000"]

    volumeMounts:
    - name: host-root
      mountPath: /host
```

Create the Pod

```bash
kubectl apply -f pod-fs.yaml
```

Connect to the Pod

```bash
kubectl exec -it fsgroup-pod -- sh
```

Verify User

```bash
id
```

Navigate to mounted volume

```bash
cd /host

touch test.txt

ls -la
```

Example Output

```text
total 8
drwxrwsrwx    2 root     3000          4096 Jul 31 20:29 .
drwxr-xr-x    1 root     root          4096 Jul 31 20:28 ..
-rw-r--r--    1 1000     3000             0 Jul 31 20:29 test.txt
```

Notice:

- Directory group owner is **3000**
- New file owner is **UID 1000**
- File group owner is **3000**

This demonstrates how **fsGroup** automatically applies group ownership to mounted volumes.

# Security Context Flow

```
Pod
 │
 ├── securityContext
 │      │
 │      ├── runAsUser
 │      ├── runAsGroup
 │      └── fsGroup
 │
 └── Containers
        │
        ├── Run as specified Linux user
        └── Mounted volumes inherit fsGroup permissions
```

# Best Practices

- Never run application containers as **root** unless absolutely necessary.
- Always specify **runAsUser** whenever possible.
- Use **fsGroup** for shared writable volumes.
- Avoid using **privileged: true**.
- Disable privilege escalation where possible.
- Use read-only root filesystems for stateless applications.
- Follow the principle of least privilege.

# Summary

- Security Context controls Linux security settings for Pods and Containers.
- Containers run as **root by default** unless configured otherwise.
- **runAsUser** specifies the user ID.
- **runAsGroup** specifies the primary group.
- **fsGroup** changes group ownership of mounted volumes.
- Running containers as non-root is a Kubernetes security best practice.
- Security Context helps reduce the attack surface and improves workload isolation.
