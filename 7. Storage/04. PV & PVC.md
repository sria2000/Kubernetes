# Kubernetes Persistent Volumes (PV) & Persistent Volume Claims (PVC)

## Overview

Containers have an ephemeral filesystem, meaning data is lost when a Pod is deleted. Kubernetes solves this problem using **Persistent Volumes (PV)** and **Persistent Volume Claims (PVC)**.

A **Persistent Volume (PV)** is a piece of storage in the Kubernetes cluster that has been provisioned either manually by an administrator or dynamically using a StorageClass.

A **Persistent Volume Claim (PVC)** is a request for storage made by a user or developer. It specifies the required storage size, access mode, and StorageClass. Kubernetes automatically binds the PVC to a suitable PV.

A Persistent Volume can be backed by many storage technologies, including:

- AWS EBS
- Azure Disk
- Google Persistent Disk
- NFS
- GlusterFS
- Ceph
- hostPath
- Local Storage
- CSI Drivers

Documentation:

- https://kubernetes.io/docs/concepts/storage/persistent-volumes/

---

# Storage Flow

```
                Physical Storage
                       │
                       ▼
              Persistent Volume (PV)
                       │
                 (Automatic Binding)
                       │
                       ▼
          Persistent Volume Claim (PVC)
                       │
                       ▼
                  Application Pod
```

---

# Persistent Volume (PV)

A Persistent Volume is cluster storage managed by Kubernetes.

Characteristics:

- Cluster-wide resource
- Created by an administrator or dynamically
- Exists independently of Pods
- Can be reused
- Backed by many storage systems
- Has a fixed capacity
- Defines supported access modes

---

# Persistent Volume Claim (PVC)

A Persistent Volume Claim is a storage request made by an application.

A PVC specifies:

- Required storage size
- Access mode
- StorageClass
- Optional selector

When a matching PV exists, Kubernetes automatically binds the claim to that volume.

---

# Access Modes

| Access Mode | Description |
|-------------|-------------|
| ReadWriteOnce (RWO) | Mounted as read/write by one node |
| ReadOnlyMany (ROX) | Mounted as read-only by many nodes |
| ReadWriteMany (RWX) | Mounted as read/write by many nodes |
| ReadWriteOncePod (RWOP) | Mounted by only one Pod |

---

# Static Provisioning

In static provisioning, an administrator creates Persistent Volumes before applications request storage.

```
Administrator
      │
      ▼
Create PV
      │
      ▼
Developer Creates PVC
      │
      ▼
Kubernetes Matches PVC to PV
      │
      ▼
Application Uses Storage
```

---

# Lab 1 - Static Provisioning

## Step 1 - Create Persistent Volume (1 GB)

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: manual-pv-1gb

spec:
  storageClassName: manual

  capacity:
    storage: 1Gi

  accessModes:
  - ReadWriteOnce

  hostPath:
    path: /mnt/data/1gb
```

Create the PV

```bash
kubectl apply -f pv-1.yaml
```

---

## Step 2 - Create Persistent Volume (3 GB)

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: manual-pv-3gb

spec:
  storageClassName: manual

  capacity:
    storage: 3Gi

  accessModes:
  - ReadWriteOnce

  hostPath:
    path: /mnt/data/2gb
```

Create the PV

```bash
kubectl apply -f pv-2.yaml
```

Verify

```bash
kubectl get pv
```

Example Output

```text
NAME            CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      STORAGECLASS
manual-pv-1gb   1Gi        RWO            Retain           Available   manual
manual-pv-3gb   3Gi        RWO            Retain           Available   manual
```

---

# Step 3 - Create a Persistent Volume Claim

Although 1 Gi and 3 Gi volumes exist, the application requires **2 Gi**.

Kubernetes automatically selects the smallest matching Persistent Volume.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim

metadata:
  name: manual-pvc-2gb

spec:
  accessModes:
  - ReadWriteOnce

  storageClassName: manual

  resources:
    requests:
      storage: 2Gi
```

Create the PVC

```bash
kubectl apply -f pvc.yaml
```

Verify

```bash
kubectl get pvc
```

Example Output

```text
NAME             STATUS   VOLUME          CAPACITY
manual-pvc-2gb   Bound    manual-pv-3gb   3Gi
```

Notice Kubernetes selected the **3 Gi** PV because the **1 Gi** volume was too small.

---

# Step 4 - Create a Pod Using the PVC

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: test-pod

spec:
  containers:
  - name: app
    image: busybox
    command: ["sleep","3600"]

    volumeMounts:
    - name: mydata
      mountPath: /data

  volumes:
  - name: mydata
    persistentVolumeClaim:
      claimName: manual-pvc-2gb
```

Deploy

```bash
kubectl apply -f pod-pvc.yaml
```

Verify

```bash
kubectl exec -it test-pod -- sh
```

```bash
cd /data

touch file1.txt

ls -l
```

The Pod is now using persistent storage provided through the PVC.

# Static vs Dynamic Provisioning

## Static Provisioning

Administrator creates Persistent Volumes before they are needed.

```
Admin Creates PV
        │
        ▼
Developer Creates PVC
        │
        ▼
PVC Matches Existing PV
```

If no suitable PV exists, the PVC remains **Pending**.

---

## Dynamic Provisioning

Persistent Volumes are created automatically when a PVC is created.

```
Developer Creates PVC
        │
        ▼
StorageClass
        │
        ▼
Provisioner Creates PV
        │
        ▼
PVC Automatically Bound
```

Dynamic provisioning is the preferred approach for production Kubernetes clusters.

---

# StorageClass

A **StorageClass** tells Kubernetes how to dynamically provision storage.

It defines:

- Storage provisioner
- Storage type
- Reclaim policy
- Volume binding mode
- Expansion support

Example

```bash
kubectl get storageclass
```

Output

```text
NAME                   PROVISIONER             RECLAIMPOLICY
local-path (default)   rancher.io/local-path   Delete
```

# Create a PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim

metadata:
  name: local-path-pvc

spec:
  accessModes:
  - ReadWriteOnce

  storageClassName: local-path

  resources:
    requests:
      storage: 128Mi
```

Deploy

```bash
kubectl apply -f rancher-pvc.yaml
```

Verify

```bash
kubectl get pvc

kubectl describe pvc local-path-pvc
```

Notice that Kubernetes automatically creates a matching Persistent Volume.

# Create a Pod

```yaml
apiVersion: v1

Deploy

kubectl apply -f test-pod.yaml

Verify

```bash
kubectl get pvc

```

```text
NAME             STATUS   VOLUME                                     CAPACITY
local-path-pvc   Bound    pvc-3a7efb40-xxxx-xxxx-xxxx-xxxxxxxxxxxx    128Mi
```

A new Persistent Volume was automatically created by the StorageClass.

# Persistent Volume Reclaim Policies

| Policy | Description |
|---------|-------------|
| Retain | Keeps the storage after the PVC is deleted |
| Delete | Deletes the storage automatically |
| Recycle *(Deprecated)* | Basic cleanup before reuse |

---

# PV vs PVC

| Persistent Volume (PV) | Persistent Volume Claim (PVC) |
|-------------------------|-------------------------------|
| Actual storage resource | Request for storage |
| Created by Admin or StorageClass | Created by Developer/Application |
| Cluster scoped | Namespace scoped |
| Supplies storage | Consumes storage |
| Can exist without PVC | Requires a matching PV |

---

# Summary

- A **Persistent Volume (PV)** is storage managed by Kubernetes.
- A **Persistent Volume Claim (PVC)** is a request for storage made by an application.
- Kubernetes automatically binds a PVC to a matching PV.
- Static provisioning requires administrators to create PVs ahead of time.
- Dynamic provisioning automatically creates PVs using a StorageClass.
- StorageClasses are the preferred solution for modern Kubernetes deployments.
- PVs allow application data to survive Pod deletion and recreation.
