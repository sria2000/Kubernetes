# Kubernetes Version Skew Policy

## Overview

On a control plane node, there can be multiple versions of individual components in play at once — e.g. `etcd`, `kubectl`, and `kube-apiserver` may all sit on different versions.

**Example:** `kubectl` at v1.26 and `kube-apiserver` at v1.33.

If the skew between components is too large, it can cause compatibility errors. Kubernetes defines a formal **version skew policy** to bound how far apart components are allowed to drift.

## Version Basics

Kubernetes versions follow **`MAJOR.MINOR.PATCH`**.

**Example:** `v1.32.2`
- Major: `1`
- Minor: `32`
- Patch: `2`

Version skew rules are expressed in terms of **minor version** differences.

---

## kube-apiserver and kubelet

| Component | Version Skew |
|---|---|
| **kube-apiserver** | In highly-available (HA) clusters, the newest and oldest `kube-apiserver` instances must be within **one minor version**.<br><br>Example: if the newest `kube-apiserver` is at 1.32, other `kube-apiserver` instances are supported at 1.32 and 1.31. |
| **kubelet** | `kubelet` must not be newer than `kube-apiserver`.<br><br>`kubelet` may be up to **three minor versions older** than `kube-apiserver`.<br><br>**Example:**<br>`kube-apiserver` is at 1.32<br>`kubelet` is supported at 1.32, 1.31, 1.30, and 1.29 |

---

## kube-proxy

| Component | Version Skew |
|---|---|
| **kube-proxy** | `kube-proxy` must not be newer than `kube-apiserver`.<br><br>`kube-proxy` may be up to **three minor versions older** than `kube-apiserver`.<br><br>**Example:**<br>`kube-apiserver` is at 1.32<br>`kube-proxy` is supported at 1.32, 1.31, 1.30, and 1.29 |

---

## Controller Manager, Scheduler, Cloud Controller Manager

| Component | Version Skew |
|---|---|
| **Controller Manager, Scheduler, Cloud Controller Manager** | Must not be newer than the `kube-apiserver` instances they communicate with.<br><br>Expected to match the `kube-apiserver` minor version, but may be up to **one minor version older** (to allow live upgrades).<br><br>**Example:**<br>`kube-apiserver` is at 1.32<br>`kube-controller-manager`, `kube-scheduler`, and `cloud-controller-manager` are supported at 1.32 and 1.31 |

---

## kubectl

| Component | Version Skew |
|---|---|
| **kubectl** | Supported within **one minor version (older or newer)** of `kube-apiserver`.<br><br>**Example:**<br>`kube-apiserver` is at 1.32<br>`kubectl` is supported at 1.33, 1.32, and 1.31 |

---

## Quick Reference — Max Allowed Skew from kube-apiserver

| Component | Max skew from kube-apiserver |
|---|---|
| kube-apiserver (across HA instances) | 1 minor version |
| kubelet | up to 3 minor versions older |
| kube-proxy | up to 3 minor versions older |
| kube-controller-manager / kube-scheduler / cloud-controller-manager | up to 1 minor version older |
| kubectl | up to 1 minor version older **or** newer |

## Why This Matters

- **Upgrade order** follows from this policy: `etcd` → `kube-apiserver` → `kube-controller-manager` / `kube-scheduler` → `kubelet` / `kube-proxy` → `kubectl`, upgrading the API server first since nothing else is allowed to be newer than it.
- Exceeding the allowed skew is a common source of `CrashLoopBackOff`, RBAC/API incompatibilities, or silent feature mismatches during cluster upgrades — especially in mixed-node clusters where node pools are upgraded in stages.
- Relevant for interview prep on cluster upgrade strategy (e.g. `kubeadm upgrade plan` / `kubeadm upgrade apply`) as well as day-to-day homelab maintenance when kubelet and API server versions drift after partial upgrades.
