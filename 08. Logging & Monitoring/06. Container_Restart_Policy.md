# Container Restart Policy in Kubernetes

## Overview

Kubernetes uses **Restart Policy** to decide what action should be taken when a container inside a Pod exits.

The restart policy is defined at the **Pod level** and controls whether containers should be restarted after they stop.

Available restart policies:
- **Always** (default)
- **OnFailure**
- **Never**

---

## Restart Policy Comparison

| Restart Policy | Description |
|---|---|
| **Always** | Instructs Kubernetes to restart a container whenever it terminates, regardless of whether the exit was due to a success (exit code 0) or a failure. **Always is the default restart policy.** |
| **OnFailure** | Kubernetes will only restart a container if it terminates with a non-zero exit code (indicating a failure). |
| **Never** | Kubernetes will not restart a container once it has terminated, regardless of the exit status (success or failure). |

---

# 1. Always Restart Policy

## Description

`Always` is the default restart policy in Kubernetes.

- Kubernetes will always restart the container when it exits.
- Used for long-running applications such as web servers, APIs, databases, etc.
- The container keeps restarting until the Pod is deleted.

## Example

Create a Pod with a command that does not exist:

```bash
kubectl run test-pod --image=busybox -- nonexistentcommand
```

Since no `--restart` flag is specified, the Pod defaults to `restartPolicy: Always`. Even though the container fails immediately (bad command), Kubernetes will keep restarting it, and you'll see the Pod cycle through `CrashLoopBackOff`.

```bash
kubectl get pods
kubectl describe pod test-pod
```

---

# 2. OnFailure Restart Policy

## Description

- Kubernetes restarts the container **only** if it exits with a non-zero exit code (failure).
- If the container exits successfully (exit code 0), it is **not** restarted.
- Commonly used for **batch jobs** or **one-off tasks** that should retry on failure but not on success — this is also the default behavior enforced by `Job` objects.

## Example

Create a Pod manifest with `restartPolicy: OnFailure`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: onfailure-demo
spec:
  restartPolicy: OnFailure
  containers:
  - name: demo
    image: busybox
    command: ["sh", "-c", "exit 1"]
```

```bash
kubectl apply -f onfailure-demo.yaml
kubectl get pods -w
```

Because the container exits with code 1 (failure), Kubernetes will keep restarting it. If the command were changed to `exit 0`, the container would terminate successfully and would **not** be restarted — the Pod would show as `Completed`.

---

# 3. Never Restart Policy

## Description

- Kubernetes will **not** restart the container once it terminates, regardless of exit status.
- Useful for **one-time tasks** where you want to inspect the exact result/logs without Kubernetes retrying automatically.
- Common in debugging Pods, one-shot diagnostic containers, or manual test runs.

## Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: never-demo
spec:
  restartPolicy: Never
  containers:
  - name: demo
    image: busybox
    command: ["sh", "-c", "exit 1"]
```

```bash
kubectl apply -f never-demo.yaml
kubectl get pods
kubectl logs never-demo
```

The container will exit with a failure and stay in a `Error` / terminated state — Kubernetes will not attempt to restart it, whether it succeeded or failed.

---

## Quick Reference

| Scenario | Recommended Policy |
|---|---|
| Long-running services (web servers, DBs, APIs) | `Always` |
| Batch jobs / retry-on-failure tasks (typically via `Job`) | `OnFailure` |
| One-shot debugging / diagnostic Pods | `Never` |

> **Note:** `restartPolicy` applies to all containers within a Pod and is set at the Pod spec level (`spec.restartPolicy`) — it cannot be set per-container. Also note that `Job` and `CronJob` objects only permit `OnFailure` or `Never` (not `Always`), since a completed Job shouldn't loop forever.
